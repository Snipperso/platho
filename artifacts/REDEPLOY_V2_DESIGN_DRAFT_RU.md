## 0. Ключевые измеренные факты

- Внешнее сообщение: жёсткий лимит 65 535 байт BOC, глубина ≤ 512. Один 32K-класс капсулы = 35 618 байт (275 ячеек, глубина 271). **Два 32K никогда не влезут в один external.**
- Вместимость батча в ОДНОМ external (консервативная цель 48 KiB): **20×1K / 14×2K / 8×4K / 4×8K / 2×16K / 1×32K** (на 64KB: 26/18/11/6/3/1).
- Гас: ~110 гас/ячейку + ~165k фиксированных на всю цепочку публикации (Vault external ~92k + Hub ~43k + ACK ~32k). Худший батч ≈ 270–350k << лимита 1M на транзакцию. **Связывающее ограничение — байты, не гас.**
- Pre-accept кредит 10k гас — реально упирались (комментарии Vault.tact:2007, 2037-2040): pre-accept должен остаться O(1).
- Тарифная база: репозиторий пинит снапшот mainnet 2026-04-30 (scripts/publish_reserve_pricing.ts:180-197): gas 66.67 nano/gas, cell_price_ps=135, bit_price_ps=0. Историческая «классическая» сетка в 6 раз дороже. **Иммутабельные константы обязаны закладываться на классическую сетку (текущие дешёвые цены — как скидка), иначе ревот конфига ломает экономику навсегда.**
- m17 gas-харнесс покрывает только 1K-класс, и его порог 100k гас УЖЕ превышен реальными 16K/32K публикациями (106k/119k) — перебазировать обязательно.
- Реальное распределение частей: текст = 1 часть; фото good = 1–2; фото maximum (продуктовый кап 64 KB) = ровно 2 части 2×32K — поправка владельца 2026-06-12, не 3. Батч закрывает «много мелких», но НЕ max-фото (2 серийных external с пайплайнингом nonce).

## 1. Батч-публикация (VPB2) — исправленный дизайн

Один подписанный external несёт N капсул под ОДНИМ nonce.

- Подписанный корень: domain `VPB2` u32 | manifest u256 | vault_hash u256 | kind u8 | owner_hash u256 | clientNonce u64 | maxCharge u128 | part_count u8 | version u8 (резерв эволюции) | ref → список частей.
- Часть (private): существующая 784-битная форма {size_class, suite, h0, h1, body-hash + 3 refs}. Часть (public): отдельная форма с header_hash + author_wallet + marketing_note — kind задаётся на уровне батча, формы частей различаются по kind (критик полноты: public-вариант обязателен, marketing_note/author_wallet контрактно-обязательны per entry).
- **Pre-accept (O(1), только корень, БЕЗ разбора списка частей — педант/секьюрити):** подпись + nonce + границы part_count + `ton_balance >= part_count × WORST_CASE_PER_PART_RESERVE` (константа, НЕ заявленный отправителем скаляр — закрывает lie-вектор, где Vault платил бы за разбор 20×32K из своего кармана). acceptMessage → дебет резерва → nonce+1 → **запись receipt {status=processing}** → commit.
- Post-accept: цикл по частям (Tact без break — флаговый цикл), exact-shape каждого узла списка ДО computeDataSize (анти cell-bomb; computeDataSize сам ограничен и бросается за капом), пересчёт канонического тарифа от ИЗМЕРЕННЫХ (cells, bits) — база (part_count, total_bytes) недоопределена (экономист). Дубликаты частей внутри батча: запретить равные соседние (h0,h1,body) — одно сравнение на часть.
- **Реджект атомарен И ДЛЯ ДЕНЕГ:** любая невалидность → receipt {reject_code, part_index} + **возврат неизрасходованного резерва** (минус фикс. анти-спам). Мой черновик молча сжигал до ~1.35 TON — это была ошибка, найдена всеми тремя аудиторами. Коды реджекта — стабильный ABI: retryable / permanent / rebuild-without-part, с общими тест-векторами в artifacts/.
- Один внутренний PublishBatchToHub: подписанный список частей форвардится **как есть** (ноль пере-сериализации); bounce_id u64 + bounce_tag u160 первыми (224 бита переживают баунс-обрезание).
- **Ключ pending_publishes: ОСТАЁТСЯ mod-2^64** + внутри PendingPublish хранится полный publish_id u256 и nonce (для receipt-слота); ACK/bounce сверяют полный id. Мой пункт «полный u256-ключ» ПРОТИВОРЕЧИЛ баунс-восстановлению (баунс отдаёт только первые 224 бита — ключ невосстановим) — найдено независимо тремя критиками. Коллизия mod-2^64 — liveness-неудобство (~2^-64), теперь видимое через receipt, а не молчаливое сжигание.
- Hub: validate-all-then-commit-all, **ни одного commit() внутри цикла** (атомарность отката), последовательные entry_id, индексы пушатся в порядке частей, ОДИН ACK {publish_id, first_entry_id u64, part_count u16, batch_uid = hash(пер-entry uid'ов)}. Баунс-обработчик ДОКАЗУЕМО не бросается на легитимном баунсе (нельзя «забаунсить баунс»).
- Пер-entry publish_id = hash(domain-тег u32 ‖ batch_publish_id u256 ‖ part_index u16) — с отдельным доменом, доказуемая дизъюнктность от легаси-id и uid (секьюрити).
- **Аирдроп: батч-ACK кредитует min(part_count × 10 ATH, remaining)** — иначе ломается задокументированное «10 ATH за финализированную капсулу» и вся пост-пул цепочка гейтов (критик полноты).
- **MAX_BATCH капится по ИЗМЕРЕННОМУ гасу хаба, не только по байтам**; m17-харнесс расширяется на все классы × представительные part_count, и сгенерированный артефакт потребляется и контрактными константами, и web/capsule-part-policy.mjs (защита от дрейфа).
- **Батч с part_count=1 — ЕДИНСТВЕННЫЙ путь публикации** (VPB1 умирает). Все пять критиков сошлись: два живых ABI публикации = двойная аудит-поверхность и клиент, который ничего не удаляет.

## 2. Receipts (квитанции) — исправленный дизайн

- Кольцо последних K квитанций на пользователя: отдельная ref-ячейка в UserState. Поля {nonce u64, action u8, result u8, entry_id/aux u64, part_count u8, at u32} = 184 бита (мой подсчёт 154 был неверен). **K=6 в одной ячейке; рекомендация K=8–10 во второй** (бурст «3 external фото + аватар = 5 nonce» выселяет K=4 до ACK — это пере-создание клина, который мы лечим).
- Запись при КАЖДОМ потреблении nonce (все 10 типов действий); каждый из 17(private)+14(public) молчаливых return'ов становится receipt-записью.
- **Обновления по nonce, не по позиции слота:** ACK/bounce/tombstone находят слот по nonce, сверяют slot.nonce, no-op при выселении (иначе поздний ACK штампует «confirmed» на чужую квитанцию). PendingPublish и Pending*Payment структуры получают поле nonce.
- **`processing` НЕ терминален** (out-of-gas post-accept; action-phase err 37 после commit) — клиент сохраняет тонкий таймаут-фоллбек. Диагностика различима одним геттером: processing+nonce-ушёл+pending-есть (action-фаза) vs pending-нет (out-of-gas).
- Маппинг result-кодов для ВСЕХ типов: ATH-флоу (аватар/минт) имеют другой жизненный цикл (ATH восстанавливается на ath_balance, не TON-рефанд) — отдельные коды; финальность минта username = ACK реестра, НЕ ATH-перевод.
- `get_user_receipts(owner)` возвращает **(текущий publish_nonce, receipts[])** одним вызовом — заменяет и nonce-поллинг, и discovery подтверждения (лучшее предложение клиент-скептика).
- Честность модели доверия: receipts — ускоритель ОБНАРУЖЕНИЯ, не якорь доверия. «Доставлено» по-прежнему = само-аутентифицированная сверка entry по хешам (политика verified-курсоров d3472cd сохраняется). Удаляется реально: парсинг ack-истории (зависимость от message-history — region-blockable!), absence-proof'ы, nonce-эвристики, клин-восстановление. Сверка payload-match остаётся.

## 3. Гигиена Vault — что осталось после критики

- ✅ Pending хранит полный publish_id (сверка) + nonce (receipt-корреляция).
- ✅ O(1) shape-чек КОРНЯ pre-accept (только корень! пер-частный разбор — post-accept; merить с part_count=20 на 64KB external против 10k кредита).
- ✅ ACK переносит фактический остаток через **explicit RESERVE retained → mode 128** (хаб сперва резервирует fee+endowment+keepalive — не дренируем protectedReserve; ACK перестаёт фейлиться по value → стейл-пендинги почти исчезают). Vault-приёмник ACK толерантен к пыли.
- ❌ **maxCharge-кламп ОТМЕНЁН** — убивал surcharge-механизм (единственный канал адаптации к фи-спайкам на иммутабельном контракте). Полный подписанный дебет остаётся; излишек авто-возвращается через mode-128 ACK.
- ❌ **Tombstone-рефанд ОТМЕНЁН** — секьюрити показал: callValue в момент tombstone НЕ у Vault (ушёл к хабу) — кредитовать = фантомные деньги/недообеспеченность; а если entry создан, юзер получил бы и entry, и рефанд (фарм при деградации ACK). Консервативное stranding — осознанный fail-closed; корневое лечение = надёжность ACK (см. выше).
- ✅ Все денежные константы: размер под КЛАССИЧЕСКУЮ сетку + рантайм fee-примитивы Tact 1.6 (getForwardFee/getComputeFee/getStorageFee) где возможно; **расширить scripts/publish_reserve_pricing.ts до генератора констант контракта + таблиц message-pricing-policy.mjs** из пиненного снапшота (контракт/клиент/артефакт не могут разойтись).
- ⚠️ Найден существующий неучтённый риск: текущие localExecReserve для ≥4K классов не покрывают форвард-фи при классической сетке (32K: 0.0676 vs ~0.116 TON) — тихий дренаж Vault при ревоте цен; тесты проверяют только пользовательский леджер, не дрейф баланса Vault. Добавить тест-инвариант на дрейф.
- ✅ «Successor manifest» — одноразовая (genesis-controller, one-shot) запись в V2 Vault, объявляющая преемника: иммутабельность сохраняется, а СЛЕДУЮЩАЯ миграция становится обнаружимой в протоколе (этот редеплой страдает от split-brain именно из-за её отсутствия).

## 4. Read-API CapsuleHub

- `get_private_entries(key_id, role, from_link, limit)` — несколько entry-view за вызов; **кодирование: одна ячейка/словарь** (надёжно на всех провайдерах включая keyless-аварийный), не вложенные кортежи; в ответе prev-links + created_at + эхо головы — ОДИН verified-вызов и импортирует, и легально двигает курсор (политика d3472cd выживает). Лимит — по ИЗМЕРЕННОМУ гасу get-метода (хеши заголовков на entry), клиент по умолчанию 8.
- `get_private_entry_range(from_id, count)` — id-based, prune-независимый архивный путь; у link-walk геттера — флаг «tail possibly truncated» (middle-prune рвёт список — задокументировано в контракте).
- Синк-проход: ~50 runGetMethod → 3–6. На аварийном keyless (~1 rps) — минута → секунды.
- Сторожить: парсер тел из истории (web/capsulehub-ton-rpc-provider.mjs) знает только старые опкоды — батч-опкод = N тел в одной транзакции, парсер переписывается (включая dual-provider verify).

## 5. Username NFT — рент-фикс (входит в V2; отдельный срочный деплой отменён решением Q5)

Исправленная экономика (по пиненному снапшоту): 38KB кода на айтем = **0.0317 TON/год** (не 0.253 — та цифра по классической сетке), эндаумент 0.021 TON истощается за ~242 дня, заморозка (долг > 0.1 TON) — ещё позже. Не «30 дней», но структурно сломано: **минт оплачивается в ATH и не даёт НИКАКОГО рекуррентного TON** — вечный пер-айтем арт нефинансируем в принципе.

- **Collection-render (TEP-62):** арт рендерит реестр в get_nft_content; айтем сжимается до ~1.3KB ({owner, registry, name_hash, username}) → 0.0008 TON/год, эндаумент хватает на ~26 лет; fwd-фи минта 0.022 → 0.002 TON; registry initOf тоже худеет (сейчас 53.6KB).
- ⚠️ Текущий get_nft_content реестра — ПАССТРУ (echo individual_content), рендера нет — его надо написать.
- ⚠️ **НЕ перекодировать SVG в percent-encoding на лету** (~19KB × ~150-200 гас/байт = 3-4M гас — потолок публичных get-методов). Алфавит юзернеймов URI-safe — динамики нет вовсе: держать ОБЕ статические копии в коллекции (один рент-счёт) или выбросить одну репрезентацию ПОСЛЕ эмпирической проверки.
- ⚠️ **Эмпирически проверить getgems/tonkeeper/toncenter-индексер на testnet ДО удаления пер-айтем арта** (наивные интеграции читают item-side individual_content напрямую).
- Уже сминченные 38KB-айтемы — тестовые, бросаются вместе со старым реестром (решение Q1/Q5); программа TopUpStorageReserve не нужна.
- Дополнительно по решению Q6: семантика `NameRecord.owner_wallet` (не обновляется при NftTransfer — переименовать/задокументировать как минтера), опциональное `username_item_address` в ProfileRegistry для он-чейн активного имени, клиентский UI трансфера и пикер из нескольких принадлежащих имён.

## 6. Что батч НЕ решает (честные границы)

- **Max-фото (2×32K + остаток) остаётся 2–3 серийными external'ами.** Лечение — клиентский трюк (педант, бесплатно, без изменения контрактов): подписать nonce n и n+1, отправить подряд; misordered второй падает PRE-ACCEPT (бесплатно, без сжигания) и переотправляется. + receipts делают каждое плечо подтверждаемым одним геттером. Кросс-external «сессии» ОТВЕРГНУТЫ (возвращают класс клин-состояний).
- Мульти-девайс на одном кошельке: серийный nonce + общее кольцо receipts = «не поддерживается, last-writer-wins» — задокументировать.
- Один батч с частями из разных чатов: атомарный реджект бьёт по всем — клиентская политика: батчить только уже-стоящие в очереди части, зеркальный пре-валидатор форм с ОБЩИМИ тест-векторами.

## 7. РЕШЕНИЯ ВЛАДЕЛЬЦА (зафиксированы 2026-06-12)

Owner-Q&A завершён. Миграционная проблематика из первоначального черновика (снапшоты юзернеймов, dual-hub окно, день-X-визард, legacy-PWA, ре-минт) **СХЛОПНУЛАСЬ**: реальных пользователей нет, аирдроп не раздавался — текущий mainnet-деплой объявляется тестом и бросается.

1. **Полный ре-генезис (Q1).** Все 9 контрактов заново, новый ATH-токен с чистыми 100M. Старый деплой бросаем; единственная «миграция» — владелец руками выводит свой тестовый TON из старого Vault до переключения. Никакого dual-hub, никаких снапшотов, никакого legacy-режима в клиенте.
2. **Аирдроп (Q2).** Канон 10 ATH за капсулу сохраняется; батч-ACK кредитует `min(part_count × 10 ATH, airdrop_remaining)`.
3. **Юзернеймы — без резервов (Q3).** Никаких reserved-списков и привилегированных минтов: владелец после деплоя накапливает ATH сообщениями (10 сообщений → 100 ATH → `platho`, 6 букв) и минтит как обычный пользователь. Анонса до этого момента нет, гонки нет.
4. **Цена батча — пользователю (Q4).** Аффинная формула: цена = база_батча + Σ маржинальных частей. Маржа протокола ТОЛЬКО в явном протокол-фи 0.01 TON/часть. Скрытой маржи в завышенных резервах не делаем (при скачке цен сети она превращается в субсидию от протокола).
5. **Сроки (Q5).** Дедлайна нет, качество первично. Полный цикл: спека → контракты+негативные матрицы → гас-замеры → машинерия → клиент → testnet (вкл. эмпирическую проверку маркетплейсов для NFT) → genesis. NFT-фикс НЕ выделяется в отдельный срочный деплой — входит в V2 (старые 38KB-айтемы бросаются вместе со старым реестром).
6. **Фичи (Q6).**
   - **Передача юзернейма — обязательна** (актив, можно продавать/передавать). Контрактно УЖЕ есть: TEP-62 `NftTransfer` в `UsernameNFTItem.tact:702`, клиентский резолв имя→владелец берёт владельца из state айтема (реестр подтверждает только name_hash→item_address) → трансфер уже работает сквозно. V2 доделывает: (а) семантика `NameRecord.owner_wallet` в реестре — поле НЕ обновляется при трансфере; переименовать в `minter_wallet` или документировать «минтер, не текущий владелец», чтобы аудиторы/интеграторы не приняли за источник истины; (б) клиентский UI трансфера (отправка NftTransfer из кошелька).
   - **Несколько юзернеймов на кошелёк — обязательны.** Контрактно УЖЕ возможно: records ключуются name_hash'ем, пер-кошелькового ограничения нет. Недостаёт обратного резолва: «активный» юзернейм сейчас живёт в localStorage (`platho.wallet.linkedPlathoUsername.v1`) — не переживает смену устройства и не верифицируем получателем без sender-declared метаданных. ПРЕДЛОЖЕНИЕ V2: опциональное поле `username_item_address` в ProfileRegistry (профиль и так редеплоится) — активное имя становится он-чейн, портируемым и проверяемым (резолв: profile → item → owner == кошелёк профиля). Клиент получает пикер активного имени из принадлежащих.
   - **Удаление/редактирование сообщений — НЕ нужно. Групповые чаты — НЕ нужны** (публичные каналы с комментами покрывают). **Платные каналы — НЕ нужны.**
   - **Аватар: `PROFILE_AVATAR_MAX_PARTS` 16 → 2.** Аватар создаётся тем же пайплайном, что и обычная картинка: режимы клиента 8/16/32 KiB (1 капсула) и 64 KiB (2 капсулы) — `app.js:648-651`. Запас до 16 частей в `ProfileRegistry.tact:21` мёртвый; ужимаем инвариант до фактического продукта (меньше поверхность для junk-указателей, проще аудит).

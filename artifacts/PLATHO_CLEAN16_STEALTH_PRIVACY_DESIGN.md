# Дизайн-спецификация: stealth-скан приватных капсул Platho (контур clean-16)

## 0. Резюме решения

Мы скрываем **получателя** и разрываем публично-скрейпимый граф «кто-кому», заменяя предсказуемый маршрутный ярлык `recipient_key_id` на **одноразовую stealth-метку**, выводимую через ECDH(эфемерный ключ отправителя, scan-ключ получателя). Получатель переходит с обхода публичного `private_recipient_index` по своему `key_id` на **сканирование** глобального диапазона капсул: дешёвый X25519-ECDH + сравнение `view_tag` как пред-фильтр, а дорогая расшифровка (ML-KEM-768 + AES-GCM) — только на совпадении.

**База** — семейство `ton-native-pq` / `scan-first-dualkey`: `header0` ужимается со 140 до **74 байт** (2 ячейки/1 ref → 1 ячейка/0 ref), а `sender_sign_pubkey`, `profile_version`, `avatar_hash` переезжают в **зашифрованное тело** (побочный выигрыш: аватар/профиль отправителя больше не светятся on-chain). Тело остаётся hybrid-v1 (X25519 + ML-KEM-768 + AES-GCM) без изменений.

**PQ-решение (явно):** метка — **классический X25519 view_tag шириной u16**; PQ-метку НЕ вводим (обоснование в §7). Тело уже пост-квантово конфиденциально; под остаточным риском только граф, и он документируется владельцу как принятый остаток.

**Отправитель осознанно остаётся видимым** (Phase 1 — рамка владельца). Сокрытие отправителя — Phase 2 (§12).

## 1. Крипто-схема stealth (scan/identity ключи, ECDH, одноразовая метка, эфемерал, view-tag)

### 1.1. Разделение ключей получателя (dual-key)

У получателя в `Vault.KeyRecord` регистрируются ДВА независимых набора:

- **SCAN-ключ (НОВЫЙ):** отдельная пара X25519 `(scan_secret s, scan_pub S = s·G)` — **только для обнаружения**. Делегируема тонкому наблюдателю; её компрометация НЕ раскрывает содержимое.
- **SPEND/IDENTITY-ключи (существующие):** `enc_pubkey` (X25519, тело), `pq_kem_pubkey` (ML-KEM-768, тело), `sign_pubkey` (Ed25519, подпись). НЕ делегируются.

Разделение критично: скан требует лишь `scan_secret`, дешёв и делегируем; открытие тела требует `enc_secret` + ML-KEM-секрет.

### 1.2. Отправитель (всё предвычислимо ДО нажатия «отправить», суб-миллисекунда)

Отправитель по кошельку получателя резолвит его ключи: `get_user(wallet).current_key_id → get_key_record(keyId)` → `{scan_pubkey S, enc_pubkey, pq_kem_pubkey}`.

1. Генерирует **ОДИН СЛУЧАЙНЫЙ** эфемерал `e` (CSPRNG, X25519), `E = e·G`. **Эфемерал переиспользуется** и для тела, и для метки — второго скалярного умножения/второго keygen НЕ плодим (Rule #1). ⚠️ Детерминированная деривация эфемерала **ОТКЛОНЕНА** (см. §1.6).
2. Три общих секрета от одного `e` против РАЗНЫХ ключей получателя:
   - `scan_shared = X25519(e, S)` — для метки (новое, дешёвое);
   - `x25519_shared = X25519(e, enc_pubkey)` — для тела (как сейчас);
   - `mlkem_shared = ML-KEM-768.Encapsulate(pq_kem_pubkey).sharedSecret` — для тела (как сейчас).
   Все результаты X25519 отклоняются, если all-zero/low-order (contributory-проверка, как `deriveX25519SharedSecret` platho-crypto.mjs:186-191).
3. **Одноразовая метка:** `view_tag = HKDF-SHA256(ikm=scan_shared, salt="PLATHO.STEALTH.VIEWTAG.SALT.V1", info="PLATHO.STEALTH.VIEWTAG.V1" || E)[:2]` → **u16**. `info=E` — доменное разделение belt-and-suspenders.
4. **Ключ тела НЕ меняется:** `AES-256-GCM key = HKDF(ikm = x25519_shared || mlkem_shared, salt/info = transcriptHash)`. AAD тела уже включает `header0Hash` (compactBodyAad platho-crypto.mjs:1363-1370), поэтому целостность ВСЕГО заголовка (теперь с `E` + `view_tag`) сохраняется автоматически.

### 1.3. Размещение эфемерала

`E` кладётся в `header0` как `ephemeral_scan_pub` РОВНО в старый байт-диапазон `recipient_key_id` (40..72). Это то же публичное значение, что уже присутствует в префиксе тела PLB1 (байты 36..68); getter читает копию из `header0`, расшифровка тела — копию из тела. Дублирование — одно значение, keygen один.

### 1.4. Одноразовость / unlinkability

Свежий случайный `e` на каждое сообщение (и на каждую ЧАСТЬ мультипарта) ⇒ уникальные `E` и `view_tag`. Посторонний видит только `E` (случайная точка) и `S` (из реестра) — вычислить `scan_shared` без `scan_secret` ИЛИ `e` невозможно (задача Диффи-Хеллмана). Граф «кто-кому» по метке не строится.

### 1.5. Без on-chain nullifier / без 32-байтного stealth_tag

Авторитетное подтверждение «моё» даёт САМА успешная AES-GCM-расшифровка (ключ уже гибридный ML-KEM). Дедуп — по on-chain `entry_id` / `body_hash`. Отдельный широкий `stealth_tag` в цепь НЕ пишем: он не несёт пользы (совпавшее тело всё равно тянется и расшифровывается) и раздувал бы состояние.

### 1.6. Почему эфемерал СЛУЧАЙНЫЙ, а не детерминированный (исправление major-находки)

Все три relinkage/system-ревьюера сошлись: детерминированный `e = HKDF(sender_scan_secret, recipient_scan_pub, client_nonce)` вреден:
- **Nonce-reuse-линкуемость:** вся энтропия `E` держится на уникальности `client_nonce` (16 байт). Повтор nonce (баг RNG, ретрай, пересборка черновика) ⇒ два сообщения одному получателю получают ИДЕНТИЧНЫЙ `E` и `view_tag` — точный публичный маркер «одному получателю», мгновенно склеивающий кластер БЕЗ взлома ДХ.
- **Эрозия forward-secrecy:** вывод `e` из долгоживущего `sender_scan_secret` связывает классическую X25519-половину всех прошлых тел с одним секретом; его компрометация даёт пересчитать `e` для всех прошлых сообщений.
- **Ретроспективный деанон исходящего графа:** выдача `scan_secret` отправителя ⇒ перебор всех публичных `recipient scan_pubkey` × nonce находит совпадение `E` → раскрывает ВСЕХ получателей отправителя постфактум.

**Решение:** `e` — строго CSPRNG на каждую отправку. Sender-recovery отправленных на новом устройстве — через локальный зашифрованный лог (device-local encrypted history уже есть) и/или сохранённый публичный `private_sender_index` (владелец оставил отправителя видимым), НЕ через воспроизводимый on-chain эфемерал.

### 1.7. Подпись отправителя

`privateCapsuleSignaturePayload` (platho-crypto.mjs:2312): убрать `recipientKeyId`, подставить `view_tag` (или `E`). `senderKeyId / profileVersion / avatarHash` брать из РАСШИФРОВАННОГО тела. `ed25519.verify` **перенести на ПОСЛЕ расшифровки** (сейчас до, :2511-2524), т.к. `sender_sign_pubkey` теперь в теле. Порядок у получателя при совпадении `view_tag`: fetch body → ML-KEM decapsulate + AES-GCM → verify senderSignature на расшифрованной identity-секции.

## 2. Точный новый байтовый layout header0 (PH0C) и что переехало в тело

### 2.1. header0 = `PH0C`, 74 байта = 592 бита, 1 ЯЧЕЙКА, 0 REF (было PH0B 140Б/1120бит/2 ячейки/1 ref)

```
offset  поле                      размер
0..4    magic 'PH0C'              4     (bump PH0B→PH0C — явная несовместимость контуров)
4       version u8                1     (PROTOCOL_VERSION++)
5       publish_kind u8           1
6       size_class u8             1
7       crypto_suite u8           1
8..40   sender_key_id u256        32    ← ОСТАЁТСЯ (отправитель видим; питает sender-индекс; offset 8 не меняется → парсер privateHeaderSenderKeyId CapsuleHub.tact:482-486 НЕ трогаем)
40..72  ephemeral_scan_pub u256   32    ← ЗАМЕНА recipient_key_id ровно в его байтах (X25519 E)
72..74  view_tag u16              2     ← новый, FP = 1/65536
=====   ИТОГО 74 байта / 592 бита / 1 ячейка / 0 ref  =====
```
592 < 1023 бит ⇒ помещается в ОДНУ корневую ячейку без ref (раньше 1120 бит требовали 2 ячейки + ref).

### 2.2. Переезжает в ЗАШИФРОВАННОЕ ТЕЛО (identity-секция в начале PCP1 plaintext, под AES-GCM)

```
sender_sign_pubkey   32  (Ed25519)
profile_version       4  (u32)
avatar_hash          32  (u256)
= +68 байт в plaintext тела (расшифровываются только получателем/отправителем)
```
Целостность сохранена: тело привязано к `header0Hash` через AAD, а `header0Hash` теперь коммитит `E` + `view_tag`.

### 2.3. Полностью удаляется (нигде)

`recipient_key_id` (был 40..72) — маршрутный ярлык получателя.

### 2.4. header1 (PH1B, 30 байт, 240 бит) — БЕЗ ИЗМЕНЕНИЙ

⚠️ **Осознанный выбор базы:** т.к. `view_tag` кладётся в `header0` (72..74), а НЕ в `header1`, мы **избегаем** major-находки minimal-index «рост header1 240→256 не проведён по Vault-стороне». `header1` остаётся 240 бит / 1 ячейка / 0 ref на ОБЕИХ сторонах. `client_nonce` (14..30) остаётся для уникальности AES-GCM nonce.

### 2.5. Клиентские правки крипты

`PLATHO_BINARY_HEADER0_BYTES` 140→74 (platho-crypto.mjs:44); переписать `privateCapsuleHeader0Bytes` (:2154-2177) и `privateCapsuleHeader0ObjectFromBytes` (:2197-2225) под 74Б; добавить PCP1 identity-секцию + её парсинг; `encryptCompactPayloadBytes` (:1448-1491) принимает ЕДИНЫЙ случайный эфемерал снаружи и выводит `scan_shared`+`view_tag`; pre-decrypt-проверка «recipientKeyId==header0» (:1526-1531) заменяется на «view_tag' совпал».

## 3. Изменения CapsuleHub

### 3.1. Константы формы header0

`CAPSULEHUB_PRIVATE_HEADER0_BITS` 1120→**592**, `_CELLS` 2→**1**, `_REFS` 1→**0** (CapsuleHub.tact:35,37,38). `requireExactPayloadCell(header0)` (:844) подхватит новые значения (exit 13513/13514). `part.bits()==784` и refs 3/4 (:832) **НЕ трогаем** — это обёртка с хешами h0/h1/bh, от контента `header0` не зависит. Bump magic PH0B→PH0C.

### 3.2. Удаление recipient-стороны ЦЕЛИКОМ (это и есть утечка графа)

- `privateHeaderRecipientKeyId` (:488-493) — удалить; байты 40..72 теперь `ephemeral_scan_pub`, контракт его НЕ индексирует.
- `map private_recipient_index` (:246), `pushPrivateRecipientIndex` (:511-525), `prunePrivateRecipientIndex` (:546-563), `get_private_recipient_index` (:1077-1096) — удалить.
- Вызовы: push в `receive` (:849), un-push в `evictExpiredPrivate` (:699) — удалить.
- `privateHeaderSenderKeyId` (:482-486) **НЕ трогаем** (sender_key_id остаётся @offset 8).

### 3.3. Структура PrivateCapsuleEntry

Удалить `recipient_prev_link:u64` (:147) и его чтение в `get_private_entry` / `PrivateCapsuleEntryView` (:172, :1041). Оставить `sender_prev_link` (sender-индекс сохраняется по решению владельца). Структура остаётся: `{publish_id u256, created_at u64, body_hash u256, sender_prev_link u64, header_0 Cell, header_1 Cell}`. `view_tag`/`ephemeral` НЕ добавляются в структуру — они живут ВНУТРИ `header_0` (эвиктируются вместе с записью, новых неэвиктируемых карт нет).

### 3.4. НОВЫЙ постраничный scan-getter

```tact
get fun get_private_scan_page(fromEntryId: Int, count: Int): PrivateScanPageView
PrivateScanPageView {
  exists, from_entry_id, next_entry_id, returned,
  oldest_live_id, latest_id,
  entries: Cell   // ref-цепочка, 400 бит/запись
}
// на запись: entry_id u64 | created_at u64 | view_tag u16 | ephemeral_scan_pub u256
```
Итерирует `private_entries.get(oid)` по `[from, from+count)`, парсит `header_0` по фикс. оффсетам (`E` @bit 320..576, `view_tag` @576..592), **пропускает эвиктнутые дыры**, тела/`header_1` НЕ читает. `count` держать **64** (консервативно; 128 при подтверждении газа — см. audit_gates). 2 записи / 1023-битная ячейка → цепочка глубины ~32 при count=64.

Плюс `get fun get_private_scan_bounds(): (private_oldest_live_id, private_latest_id)` — **отдельным геттером** (НЕ дописывать в `get_state`, чтобы не сдвинуть фиксированный порядок полей `CapsuleHubStateView` и не сломать горячий декодер провайдера — исправление minor-находки).

### 3.5. FIFO-эвикция сохраняется и упрощается

`evictExpiredPrivate` (:684-708): убрать recipient un-push (:699); `prunePrivateSenderIndex` по `sender_key_id` (offset 8, парсер без изменений), FIFO oldest-first, `private_oldest_live_id`, стоп на первой не-истёкшей записи, годовая retention `CAPSULEHUB_INDEX_RETENTION_SECONDS=31536000` — БЕЗ изменений механики. Состояние по построению **УМЕНЬШАЕТСЯ** (минус карта, минус u64/запись, минус 66Б header0/запись). Rule #2 соблюдён — неограниченного роста НЕ вводим.

### 3.6. Газ/эндаумент — ПЕРЕСЧИТАТЬ ВНИЗ (измерить на ПОЛНОЙ карте, не на пустом sandbox)

- `HUB_PART_GAS_PRIVATE` 170000 → ориентировочно **~120000–135000** (было «1 sender push + 1 recipient push + 2 un-push при эвикции» → стало «1 push + 1 un-push»).
- `CAPSULEHUB_PRIVATE_ENTRY_STORAGE_ENDOWMENT` 3300000 → **~2100000–2400000** (меньше header0 + нет recipient-index-слота + нет recipient_prev_link).

## 4. Изменения Vault

### 4.1. Регистрация scan-ключа БЕЗ отдельного релинка

- В `struct KeyRecord` (:296-309) добавить `scan_pubkey: Int as uint256` (X25519).
- В message `RegisterMessagingKeys 0x52705EDA` (:141-149) добавить `scan_pubkey`; писать `record.scan_pubkey = msg.scan_pubkey` в `key_records.set` (:1709-1722; `owner_wallet: sender()` без изменений). Директория scan-ключей наполняется сама: каждый пишет свой `scan_pubkey` при активации внутренней tx (`sender()=owner`). Публичная связка `scan_pubkey↔wallet` НЕ ломает разрыв графа — метка выводится через ECDH, а не через директорию.

### 4.2. ⚠️ Путь РОТАЦИИ ReplaceMessagingKeys — ОБЯЗАТЕЛЬНО дополнить (исправление major-находки)

`KeyRecord` пишется НЕ только при регистрации, но и при ротации: external `ReplaceMessagingKeys` (:1729) читает новые ключи из ПОДПИСАННОГО `actionPayload` фиксированной ширины (`bits()==800`, :1767; внешний signed-payload `bits()==864`, :1740-1741), аутентифицированного `auth_pubkey`. **Без правки** ротация запишет `scan_pubkey=0` → получатель станет НЕсканируемым (отправитель выведет `X25519(e, 0)`, отклоняемый как all-zero → отправка ПАДАЕТ), либо сломает fixed-width assert.

**Правка:** расширить action-payload `800→1056` бит (+256 `scan_pubkey`) и внешний signed-payload соответственно; добавить `loadUint(256)` для `scan_pubkey`; включить его в подписанный payload/домен; писать в `key_records.set` на пути ротации (:1827-1840); добавить тест-вектор ротации со scan-ключом.

### 4.3. get_key_record — НЕ удалять, НЕ прятать

Отправитель по определению знает кошелёк получателя (он ему пишет) — деанон получателя ОТПРАВИТЕЛЕМ вне модели угроз. Утечка была не в геттере, а в `recipient_key_id` внутри `header0` + публичном recipient-индексе Hub — оба удалены. Добавить `scan_pubkey` в `VaultKeyRecordView` (:417-431) и в оба return `get_key_record` (:2704, :2721/:2723), чтобы отправитель тянул scan-ключ тем же геттером. `computeKeyId` (:1189) НЕ менять — `scan_pubkey` хранится РЯДОМ, не входит в `key_id` (минимальное изменение; подмена невозможна, т.к. `sender()=owner`).

### 4.4. Скраб author_wallet в приватном батче — ОБЯЗАТЕЛЬНО (по указанию владельца)

`emit PublishBatchToHub` (:2321): в приватной ветке (`kind==PUBLISH_KIND_PRIVATE`) `author_wallet` избыточен — Hub для приватных капсул его НЕ читает (CapsuleHub.tact:829-862; читает только в public: :890,:895,:909). Обнуляем его для приватных батчей.

⚠️ **Тонкость типа:** поле имеет тип Tact `Address`, который НЕ сериализует `addr_none`. Сменить тип на `Address?` (private → `null` = 1 Maybe-бит; public → читать `msg.author_wallet!!`). `HUB_BATCH_MSG_ROOT_BITS=924` (:343) держать пином по ХУДШЕМУ (публичному, полный адрес) случаю; НЕ занижать под приватный корень.

⚠️ **Честная граница (не вводить в заблуждение):** это убирает ИЗБЫТОЧНЫЙ сендер-линк на уровне Vault→Hub сообщения, но САМ ПО СЕБЕ отправителя НЕ скрывает. Отправитель остаётся идентифицируем через (1) `sender_key_id` в header0 (остаётся по решению владельца → `get_key_record`→wallet), (2) публичный `private_sender_index` по `sender_key_id`, (3) `owner_wallet` в теле подписанного publish-external. Полная поверхность идентификации отправителя = {sender_key_id, private_sender_index, publish-external owner, author_wallet}. Скраб author_wallet снимает ЧЕТВЁРТЫЙ, самый лишний из них, и удешевляет будущую Phase-2 по сокрытию отправителя — но пока живы (1)+(2) (а они живы намеренно: `private_sender_index` = твой собственный ОТПРАВЛЕННЫЙ-ящик, дешёвая outbox-выборка без скана), отправитель виден. Скраб = гигиена + задел, НЕ сокрытие.

### 4.5. Зеркальные константы Vault — ОБЯЗАТЕЛЬНО (исправление major-находки)

Vault держит СВОЮ копию формы header0 и exact-валидирует её ДО форварда в Hub:
- `CAPSULEHUB_PRIVATE_HEADER0_BITS/CELLS/REFS` (Vault.tact:78,80,81 = 1120/2/1) → **592/1/0**. Иначе `isPrivateCapsuleShapeValid`/`isExactCapsuleCell` (:962-969) отвергнут новый 592-битный header0 как `RJ_PAYLOAD_SHAPE` → приватная отправка падает на СВОЁМ же Vault.
- `STORAGE_RESERVE_PRIVATE=4300000` (Vault.tact:358, «1M keepalive + 3.3M endowment») → пересчитать под новый endowment (~2.1–2.4M), иначе Vault удерживает завышенный резерв и нивелирует экономию ренты.
- Генератор пинов (Session-5) должен пинить ОБЕ стороны из ОДНОГО ABI-источника; gate это проверяет.

### 4.6. Value-модель — НЕ МЕНЯТЬ

`PendingBatchPublish.owner_wallet` (:261,296), `creditBatchSettlementRefund→ton_balance`, ACK/bounce/prune, receipt-ring по nonce — все ключуются на `owner_wallet` ОТПРАВИТЕЛЯ отдельно от wire-`author_wallet`. Stealth их не касается (Rule #3). Vault обрабатывает приватный `header0` НЕПРОЗРАЧНО (shape+hash, не парсит поля) — замена содержимого валидацию не ломает при согласованных константах формы.

### 4.7. Эндаумент регистрации

## 5. Модель сканирования у получателя + стоимость на тонком клиенте

### 5.1. Форвард-скан по глобальному entry_id (вместо обхода индекса по своему key_id)

1. Границы: `get_private_scan_bounds()` → `(low=private_oldest_live_id, high=private_latest_id)`. Нижняя граница ограничена ГОДОВОЙ FIFO-эвикцией, не нулём.
2. Курсор = последний просканированный глобальный `entry_id`, localStorage-ключ привязан к **scan-ключу/кошельку, НЕ к key_id-ярлыку** (снять маршрутный ярлык из ключа кэша; сейчас `privateChainIndexStorageKey` кладёт `keyId`, app.js:11131). Steady-state резюмирует с курсора вверх к `high`.
3. Тянуть страницами `get_private_scan_page(from, count≤64)` → компактный `{entry_id, created_at, view_tag, ephemeral_scan_pub}`, БЕЗ тела/`header_1`. Последовательно, через ЕДИНЫЙ RPC-пул (**НЕ Promise.all** — история freeze при concurrent Vault reads, `withVaultReadLock`).
4. На КАЖДОГО кандидата: один `X25519 ECDH(scan_secret, ephemeral_scan_pub)` + HKDF → `view_tag'`, сравнение с on-chain `view_tag`. `cooperativeYield(setTimeout 0)` после каждого кандидата (не только совпавших) — Rule #4, iPhone SE2.
5. Только на совпадении (~1/65536 ложных + реальные): `get_private_entry` → `resolveBody` → ML-KEM-768 decapsulate + AES-GCM open. Успех = наше; провал = ложное срабатывание, курсор двигается дальше.

Fail-closed контракты `scanPrivateEntryId` сохранить: транзиентная ошибка НЕ двигает курсор; совпавшая-но-не-открытая запись копит cross-session strike; единый single-flight `privateChainSyncPromise`; bounded per-tick limits.

### 5.2. Мультипарт-ассемблинг (исправление major system-находки)

`recipient_prev_link` и recipient-индекс удалены, каждая часть несёт СВОЙ `E`/`view_tag`, on-chain группировки нет. Straddle-guard (v649/v650) и head-repair перестраиваются вокруг **content-derived** полей РАСШИФРОВАННОГО PCP1: `stream_id + part_index + part_total`. Финализация потока откладывается до накопления всех `part_total` частей; отдельный bounded straddle-extension по аналогии с `PRIVATE_CHAIN_STRADDLE_EXTENSION_SCAN_LIMIT`, управляемый по `part_total`, а не по индексной цепочке. Покрыть тестами частичный/переупорядоченный приём на границах страниц/эвикции.

### 5.3. Честная стоимость на тонком клиенте (исправление major system-находки «O(глобального потока)»)

**Прямо признаём:** удаляя recipient-индекс, получатель теряет O(свой инбокс)-обход и переходит на O(**глобальный приватный поток**)-скан. Это цена unlinkability и врождённая «стена сканирования» stealth-адресов.

- **Steady-state = глобальный ПРИРОСТ с курсора**, НЕ объём пользователя: клиент, открывший приложение раз в сутки, ре-сканирует суточный глобальный трафик сети. При цели «десятки тысяч пользователей» (design-for-launch-scale) это существенно.
- **ДОМИНАНТА на keyless-контуре — не ECDH, а последовательный RPC-обход страниц.** `ECDH ~0.3мс` × M дёшев; узкое место — `M/64` вызовов `get_private_scan_page` строго single-flight на keyless ~1.1с/запрос (censorship-resilience 1rps). Пример: 500k записей/год → ~7800 постраничных вызовов ≈ >2 ч keyless (≈ минуты со своим keyed 10rps ключом) только на выкачивание ДО расшифровок. Rule #4 явно РАЗРЕШАЕТ дорогую первичную синхронизацию.
- **Steady-state дёшев** по дельте (курсор + годовая эвикция снизу), но линеен по глобальному трафику между открытиями приложения.

**Смягчения (закладываем):**
1. **ECDH-префильтр в Web Worker** — скан не занимает main-thread даже с cooperativeYield.
2. **Прогресс-индикатор** + скан high→low (свежие записи первыми) при первом входе.
3. **Недоверенный RPC-фасад/агрегатор** (вне контракта), отдающий сжатый поток `{entry_id, view_tag, E}` большими блоками — режет round-trip'ы; клиент всё равно перепроверяет `view_tag` локально (доверие не требуется).
4. Новые геттеры занести в `TONCENTER_RUN_GET_METHOD_CACHE_TTLS_MS`/`PRIORITIES` (приоритет 'messages') и в `REQUIRED_TON_RPC_CRITICAL_METHODS` — иначе фон-приоритет + дефолтный TTL замедлят скан.

Sender-recovery отправителя (outbox) — дёшево через сохранённый `private_sender_index` по своему `sender_key_id` (не скан). Асимметрия принята: отправитель = индекс (видим), получатель = stealth-скан.

## 7. PQ-решение для stealth-МЕТКИ (явное, с trade-off)

**Рекомендация: метка — КЛАССИЧЕСКИЙ X25519 view_tag (u16); тело — HYBRID ML-KEM-768 (не меняем). PQ-метку/гибридный on-chain stealth_tag НЕ вводить.**

> ✅ **РЕШЕНО ВЛАДЕЛЬЦЕМ (2026-07-13):** метка остаётся классической. PQ-защита ГРАФА отклонена — она кратно (~30x по скан-загрузке, полная ML-KEM-декап на кандидата вместо дешёвого 2-байтового пред-фильтра) удорожает и без того узкий скан ради ЧИСТО РЕТРОСПЕКТИВНОГО риска (квантового противника ещё нет; содержимое защищено ML-KEM навсегда). Квантовый ретро-деанон графа — ПРИНЯТЫЙ остаток.

**Обоснование (главный честный вывод):**

1. **Тело уже пост-квантово конфиденциально** (ML-KEM-768). Содержимое кванту недоступно навсегда. Под остаточным риском ТОЛЬКО граф получателя (harvest-now/decrypt-later: записать цепь → в будущем сломать X25519 → восстановить кто-кому).

2. **Практического пост-квантового NIKE не существует.** X25519 stealth работает как NIKE (обе стороны выводят общий секрет из статических+эфемерных публичных ключей без ct). ML-KEM — это KEM, а не NIKE: инкапсуляция рождает свежий ct ~1088Б на сообщение, а получатель ОБЯЗАН декапсулировать (дорого), чтобы получить секрет. CSIDH-класс сломан/непрактичен.

3. **Следствие:** любой PQ view_tag ⇒ ML-KEM decapsulate на КАЖДОМ кандидате глобального потока (нельзя понять «мой ли ct», не декапсулировав) → смерть тонкого клиента на SE2 (нарушение Rule #4). А дешёвый классический pre-filter ОБЯЗАТЕЛЕН для скана.

4. **«Гибридная метка» `HKDF(x25519_scan_shared || mlkem_shared)` косметична для графа:** пока рядом лежит ДЕШЁВЫЙ классический `view_tag` (а он обязателен), именно он — слабое звено; квантовый противник деанонимизирует граф через него, ИГНОРИРУЯ гибридный tag. То есть PQ-свойство stealth_tag не улучшает квантовую стойкость графа, а +32 байта/запись стоит.

5. **Рычаг квантовой стойкости графа — ШИРИНА классического view_tag, а не гибрид.** Квант из публичного `E` получает ТОЧНЫЙ `scan_shared` (полноширинный секрет); «зашумлённость» возникает ИСКЛЮЧИТЕЛЬНО из того, что on-chain закоммичено лишь `w` бит. Узкий u8 → бакет `users/2^8` (шумнее); u16 → `users/2^16` (чище). **⚠️ Это НЕ криптостойкость:** при пересечении по нескольким сообщениям одной долгоживущей пары бакет схлопывается до уникального получателя за ~2–3 сообщения, а шум по view_tag НЕ независим от тайминг-улик (§12).

**Выбор ширины (u16 по умолчанию):** связывающее ограничение — RPC-масштабирование (Rule #4) и число ложных ML-KEM-decapsulate. u8 (1/256) даёт в 256 раз больше пустых body-fetch на ДЕФИЦИТНЫЙ общий RPC (~N·M·FP) и в 256 раз больше decapsulate. Поэтому **u16** (FP 1/65536). u8 остаётся настраиваемым рычагом для privacy-max-деплоя (крупнее квантовые бакеты ценой RPC) — решение владельца.

**Зарезервировать** значения `crypto_suite` + путь bump version под будущий PQ-scan контур, если появится практический PQ-NIKE или владелец примет стоимость PQ-скана.

## 8. ⚠️ Критический аудит-гейт: анонимность гибридного KEM (исправление major relinkage-находки)

Тело hybrid-v1 оставлено читаемым из истории TON: `x25519_ephemeral_public(32Б)` и `ml_kem_768_ciphertext(1088Б)` лежат в cleartext ДО AES-GCM-секции. Одновременно `enc_pubkey` и полный `pq_kem_pubkey` КАЖДОГО получателя публичны в `Vault.KeyRecord`.

**Риск:** весь релинкедж-барьер получателя держится на том, что KEM-шифртекст НЕ выдаёт, к какому `pq_kem_pubkey` он инкапсулирован (свойство **ANO-CCA / key-privacy** + **strong robustness**). IND-CCA (уже купленный) этого НЕ влечёт. Если гибрид не key-anonymous — посторонний **классически (БЕЗ кванта, пассивно, немедленно)** тестирует шифртекст против публичного каталога ключей и восстанавливает получателя напрямую — граф не рвётся вовсе.

X25519-половина НЕ тестируема (нужен `e` или `enc_secret`), но ML-KEM-ct — открытый вопрос анонимности.

**Обязательный гейт:** доказать ANO-CCA (key-privacy) и strong robustness для гибрида X25519+ML-KEM-768 при пассивно видимом on-chain ct и публичном каталоге. Опереться на актуальный результат об анонимности ML-KEM/Kyber-768 (Maram–Xagawa) с implicit rejection и зафиксировать как ПИН-ДОПУЩЕНИЕ в `CRYPTO_PROTOCOL.md` рядом со stealth-разделом. Если не держится — анонимизирующая обёртка KEM-ct или иначе весь stealth-заголовок бесполезен.

## 13. Остаточные утечки (честно)

1. ОТПРАВИТЕЛЬ полностью видим (осознанно, Phase 1): sender_key_id остаётся cleartext в header0 @8..40 + private_sender_index на цепи; get_key_record(sender_key_id)→owner_wallet разворачивает в кошелёк. Публично: «этот кошелёк отправил приватную капсулу (кому-то, что-то зашифрованное) в момент T». Скрыто только КОМУ.
2. private_sender_index (сохранён) публично перечисляет ВЕСЬ исходящий приватный поток любого отправителя (счётчик отправок + тайминги) по предсказуемому sender_key_id одним геттером — усилитель тайминг-атаки; полный исходящий граф активности отправителя открыт.
3. ТАЙМИНГ/reply-корреляция диалога: в переписке A↔B оба — видимые отправители; получатель сообщения N почти всегда = отправитель сообщения N+1. Наблюдатель по интерливингу запрос/ответ и характерным латентностям склеивает пару {A,B} за много раундов БЕЗ криптографии и без кванта. Stealth ломает индексно-ярлычный граф (скрипт сына), НЕ тайминговый граф собеседников.
4. ТРАНСПОРТНАЯ утечка инбокса RPC-оператору (toncenter — единственный транспорт в проде): body-fetch выполняется практически только на СВОИХ сообщениях (FP 1/65536 ничтожен), а заголовки этих записей несут cleartext sender_key_id → кошелёк отправителя. Оператор тривиально строит входящий граф получателя «кто написал этому IP». Смягчение (закладывается опционально): decoy-фетчи чужих entry_id / ротация RPC-эндпойнтов / фоновый сплошной range-фетч (дороже по RPC). Регресса против старой indexed-модели нет, но новая модель это НЕ закрывает.
5. КВАНТОВЫЙ ретроспективный деанон ГРАФА: противник, записавший цепь И сломавший X25519, пересчитывает классический view_tag и вместе с видимым отправителем восстанавливает граф получателя (при ≥~2-3 сообщениях на долгоживущую пару u16-метка схлопывает бакет до уникального получателя). СОДЕРЖИМОЕ остаётся PQ-стойким навсегда (ML-KEM тела). Принятый trade-off (§7); полностью закрывается только PQ-скан контуром при появлении практического PQ-NIKE.
6. scan_pubkey↔wallet публичны в Vault KeyRecord (регистрация — внутренняя tx от кошелька): МНОЖЕСТВО зарегистрированных получателей перечислимо (кто СПОСОБЕН принимать), но НЕ какие сообщения к ним идут. Анонимити-сет получателя = все держатели scan-ключей контура; при малой активной базе на старте практическая анонимность ниже теоретической.
7. Метаданные трафика: created_at, size_class (@6 в открытом header0, грубая длина сообщения), глобальный порядок entry_id, part_count, ритм отправок конкретного видимого отправителя, длина sender-индекса (точный счётчик отправленных) — публичны. Поверхность трафик-анализа поверх формально скрытого получателя.
8. Активный противник, ЗНАЮЩИЙ scan_secret получателя (делегированный view-ключ скомпрометирован), видит ВЕСЬ входящий граф получателя — но НЕ содержимое (dual-key). Цена делегируемости.
9. Анонимность гибридного KEM (ANO-CCA) — ПИН-ДОПУЩЕНИЕ, а не доказанный факт до аудита (§8): если гибрид X25519+ML-KEM-768 окажется не key-anonymous/не robust, пассивный КЛАССИЧЕСКИЙ противник тестирует ct против публичного каталога и деанонимизирует получателя напрямую — граф не рвётся. Обязательный гейт перед immutable-деплоем.

## 15. Результат гейта §8 (анонимность гибрида) — вердикт: FAIL-как-есть, но анонимность ДОСТИЖИМА

Мультиагентный гейт-проход (обзор литературы + анализ кода) заключил: **криптоядро выбрано верно, анонимность достижима**, но гейт НЕ пройден и требует внешнего аудита перед необратимым деплоем.

**Ядро подтверждено литературой (анонимность — QROM-ДОПУЩЕНИЕ, НЕ следствие IND-CCA):**
- X25519-половина анонимна — BBDP «Key-Privacy in PKE», Asiacrypt 2001 (при свежем случайном эфемерале + отбраковке all-zero, RFC 9180 §7.1.4).
- ML-KEM-768 анонимна — Maram–Xagawa «Post-Quantum Anonymity of Kyber», PKC 2023 (eprint 2022/1696) — в модели QROM.
- Гибрид анонимен ТОЛЬКО если анонимны ОБА компонента — «Anonymity of X-Wing» (eprint 2026/396); combiner HKDF прячет ключ, но НЕ открытые куски (E и ct лежат на цепи и тестируются независимо).

**Две подтверждённые по коду пассивные утечки:**
1. **БЛОКЕР — `recipient_key_id` открыт в header0 (PH0B).** Это ровно то, что снимает stealth PH0C. Подтверждает необходимость редизайна; в текущем live-коде граф открыт настежь (stealth в коде ещё не реализован — grep `PH0C`/`view_tag`/`scan_pubkey` по `web/` пуст).
2. **BREAKS-GATE — НОВОЕ, дизайн (§1-14) ПРОПУСТИЛ:** `ReceiveIntent` (`Vault.tact:284-286`) хранит `sender_wallet` + `recipient_wallet` ОТКРЫТЫМ `Address` в состоянии Vault, отдаёт `get_receive_intent` (`:2759`). → любой **платёжный чек** (PCP1 kind 3) раскрывает ребро sender→recipient напрямую, **В ОБХОД stealth-заголовка**. Поле `commitment` рядом есть, но plaintext-адрес получателя хранится ВСЁ РАВНО. Переработать `ReceiveIntent` на **commitment-only** (hashlock/stealth-адрес получателя, БЕЗ plaintext `Address` в состоянии) — правка КОНТРАКТА в immutable genesis.

**Уточнения дизайна (обязательные):**
- `view_tag` ОБЯЗАН выводиться из **per-capsule эфемерали** (`truncate16(H(domain || X25519(eph_scan_sk, recipient_scan_pub)))`), а НЕ из статического scan-ключа — иначе постоянный 16-битный псевдо-ID получателя + intersection-атака. (Наш §1 так и задумал — подтверждено.)
- Привязать коммитмент получателя `H(enc_pubkey || pq_kem_pubkey)` в HKDF info/AAD для strong robustness — СТРОГО не на цепь (анонимности не вредит).
- Приватные капсулы **hybrid-only** (уже enforced, `assertAllowedPrivateCapsulePair`) нейтрализуют suite-partition различитель — закрепить как инвариант.

**Требование гейта:** НЕ запускать immutable genesis в текущем состоянии. Порядок: (1) реализовать ТРИ правки — PH0C + scan/trial-decrypt + ReceiveIntent commitment-only; (2) привязка коммитмента получателя в KDF/AAD + пин QROM-допущений в `CRYPTO_PROTOCOL.md` с цитатами; (3) **внешний академический крипто-аудит** анонимности гибрида X25519⊕ML-KEM-768 + остаточных on-chain утечек ПЕРЕД необратимым деплоем (несущее необратимое допущение частично стоит на QROM-идеализации).

## 16. Платёжный путь — ReceiveIntent commitment-only (закрытие второй утечки графа)

_Рекомендованный вариант: recipient-bound-hashlock_

# Рекомендованный дизайн: recipient-bound-hashlock (commitment-only ReceiveIntent)

## Выбор и обоснование
Из трёх вариантов выбран **recipient-bound-hashlock**. bearer-hashlock — фактически тот же самый механизм (co-commit кошелька внутрь хэша), а его самостоятельная ценность (опустить commitment из геттера) красной командой признана мнимой: сырое состояние Vault парсится напрямую, форма геттера приватности не даёт. stealth-payment получил **funds_safety=false / blocker** (теряет basechain-гейт ATH и заводит настоящий stealth-address ценой, которую владелец уже отверг для zk-пула). recipient-bound-hashlock даёт лучший баланс приватность/простота/сохранность (funds-safety 8.5), и все его major-находки закрываются малыми, консервативными правками. Полезное из bearer-hashlock (единый хэш-гейт, снятие create-проверки получателя) вплавлено; ошибочная рекомендация «случайный intent_id разорвёт связь create↔claim» **отвергнута** (см. остаток).

## Commitment-схема
`commitment = H(RCCM ‖ secret32 ‖ recipient_wallet)`, где
- `RCCM = 0x5243434d` (уже есть, `RECEIVE_INTENT_COMMITMENT_DOMAIN`);
- `secret32` — 256-бит из CSPRNG клиента-отправителя, уникальный per-intent, живёт ТОЛЬКО в шифрованном теле капсулы-чека;
- `recipient_wallet` сериализуется РОВНО как `beginCell().storeUint(RCCM,32).storeUint(secret32,256).storeAddress(recipient).endCell().hash()` — идентично тому `storeAddress`, что контракт применяет к `msg.owner_wallet` на клейме.

Свойства: hiding — без `secret32` (256 бит) кандидат-получатель неотличим, перебор кошельков бесполезен; binding — открыть на другой кошелёк = найти преимидж-коллизию (инфизибл). `commitment` статистически неотличим от случайного числа. Поле `commitment` СЕЙЧАС хранит `secret32` в открытую (helper `computeReceiveIntentCommitment` возвращает `secret32`) — теперь становится СКРЫВАЮЩИМ и заменяет собой И plaintext-адрес получателя, И старый открытый секрет.

## Новый struct ReceiveIntent
```
sender_wallet: Address        // PLAINTEXT — допустимо (create sender-аутентифицирован, отмена по нему)
asset: Int as uint8
amount: Int as uint128
commitment: Int as uint256    // ТЕПЕРЬ hiding = H(RCCM‖secret32‖recipient)
client_nonce: Int as uint64
settlement_reserve_ton: Int as uint128
created_at: Int as uint64
claimed: Bool
```
**УДАЛЕНО: `recipient_wallet: Address`** — больше не хранится нигде в состоянии. Struct стал МЕНЬШЕ на один Address (~267 бит), storage-endowment остаётся консервативным (не снижать). `VaultReceiveIntentView` синхронно теряет поле `recipient_wallet`; `commitment` в геттере можно оставить (он hiding, ничего не выдаёт) — но НЕ полагаться на форму геттера как на приватностный контроль. `claimed:Bool` после `del(intent)` фактически мёртв — можно убрать ради минимизации (опционально, консервативно допустимо оставить). `created_at` — корреллятор (см. остаток), но сохраняем для UX/дебага.

## Деривация intent_id (без recipient_wallet)
```
intent_id = H(RCID ‖ sender_wallet ‖ asset(8) ‖ amount(128) ‖ client_nonce(64) ‖ commitment(256)) % 2^128
```
`RCID = 0x52434944`. Из старой формулы УБРАН `storeAddress(recipientWallet)`, ДОБАВЛЕН `storeUint(commitment,256)`. Так id больше НЕ является публично-тестируемой функцией адреса/ключей получателя (ограничение 4): sender plaintext и так виден, а commitment неугадываем без secret32. Уникальность ключа гарантирует строго растущий `client_nonce == publish_nonce` отправителя; коллизия на 128 бит birthday-порядка (~2^64, как сейчас) — приемлемо. Контракт на create ПЕРЕсчитывает id из `msg.owner_wallet`(=sender)+payload — клиентскому id никогда не доверяет. Клиент считает id по идентичной формуле и кладёт в шифрованное тело капсулы.

## Поток CREATE (0x7E1F5035)
Пре-аксепт БЕЗ изменений (user exists, auth!=0, sig, домены, manifest/vault-hash, nonce, `ton_balance>=STATE_GROWTH_EXEC_RESERVE`, acceptMessage, nonce++, receipt, дебет 2M, commit). Пост-аксепт из ref-actionPayload:
- **Формат payload меняется: `{asset(8) ‖ amount(128) ‖ commitment(256)}` — БЕЗ Address получателя.** Это самая вероятная регрессия: если оставить `recipientWallet` в подписанном create-теле, получатель останется полностью открыт в CREATE-external и вся правка обнулится. `loadAddress()` (строка 1899) удаляется.
- Гейты `asset∈{TON,ATH}`, `amount>0`, `commitment!=0` (строка 1913) — сохраняются.
- **ATH-ветка: снять `isBasechainAddress(recipientWallet)` (строка 1945) — получателя тут больше нет.** `isBasechainAddress(msg.owner_wallet)` (sender, строка 1942) — СОХРАНИТЬ.
- Резервы (`STORAGE_ENDOWMENT 5M + STATE_GROWTH 2M + SETTLEMENT 2M`), дебеты (`ton_balance -= amount+remaining` для TON; `ath_balance -= amount`, `ton_balance -= remaining` для ATH), `exists(intentId)`-гард ПЕРЕД дебетом, запись intent, `count++` — без изменений (в записи intent убрано поле `recipient_wallet`).

## Поток CLAIM (0x, action=CLAIM)
Пре-аксепт БЕЗ изменений. `actionPayload = {intentId(256), secret32(256)}` — по проводу тот же. Пост-аксепт (после `acceptMessage`, ДО любой мутации; в claim нет `commit()`, поэтому любой throw откатывает всё чисто):
1. lookup `intent` по `intentId`, `throwUnless(16276, intentOpt != null)` — сохраняется как отдельный код (null / уже сделан del).
2. **ЗАМЕНА двух проверок (строки 2012 `owner==recipient_wallet` и 2013 `secret32==commitment`) на ОДНУ хэш-гейт:**
   `computed = beginCell().storeUint(RCCM,32).storeUint(secret32,256).storeAddress(msg.owner_wallet).endCell().hash();`
   `throwUnless(<НОВЫЙ_КОД, напр.16278>, computed == intent.commitment);`
   Один этот чек одновременно доказывает знание secret И привязывает средства к предъявленному кошельку.
3. **Для ATH — вернуть утерянный basechain-гейт получателя (закрытие blocker'а):** в ветке `intent.asset==ASSET_ATH` до кредита `throwUnless(<новый код, напр.16281>, self.isBasechainAddress(msg.owner_wallet));` — зеркало снятой create-проверки, иначе ATH-кредит уйдёт на masterchain-кошелёк, откуда `WithdrawAthFromVaultBalance` (гейт 16075, basechain) не выведет → заморозка навсегда.
4. Далее как раньше: `publish_nonce++`, receipt `ACT_CLAIM_INTENT`, кредит `ton_balance/ath_balance += amount` для `msg.owner_wallet`, `del(intentId)`, `count--`. Все guard'ы — ДО nonce++/кредита/del.

Газ: +1 построение ячейки (secret256+address) и хэш, всё пост-аксепт — тривиально, 10k pre-accept credit не задет.

## Поток CANCEL
БЕЗ изменений по сути. `sender_wallet` остаётся plaintext, гейт `throwUnless(16286, msg.owner_wallet == intent.sender_wallet)` сохраняется, возврат `amount` в баланс отправителя, `del`, `count--`. Резервы (storage/settlement/state-growth) невозвратны — как сейчас. secret32/commitment в отмене не участвуют: отправитель аутентифицирован подписью и возвращает свои же средства.

## Сеттл средств
Кредит идёт во ВНУТРЕННИЙ баланс `msg.owner_wallet`: `ASSET_TON → ton_balance += amount`, `ASSET_ATH → ath_balance += amount`. Адрес получателя заранее НЕ хранится и для сеттла не нужен — место зачисления определяется в момент клейма самим предъявленным кошельком, а его легитимность доказывает хэш-гейт, а не хранимое поле. Отмена — симметрично в баланс sender. Дебет на create компенсируется РОВНО одним кредитом (claim ЛИБО cancel); `del` + `publish_nonce++` в той же транзакции исключают двойное освобождение. Строгое сохранение баланса, value-модель (внутренние балансы, резервы, receipt-ring по nonce) не тронута.

## Защита от claim-race / front-run / кражи
Кредит ВСЕГДА идёт на `users.get(msg.owner_wallet)`, а хэш-гейт `H(RCCM‖secret32‖owner_wallet)==commitment` проходит ТОЛЬКО когда owner_wallet == вшитый в commitment получатель. Наблюдатель (в т.ч. враждебный/сговорчивый RPC), увидевший `secret32` в открытом claim-external, реплеит его из своего кошелька `W'` → `H(RCCM‖secret32‖W')≠commitment` → revert (preimage-resistance не даёт подобрать под свой адрес). Подделать чужой `owner_wallet` он не может: `checkSignature` берёт `auth_pubkey` из `users.get(owner_wallet)`, а регистрация UserState жёстко keyed by `sender()` реального внутреннего сообщения — чужой не заведёт user под адресом жертвы. Same-auth two-wallet-кейс безопасен: два кошелька A≠B под одним auth-ключом дают `H(...‖A)≠H(...‖B)`, commitment фиксирует именно намеченный кошелёк (эквивалент старой явной recipient-проверки, подтверждено). Двойной клейм / claim-после-cancel закрыты `del`+null-гейт (16276). Реплей идентичного BoC получателя кредитует получателя один раз, второй прилёт падает на `publish_nonce` пре-аксепт.

## Что видно at-rest vs at-claim (честно)
**At-rest (до клейма) — ЧИСТО:** в состоянии и геттере только `sender_wallet` (полу-ребро, по решению владельца), `asset`, `amount`, `commitment` (hiding — не выдаёт ни адрес, ни секрет), `nonce`, `reserve`, `created_at`. Ребро sender→recipient в состоянии Vault РАЗОРВАНО: перечисление всех receive_intents (в т.ч. неотозванных и исторических) не выдаёт получателей. Адрес получателя не касается цепочки даже транзитно на создании (в create-payload только commitment).

**At-claim — ребро ВОССТАНАВЛИВАЕТСЯ (жёсткий предел hashlock-семейства, признаём честно):** claim-external подписан получателем и несёт `msg.owner_wallet`(=получатель) в открытую + `intentId`. Наблюдатель, проиндексировавший CREATE-external, ПЕРЕсчитывает `intentId` (sender/asset/amount/nonce/commitment все видны в create) и матчит с claim по равенству ключа карты (add(key) в create-tx отправителя ↔ del(key) в claim-tx получателя) → полная склейка sender→recipient В МОМЕНТ ЗАБОРА средств. Это неустранимо чистыми хэш-external: любой ключ, под которым create кладёт запись, обязан присутствовать и в claim. Разрыв требует zk/nullifier-доказательства членства без раскрытия ключа — вне досягаемости и вне текущей правки (владелец уже отклонил zk-класс). **Вывод: stealth держится ДО момента, когда получатель забирает средства.**

### 16.3. Остаточные утечки (честно)

1. At-claim линковка sender→recipient — ЖЁСТКИЙ предел hashlock: наблюдатель пересчитывает intent_id из видимых входов CREATE и матчит по равенству ключа карты (add в create-tx ↔ del в claim-tx) → полное ребро в момент забора средств. Неустранимо без zk/nullifier. Stealth держится только до первого клейма.
2. amount+asset plaintext (нужны для сеттла) — НЕЗАВИСИМЫЙ канал линковки помимо id: нестандартный номинал почти однозначно матчит create↔claim без всякого id; узкое окно create→stealth-скан→claim добавляет тайминг. Смягчение только паллиативами (фикс-деноминации/бакетирование/дробление/джиттер клейма), все клиентские, вне контракта.
3. Получатель полностью деанонимизируется в claim-external (owner_wallet + Vault-идентичность + auth-подпись) — неизбежно, он обязан аутентифицироваться для кредита. В связке с sender plaintext клейм публикует ГОТОВОЕ ребро X→Y.
4. sender_wallet plaintext (решение владельца) — отправительская сторона ребра видна всегда; приватность асимметрична (отправитель виден, получатель — до клейма).
5. Сырое состояние Vault перечислимо напрямую (не только геттер): {sender, amount, asset, created_at, commitment} по всем открытым чекам. Удаление recipient_wallet из геттера НЕ мешает парсу — реальная защита = отсутствие recipient в state + энтропия secret32, а НЕ форма геттера.
6. created_at (если оставлен) — точная метка времени как корреллятор к claim той же суммы; для сохранности не нужен, можно огрубить/убрать.
7. После клейма secret32 навсегда на цепочке → commitment ЭТОГО intent становится оффлайн-проверяемым по кандидату-кошельку (но owner уже раскрыт клеймом — доп. утечки нет; другие intent'ы не страдают, secret уникален per-intent).
8. receipt-ring на клейме пишет ACT_CLAIM_INTENT+таймстамп на состоянии ПОЛУЧАТЕЛЯ (durable claim-log) — амплификация уже-раскрытого owner_wallet, не новый канал; оценить в аудите.
9. Availability: чек привязан к одному кошельку; смена/утеря кошелька получателем до клейма запирает ИМЕННО этот чек — не потеря (возврат через cancel sender'ом), но окно недоступности. Задокументировать UX.
10. ОТВЕРГНУТО как ложное улучшение: 'случайный intent_id (nullifier) разорвёт create↔claim' — случайный ключ всё равно едет ОТКРЫТО и в create-, и в claim-external и матчится тривиальным равенством; линковка не слабее. Не внедрять с ложной уверенностью.

### 16.4. Интеграция в clean-16

clean-16 stealth скрывает ПОЛУЧАТЕЛЯ капсулы (дискавери через скан вместо адреса-в-заголовке). Эта правка закрывает ВТОРУЮ утечку графа в обход stealth-заголовка — платёжный путь: recipient_wallet больше не лежит plaintext в состоянии Vault (intent_id и все поля перестают быть функцией адреса/ключей получателя). At-rest обе поверхности (капсула + чек) симметрично скрывают получателя, и приватность чека УСЛОВНА на корректности stealth-скана самой капсулы (secret32 доставляется только через расшифрованное тело). Тело капсулы PCP1 kind 3 wire-совместимо (меняется лишь клиентская формула commitment/intent_id), поэтому normalizeFeedBlocks / whitelist / декодер НЕ затрагиваются — риск 'поле исчезло на reload' отсутствует. Быстрый сенд сохранён (create без пула/ожидания). Остаточная at-claim деанонимизация — общий предел и капсульного, и платёжного stealth в не-zk модели: получатель доксит себя актом получения; это принимается в модель угроз clean-16 как явное asdesigned-ограничение (полный разрыв — только отдельный zk-трек, ранее отклонённый владельцем). Обязательные гейты перед genesis: (1) общий тест-вектор storeAddress-преимиджа commitment/id (клиент↔контракт), (2) release-gate на отсутствие Address в create-payload и recipient_wallet в state/getter, (3) тест ATH-claim с masterchain-owner → revert (16281), (4) тест claim с owner≠намеченного при общем auth-ключе → revert (16278). Аудит — после правки, как для immutable genesis.

## 17. zk-анонимизация платёжного обнала (Level 1.5: nullifier-claim + деноминации)

> ⛔ **ОТЛОЖЕНО — владелец выбрал Goal A (2026-07-13).** Этот раздел НЕ входит в scope clean-16. Причина: приватность платёжного графа на публичной цепи возможна только «в толпе одинаковых платежей» (совпадение суммы+тайминга+наличие толпы); редкий/крупный/нестандартный платёж не прячется НИКАКОЙ техникой (бакет-1 → тривиальный матч create↔claim по сумме+таймингу без атаки на крипту), а zk прикрыл бы лишь повседневную мелочь при объёме — наименее чувствительное — ценой MPC-церемонии, on-chain Poseidon (freeze-риск), деноминаций и 10-30с пруфа. Платёжная приватность genesis = **commitment-only (§16)**: массовый скрейп мёртв, приём пассивен, ребро всплывает только при обнале конкретного чека. Раздел сохранён как готовый дизайн будущего v2-пула (если появится поток мелких платежей) + off-ledger как путь для по-настоящему чувствительных сумм. НИЖЕ — исходный дизайн-материал.

_Рекомендованный уровень: nullifier-claim + деноминации (Уровень 1.5), укреплённый: per-epoch Poseidon-Merkle-деревья, ЕДИНЫЙ per-cheque nullifier для claim и refund, claim/refund приходят INTERNAL-сообщением с оплатой газа получателем, verifier POST-accept, turnstile-инвариант net_locked ≥ 0 per-(asset,denom), ОБЯЗАТЕЛЬНЫЙ auto-refund sweep на ретайре эпохи, root тэгирован эпохой, скользящее окно W эпох как единый анонимный набор. Полный shielded (Level 2) — ОТКЛОНЁН для immutable genesis, помечен как будущий v2-пул._

### 17.0. Рекомендация по уровню

Рекомендую **nullifier-claim + деноминации (Уровень 1.5)**, НЕ полный shielded (Level 2).

**Почему этого достаточно под цель владельца.** Цель — «не светить платёжный граф», то есть разорвать ребро create(sender)→claim(recipient). Обе privacy-ревью дали `edge_broken=false` (ребро НЕ рвётся) ТОЛЬКО из-за пустого анонимного набора на старте — это проблема ЛИКВИДНОСТИ, а не уровня схемы. Криптографически L1.5 рвёт ребро ровно как Tornado: membership-пруф прячет лист, nullifier односторонне развязан от commitment. Полный shielded добавляет скрытие СУММЫ и ФАКТА получения — но владелец явно принял, что sender+amount видны на create, а получатель виден на claim. Значит две из трёх «доплат» Level 2 (скрытие суммы, скрытие получателя) не входят в заявленную цель.

**Почему НЕ полный shielded на immutable genesis.** Level 2 несёт непропорциональный риск для необратимого деплоя: (1) join-split ~60–120k constraints против ~30k — 2–4× вес пруфа на iPhone SE2; (2) требует клиентского приватного note-леджера + локальной реконструкции Merkle-дерева из событий — память, код и КРАТНО больший аудит-surface на неизменяемой цепи; (3) вводит неподписанный анонимный путь доставки с нерешённым (в ревью — `blocker`) вектором фандинга газа relayer'а, который сам ре-линкует ребро; (4) больше линчпин-багов схемы (isDummy↔value, cross-asset output-binding, dummy-nullifier коллизии), каждый на genesis неисправим. При этом на старте набор всё равно 1–3, поэтому Level 2 не покупает практическую приватность, которой нет у L1.5 — он покупает скрытие суммы ценой рисков, несовместимых со «священной сохранностью» на immutable-цепи.

**Условие пересмотра.** Единственная причина взять Level 2 — если владелец сочтёт скрытие СУММЫ обязательным (деноминационный налог неприемлем). Тогда Level 2 включается как отдельный v2-пул ПОСЛЕ того, как L1.5 наберёт ликвидность и пройдёт боевой аудит — не в genesis. На genesis L1.5 закладывает всё scaffolding (verifier, Merkle, nullifier, turnstile), поверх которого v2 достраивается расширением, а не переписыванием.

**Оговорка про сторону получателя.** L1.5 кредитует НАЗВАННЫЙ owner_wallet — осознанный дизайн (получатель на claim принят видимым). Но повторное использование одного owner_wallet кластеризует все его клеймы. Рекомендую кредитовать на СВЕЖУЮ приёмную внутреннюю идентичность на клейм (эфемерный auth_pubkey); минимум — честно задокументировать address-reuse как остаток.

# Рекомендованный дизайн: nullifier-claim + деноминации (Уровень 1.5, укреплённый)

Анонимный обнал чек-эскроу: получатель на claim доказывает в нуле «знаю секрет какого-то неистраченного чека деноминации D актива A в живой эпохе», гасит nullifier и кредитует свой баланс на D — НЕ раскрывая, ЧЕЙ чек взят. Публичное ребро create(sender)→claim(recipient) рвётся для третьих лиц; сумма прячется до гранулярности деноминации; рост состояния ограничен эпохами; форж капируется turnstile-суб-пулом + церемонией.

## 1. Что доказывает схема (circuit)

Схема Tornado-класса (~30k constraints, Poseidon rate-2 над BLS12-381) доказывает атомарно:

- **Членство.** commitment = Poseidon(sharedSecret ‖ D ‖ asset ‖ epoch ‖ payoutBinding) — деноминация, актив и эпоха ВШИТЫ в лист; commitment — лист инкрементального Poseidon-Merkle-дерева глубины 20 (~1M листьев) КОНКРЕТНОЙ эпохи с публичным корнем root.
- **Корректный nullifier.** nullifierHash = Poseidon(sharedSecret ‖ leafIndex), где sharedSecret — ОБЩИЙ per-cheque секрет (не mode-специфичный). Ключевая правка: и claim (получатель), и refund (отправитель) дают ОДИН И ТОТ ЖЕ nullifierHash → истинное взаимное исключение (устраняет blocker двойной выплаты dual-key).
- **Привязка выплаты (anti-malleability).** payoutBinding = Poseidon(payoutOwnerWallet ‖ mode) совпадает с публичным входом; пруф, скопированный из мемпула с чужим payout, проваливает верификацию.
- **Согласованность величины.** D пересобирается из witness И публичного входа — нельзя клеймить D=1000 против листа D=1.

**PUBLIC входы (все связаны в IC-векторе пейринга):** root, nullifierHash, D (denomIndex), asset (TON|ATH), epoch, payoutOwnerWallet, mode(claim|refund). Кредитуемая сумма — ЧИСТАЯ функция связанных D/asset, НИКОГДА не из произвольного поля сообщения (закрывает cross-pool/cross-asset форж).

**PRIVATE (witness):** sharedSecret, siblings[20] + pathBits, leafIndex, payoutOwnerWallet-preimage. НЕ раскрывается: leafIndex, чей лист, чей чек, intent_id.

**Кто генерит sharedSecret:** ОТПРАВИТЕЛЬ при create, доставляет получателю в шифртеле капсулы-чека PCP1 kind3 (приём пассивен). Отправитель знает секрет — но он и так знает получателя; приватность рвётся против ЦЕПИ/третьих лиц.

## 2. Nullifier и ограничение роста состояния

- **spent-set:** `map<epoch, map<uint256 nullifierHash, Bool>>`, эпоха-скоупный.
- **Единый nullifier для claim и refund** (правка blocker): обе ветки потребляют ИДЕНТИЧНЫЙ nullifierHash; mode гейтит лишь ветку выплаты и авторизацию. Ровно-один-раз.
- **Ограничение роста БЕЗ дыры двойной траты (три жёстких инварианта):**
  1. **per-epoch деревья ОБЯЗАТЕЛЬНЫ** (не единое вечное дерево). Единое append-only дерево + эвикция nullifier по эпохам = replay уже потраченного чека против нового корня — запрещено.
  2. **root тэгирован эпохой.** Контракт проверяет, что root принадлежит дереву ИМЕННО объявленной public epoch (не «∈ глобальное окно»), иначе throw. root и nullifier-bucket выбираются ОДНИМ связанным public epoch атомарно.
  3. **Порядок ретайра.** nullifier-набор эпохи E эвиктится СТРОГО ПОСЛЕ того, как корень E НАВСЕГДА выпал из окна принимаемых корней И закрылись окна claim+refund. Тогда membership-пруф на старый лист против живого корня построить нельзя → повторная трата невозможна даже при известном nullifier. Sequencing зафиксирован ИНВАРИАНТОМ в контракте.
- **Разведение двух временных окон** (правка privacy-major): «эпоха для эвикции состояния» и «принимаемый анонимный набор» — РАЗНЫЕ. Членство/claim разрешены против скользящего окна из W соседних эпох как ОДНОГО анонимного набора (бакеты сливаются, набор растёт); эпоха эвиктится только когда ВСЕ её claim+refund окна закрыты. Длина эпохи — по бюджету состояния, ширина W — по приватности, независимо.
- Опция для компактности: indexed-Merkle-tree (Aztec) для доказуемого невключения — на 1.5 избыточно, достаточно поэпохного flat-map со сбросом целой эпохи.

## 3. Деноминации, сумма и сбор произвольных сумм

- Фиксированные деноминации, отдельный логический пул на (asset, denom, epoch); внутри — неразличимы. Причина жёсткости: произвольный номинал тривиально матчит create↔claim по величине даже при идеальном zk.
- **Малая лестница круглых номиналов** (концентрировать ликвидность в один набор — урок Zcash Ironwood): например GRAM {1, 10, 100, 1000}; ATH — своя параллельная лестница в отдельном пуле. Точные значения — выбор владельца.
- **Произвольные суммы — ПУТЬ A (классический Tornado).** Клиент делает КАНОНИЧЕСКОЕ жадное разложение (все дробят одинаково → слабее split-fingerprint): 250 = 100+100+10+10+10+10+10; каждый чек = свой commitment+nullifier+пруф+claim. Остаток ниже младшего номинала — плоским (legacy) путём с утечкой либо округлением (решение владельца).
- **Остаточная утечка Пути A** — split-fingerprint — принимаем; смягчается каноническим разложением и малым числом круглых номиналов.
- **ПУТЬ B (UTXO-ноты со скрытой суммой) — ОТКЛОНЁН на 1.5:** тяжёлая join-split-цепь + приватное локальное note-состояние → неподъёмно для SE2 и аудита immutable-цепи. Помечен как будущий v2.

## 4. On-chain изменения

- **Commitment-дерево на (asset, denom, epoch):** инкрементальное Poseidon глубины 20; в стейте nextLeafIndex, frontier (правый край, НЕ все листья), текущий root, кольцо корней окна W. Листья on-chain НЕ хранятся (клиент реконструирует путь из emitted-событий).
- **Nullifier-набор:** `map<epoch, map<uint256, Bool>>`, эвикция целой истёкшей+свёрнутой эпохи.
- **Verifier Groth16 на НАТИВНЫХ опкодах BLS12-381 TVM** (с 2023); VK ВШИТ в genesis (портировать эквивалент авто-верификатора TONado под Tact). ⚠️ КРИТИЧНО: Poseidon НЕ имеет нативного TVM-опкода (нативны только группа/пейринг); on-chain вставка листа (~20 Poseidon по глубине) = дорогая полевая арифметика. Забенчить газ CREATE до genesis; при дороговизне — off-chain корень + пруф корректной вставки, либо TVM-дешёвая circuit-совместимая хэш-функция дерева.
- **Turnstile per (asset, denom):** created_value, claimed_value, cancelled_value; инвариант net_locked = created − claimed − cancelled ≥ 0, ЖЁСТКИЙ throwUnless ПЕРЕД каждым кредитом (не пассивная «сверка»).
- **Новые message (расширяют ReceiveIntent 0x7E1F5035/36/37):**
  - `CreateShieldedCheque`: дебет user.balance отправителя на D + резервы (worst-case verify-газ инлайн-константой); вставка листа; апдейт корня; слим-запись ChequeNote{commitment, sender_wallet, asset, denom, epoch, settlement_reserve} БЕЗ recipient; created_value += D; receipt-ring ACT_CREATE_INTENT.
  - `ClaimShielded`: proof 192B + public; проверки root∈окно-W-и-тэг-эпохи, nullifierHash∉spent, verify, throwUnless(net_locked ≥ D), кредит user.balance(asset) += D, claimed_value += D, вставка nullifier, ACT_CLAIM_INTENT.
  - `RefundShieldedExpired`: sender-signed, mode=refund, epoch ≥ expiry, ТОТ ЖЕ единый nullifier; кредит sender, cancelled_value += D.
- **Приём claim/refund — INTERNAL, не external** (правка blocker газ-дренажа): внутреннее сообщение от кошелька получателя с value ≥ worst-case верификации; pre-accept только auth/nonce/manifest (10k credit сохранён), verifier POST-accept (паттерн publish-external). Получатель и так раскрыт на 1.5 — приватность не теряется, бесплатный external-флуд мусорными пруфами исключён.
- **ATH fail-closed:** asset==ATH ⇒ parseStdAddress(payoutOwnerWallet).workchain == 0 (переиспользовать isBasechainAddress), иначе throw — против вечной заморозки ATH на masterchain. Вывод ATH из Vault по-прежнему требует basechain-owner.

## 5. Settlement и сохранность средств

- **Нет двойного клейма:** nullifier проверяется+вставляется атомарно; claim и refund делят ОДИН nullifier.
- **Нет форджа:** валидный Groth16 (VK из церемонии) + архитектурный TURNSTILE per-(asset,denom): claim не выносит больше net_locked своего суб-пула, не трогает общий supply Vault (airdrop/vesting/MSS изолированы). ⚠️ ЧЕСТНО: turnstile капирует ИНФЛЯЦИЮ supply, но НЕ кражу in-flight escrow — при утечке τ форжер сливает ВСЕ неистраченные чеки бакета до net_locked (кража pending честных получателей без превышения supply). Поэтому turnstile — только анти-инфляционный лимит, а НЕ гарантия custody; настоящая защита custody — церемония.
- **Нет потери — ТОТАЛЬНАЯ резолюция цикла** (правка blocker осиротевших чеков): ни один (asset,denom,epoch)-лот не ретайрится, пока каждый лист не claimed ИЛИ refunded. Перед ретайром эпохи — форсированный AUTO-REFUND SWEEP отправителю как терминальный шаг, атомарно с закрытием nullifier-set эпохи. Чек с потерянным secret не застревает — средства возвращаются отправителю.
- **Устаревший пруф** (правка major доставки): клиент ОБЯЗАН ре-доказывать против ЖИВОГО корня перед отправкой claim; окно валидности чека заведомо шире периода продвижения корней; auto-sweep гарантирует, что деньги не теряются.
- **Интеграция с плоскими балансами:** CREATE дебетует users[sender], CLAIM кредитует users[recipient] РОВНО как текущий ClaimReceiveIntent (Vault.tact ~2017-2021); инкремент publish_nonce + receipt-ring как сегодня; settlement_reserve_ton сохраняется.

## 6. Что скрыто vs остаток

**СКРЫТО:** КАКОЙ чек дренирует клейм — ребро create(sender назван)→claim РАЗОРВАНО для третьих лиц: наблюдатель видит N create'ов номинала D и M клеймов номинала D, но не матчит конкретную пару (commitment из nullifierHash не выводится, membership прячет лист). Сумма скрыта до гранулярности деноминации. Приём УЖЕ пассивен (stealth-скан капсулы), zk добавляет анонимность именно ОБНАЛА.

**НЕ СКРЫТО (принято владельцем):** отправитель + сумма-в-деноминации на CREATE; payout-адрес получателя на CLAIM — но БЕЗ линковки к конкретному отправителю; деноминация D раскрыта. Рвётся связка create↔claim, а не факт существования каждой из них.

### 17.1. План trusted setup

**Выбор: Groth16 + обязательная многосторонняя MPC-церемония + turnstile-бэкстоп.** НЕ single-party setup.

**Почему Groth16, а не PLONK/Halo2.** Схема ФИКСИРОВАНА и immutable — ревизий не будет, поэтому universal/updatable SRS у PLONK не окупается: платить +газ и +размер пруфа (256–500B vs 192B, верификация ~25мс vs ~8мс) за ненужную переиспользуемость нерационально. Прецедент TONado Cash — на Groth16 над теми же нативными BLS12-381 опкодами TVM. Halo2 (без setup) устранил бы риск токсичных отходов как класс, но тяжелее верификация и НЕТ TON-прецедента — на genesis не берём.

**Главный риск.** Groth16 = per-circuit phase-2 setup. Утечка τ («токсичные отходы») у ЛЮБОГО участника = способность форжить валидные пруфы = слив пула реальных денег. Прецедент фатальности: Zcash Sprout 2018 — класс-уязвимость параметров позволяла НЕОГРАНИЧЕННЫЙ форж shielded-токенов. На immutable clean-16 патча нет.

**Церемония (обязательна ДО деплоя):**
- Переиспользовать публичный perpetual-powers-of-tau как **phase-1** (десятки-сотни независимых участников, многократно проверена).
- Провести Platho-специфичную **phase-2** под ТОЧНУЮ claim-цепь: ≥ несколько десятков независимых участников, ПУБЛИЧНЫЙ transcript, аттестация уничтожения доли каждым.
- Свойство: setup безопасен, ПОКА ХОТЯ БЫ ОДИН участник честен и уничтожил τ (прецедент Zcash Sapling 100+).
- Дедлайн церемонии жёстко привязать к деплою clean-16; VK из финального transcript вшивается константами в genesis.

**Два страховочных слоя (нужны ОБА):**
1. Церемония — защищает custody (это критическая защита средств, НЕ опциональный трюк: turnstile кражу pending-escrow не ловит).
2. Turnstile per-(asset,denom) — капирует ущерб форжа границей net_locked своего суб-пула, не давая тронуть общий supply Vault и балансы других/другого актива.

**Честная коммуникация владельцу:** «форж = потеря всей живой ликвидности пула деноминации», НЕ «безопасно из-за turnstile». Turnstile держит «нет инфляции», а не «нельзя украсть pending». Сжимать окно pending-экспозиции (короткий claim-grace, ограничение размера живого escrow бакета) как cap ущерба.

**Fallback:** если доверие к организуемой церемонии низко — PLONK/universal-updatable SRS (переиспользуемый много раз проверенный публичный SRS снижает ceremony-риск) ценой +газ/+размер пруфа. Оба варианта используют одну MPC-митигацию; turnstile остаётся при любом выборе.

### 17.2. Изменения контракта

1. Расширить ReceiveIntent-путь: CreateShieldedCheque (дебет user.balance на D+резервы, вставка листа в per-(asset,denom,epoch) дерево, апдейт корня, слим-ChequeNote БЕЗ recipient, created_value += D, receipt-ring ACT_CREATE_INTENT).
2. ClaimShielded приходит INTERNAL от кошелька получателя с value ≥ worst-case verify-газа (НЕ external — иначе бесплатный gas-дренаж через 10k pre-accept). Pre-accept: только auth/nonce/manifest. Post-accept: verify Groth16, root∈окно-W и root тэгирован объявленной epoch, nullifierHash∉spent[epoch], throwUnless(net_locked = created−claimed−cancelled ≥ D), кредит user.balance(asset) += D, claimed_value += D, вставка nullifier, receipt-ring ACT_CLAIM_INTENT.
3. Единый per-cheque nullifierHash = Poseidon(sharedSecret‖leafIndex) для claim И refund (НЕ mode-специфичный ключ) — истинное взаимное исключение, устраняет двойную выплату dual-key.
4. RefundShieldedExpired: sender-signed, mode=refund, epoch ≥ expiry, ТОТ ЖЕ единый nullifier, кредит sender, cancelled_value += D; жёсткий дедлайн settlement-close S.
5. Per-epoch commitment-деревья ОБЯЗАТЕЛЬНЫ (не единое вечное дерево); в стейте nextLeafIndex, frontier, текущий root, кольцо корней окна W; листья on-chain не хранятся (emit-события для клиентской реконструкции пути).
6. Инвариант ретайра эпохи в КОДЕ (не комментарии): nullifier-set эпохи E эвиктится строго ПОСЛЕ выпадения корня E из окна И закрытия claim+refund окон; root и nullifier-bucket выбираются одним связанным public epoch атомарно.
7. ОБЯЗАТЕЛЬНЫЙ auto-refund sweep как терминальный шаг ретайра эпохи: ни один лот не ретайрится, пока каждый лист не claimed ИЛИ refunded — иначе безвозвратная потеря на immutable-цепи.
8. Turnstile per-(asset,denom): жёсткий throwUnless(net_locked ≥ D) ПЕРЕД кредитом (не пассивная сверка); cancel/refund атомарно инкрементит cancelled_value.
9. ATH fail-closed: asset==ATH ⇒ parseStdAddress(payoutOwnerWallet).workchain==0 (переиспользовать isBasechainAddress), иначе throw ДО кредита — против вечной заморозки ATH на masterchain-адресе.
10. Groth16-verifier на нативных BLS12-381 опкодах TVM, VK вшит константами в genesis; полный IC-вектор {root,nullifierHash,denomIndex,asset,epoch,payoutOwnerWallet,mode} связан в пейринге; кредитуемая сумма — чистая функция связанных denom/asset, никогда из произвольного поля сообщения.
11. payoutOwnerWallet вшит публичным входом (anti-malleability): скопированный из мемпула пруф с чужим payout проваливает верификацию; сохранить существующий signed_payload+publish_nonce гейт по названному payout-owner В ДОПОЛНЕНИЕ к zk-привязке (против грифинга nonce/receipt-ring).
12. Резерв на CREATE калибруется под worst-case Groth16-газ как инлайн-константа (нет pre-accept fee-getter — паттерн Vault-externals на краю 10k credit).

### 17.3. Изменения клиента

1. Упаковать zk-прувер в PWA/TG-Mini-App. ⚠️ Нативный rapidsnark/mopro в webview НЕДОСТУПЕН (mopro даёт Swift/Kotlin биндинги для НАТИВНЫХ приложений, не для webview) — доступен только WASM. Реальный митигатор — не 'нативная скорость', а ФОНОВОЕ ПРЕДВЫЧИСЛЕНИЕ.
2. Предвычислять пруф в фоне СРАЗУ после пассивного stealth-приёма капсулы-чека (sharedSecret/leafIndex в шифртеле PCP1 kind3, дерево публично, root+payoutOwnerWallet известны) — ДО того как юзер жмёт 'получить'. Тогда wall-time на клейме ≈ 0 даже при генерации 10–30с.
3. Включить cross-origin isolation (COOP/COEP) для многопоточного WASM (SharedArrayBuffer) — иначе однопоточный WASM-пруф Tornado-класса на iPhone SE2 = десятки секунд + риск OOM (webview jetsam ~1–1.5ГБ, proving key десятки МБ).
4. Переписать UX-бюджет честно: 'фон 10–30с, на клейме мгновенно', НЕ 'нативные 1–3с'. Забенчить пиковую RAM и время на РЕАЛЬНОМ SE2 в Safari/TMA-webview ДО фиксации схемы; graceful-degradation при нехватке памяти; минимизировать constraints под мобильный WASM.
5. Ре-доказывать против ЖИВОГО корня перед отправкой claim: если окно принимаемых корней прокрутилось мимо root предвычисленного пруфа — перестроить Merkle-путь к свежему недавнему корню.
6. Клиент реконструирует Merkle-путь из emitted-событий вставки листьев (листья on-chain не хранятся).
7. Каноническое жадное разложение произвольной суммы в мультимножество номиналов (все дробят одинаково → слабее split-fingerprint); предвычислять ВСЕ под-пруфы; 'claim all' шлёт несколько claim-internal.
8. Рандомизированная (крупная) задержка клейма относительно приёма — убить timing/FIFO-корреляцию (приём не спешный, почти бесплатно); не предлагать 'получить' немедленно.
9. ЖИВОЙ индикатор размера анонимного набора его (asset,denom) перед клеймом: 'сейчас в наборе N — приватность слабая, подожди'; блокировать/предупреждать при N < порога.
10. Кредитовать на СВЕЖУЮ приёмную внутреннюю идентичность на клейм (эфемерный auth_pubkey), не переиспользовать один owner_wallet — иначе клеймы получателя кластеризуются.
11. UX-пометка: ATH-приём раскрывает класс адреса (basechain-owner), ATH-приватность слабее TON.

### 17.4. Цена (честно)

**Верификация:** ≈ 0.015 GRAM за пруф (прецедент TONado, нативные BLS12-381 опкоды, gas-bounded, без софт-пейринга) — совпадает с бюджетом владельца +~0.015 GRAM на приём. НО это ТОЛЬКО верификация.

**⚠️ Скрытая цена CREATE:** вставка листа = ~20 Poseidon-хэшей ON-CHAIN, а у Poseidon НЕТ нативного TVM-опкода (нативны только группа/пейринг BLS12-381) → дорогая полевая арифметика в TVM. Poseidon дёшев OFF-chain (в схеме), но здесь считается ON-chain — обратный случай, та же боль, что дорогой deposit в Tornado на EVM. Фактический газ CREATE НЕ измерен; при immutable мискалибровка = навсегда замороженные create/claim. **Обязательно забенчить реальный газ Tact CREATE+CLAIM на целевой глубине дерева ДО genesis с запасом под лимит компьюта.**

**Хранение:** +1 nullifierHash (256-бит ключ+флаг) в map эпохи на claim; +1 лист + обновление frontier на create; кольцо корней окна W. Storage-endowment на чек — порядка текущего VAULT_RECEIVE_INTENT_STORAGE_ENDOWMENT (5,000,000 нанотон). Поэпохная эвикция nullifier ограничивает суммарный стейт (иначе nullifier неэвиктируем: оценки Aztec ~2ГБ/год@1tps).

**Пруф на устройстве:** НЕ 'нативные 1–3с' (rapidsnark в webview недоступен) — реалистично ФОН 10–30с WASM на iPhone SE2 (при COOP/COEP-многопотоке — быстрее), на клейме мгновенно за счёт предвычисления. Риск OOM на SE2 (3ГБ RAM, proving key десятки МБ).

**Деноминации/UX:** произвольная сумма = K чеков = K пруфов (K фоновых генераций) + K claim-internal + K×(0.015 + запись). Для 137 GRAM при лестнице {1,10,100,1000} — до ~11 чеков. Для редких КРУГЛЫХ целевых сумм терпимо; для некруглых — деградация газа/времени + split-fingerprint. Итог per-приём: verify(~0.015) + storage-write + worst-case CREATE-газ (замерить), ×K для дробной суммы.

### 17.5. Остаточные утечки (честно)

1. МАЛЫЙ АНОНИМНЫЙ НАБОР НА СТАРТЕ — ДОМИНИРУЮЩАЯ СЛАБОСТЬ И ПРЯМОЕ ПРОТИВОРЕЧИЕ С ЦЕЛЬЮ. Владелец принял zk именно потому, что платежи редкие/ценные. Но 'редкий+ценный' = крупный/нестандартный номинал = бакет (D,asset,epoch) с 1–3 листами, часто уникальный. Эффективный набор = одновременно неистраченные чеки той же деноминации; при launch-scale он схлопывается до 1, и наблюдатель матчит единственный create с единственным claim ТРИВИАЛЬНО, без атаки на крипту. Это НЕ переходная фаза, а свойство профиля 'редкие платежи'. РЕШЕНИЕ: гейтить запуск zk-платежей за минимальным ЖИВЫМ набором per-(D,asset), а не запускать 'с честной пометкой'; при N<порога иллюзию приватности не давать.
2. Split-fingerprint: редкая комбинация K чеков при дроблении суммы + со-тайминг клеймов сама линкует (смягчено каноническим разложением и малым числом круглых номиналов, не устранено).
3. Timing/FIFO-корреляция: клейм сразу после create схлопывает набор до окна create'ов — смягчение крупной рандомизированной задержкой клейма.
4. Address-reuse получателя: кредит на названный owner_wallet кластеризует все его клеймы (ВСТРОЕННОЕ свойство кредита в именованный реестр на 1.5, а не опция) — смягчение свежей приёмной идентичностью на клейм; иначе атака пересечения бакетов вскрывает и отправителя.
5. Отправители перечислимы поимённо: CREATE хранит sender_wallet+asset+denom+epoch открыто → наблюдатель знает членов набора; при малом наборе пересечение множеств-корзин по повторным клеймам одного получателя вскрывает отправителя.
6. Получатель как таковой виден ('получил D') + раскрытая деноминация — метаданные КТО и в какое ведро суммы принимает, даже если ОТ КОГО скрыто.
7. ATH-приватность структурно слабее TON: требование basechain-owner раскрывает класс адреса и сужает ATH-набор — принять и пометить в UX.
8. Утечка суммы на границах: очень крупная/нестандартная суммарная величина из редких номиналов сужает набор; остаток ниже младшего номинала идёт плоским путём с утечкой.
9. Риск токсичных отходов церемонии — это САХРАННОСТЬ, не приватность: turnstile капирует инфляцию supply, но НЕ кражу pending-escrow бакета при утечке τ; заперт церемонией, не нулевой.

### 17.6. Интеграция в clean-16

clean-16 stealth уже скрывает получателя СООБЩЕНИЙ; этот платёжный слой — ортогональное дополнение на ТОМ ЖЕ immutable genesis. Складывается так:

1. **Переиспользует существующий scaffolding.** ReceiveIntent-путь (сообщения 0x7E1F5035/36/37, struct ReceiveIntent с commitment/settlement_reserve, ACT_CREATE/CLAIM/CANCEL_INTENT в receipt-ring K=20, плоские ton_balance/ath_balance uint128) расширяется, а не переписывается: commitment-only чек-эскроу уже спроектирован, добавляется Merkle-членство + nullifier + verifier поверх.

2. **Пассивный приём уже есть.** stealth-скан капсулы-чека PCP1 kind3 + secret в шифртеле — получатель на ПРИЁМЕ не светится; zk закрывает ровно ОБНАЛ, который оставался именованным. Half-схемы бесплатно унаследованы от stealth-инфраструктуры clean-16.

3. **Genesis-артефакты, вшиваемые ДО деплоя:** Groth16-verifier (нативные BLS12-381 опкоды TVM) + VK из MPC-церемонии (phase-1 perpetual-PoT + Platho phase-2) + параметры Merkle (глубина 20) + лестница деноминаций + длина эпохи/окно W/expiry/settlement-close. Всё immutable — калибруется и замеряется до ceremony-дедлайна.

4. **Состояние ограничено по построению** — в духе существующей FIFO-модели Vault (CapsuleHub auto-eviction): per-epoch деревья + истечение чеков + поэпохная эвикция nullifier + auto-refund sweep дают ограниченный активный стейт без риска двойной траты.

5. **Развязка со stealth-сообщениями:** платёжный zk НЕ трогает send-путь и приватность сообщений; это отдельный суб-пул с turnstile-изоляцией, не затрагивающий общий supply (airdrop/vesting/MSS) и балансы других контрактов.

6. **Запуск синхронизировать с ликвидностью.** Приватность приходит только с наполнением набора — гейтить включение zk-платежей за минимальным живым набором, не давать иллюзию на пустом пуле.

### 17.7. Аудит-гейты

1. G-FORGE (custody, blocker-класс): аудит IC-вектора портированного/сгенерированного Tact-верификатора — ВСЕ публичные входы {root,nullifierHash,denomIndex,asset,epoch,payoutOwnerWallet,mode} связаны в пейринге; кредитуемая сумма — чистая функция связанных denom/asset, никогда из произвольного поля сообщения. Тест: пруф дешёвого пула не кредитует дорогой/чужой актив/устаревшую эпоху.
2. G-NULLIFIER-DUAL: единый per-cheque nullifierHash для claim и refund; тест 'получатель склеймил → отправитель НЕ может отрефандить тот же чек' и наоборот (устранение двойной выплаты dual-key).
3. G-EPOCH-REPLAY: per-epoch деревья + порядок ретайра. Пин-тест на границе: root E принят ⇒ bucket E жив; bucket E мёртв ⇒ root E отвергнут НАВСЕГДА. Тест replay уже потраченного листа против нового корня после эвикции его nullifier — должен падать.
4. G-ORPHAN-SWEEP: ни один лот не ретайрится, пока каждый лист не claimed ИЛИ refunded; форсированный auto-refund sweep атомарен с закрытием эпохи. Тест 'не-склеймленный не-отменённый чек на ретайре → средства вернулись отправителю, не потеряны'.
5. G-GAS-DRAIN: claim/refund приходят INTERNAL с value ≥ worst-case verify; verifier POST-accept, pre-accept только auth/nonce/manifest. Тест: external-флуд мусорными пруфами не дренирует баланс Vault.
6. G-GAS-CALIBRATION: замерить фактический газ Tact CREATE (вставка листа, ~20 Poseidon on-chain без нативного опкода) + CLAIM на целевой глубине дерева на TVM с запасом под лимит компьюта — ДО genesis (immutable мискалибровка = замороженные средства).
7. G-ATH-FREEZE: asset==ATH ⇒ payoutOwnerWallet.workchain==0 fail-closed ДО кредита; тест 'ATH-claim на masterchain-адрес отвергается'.
8. G-TURNSTILE: жёсткий throwUnless(net_locked = created−claimed−cancelled ≥ D) перед кредитом; cancel атомарно инкрементит cancelled_value; тест 'claimed+cancelled не превышает created per (asset,denom)'.
9. G-ANTI-MALLEABILITY: payoutOwnerWallet вшит публичным входом; тест 'скопированный из мемпула пруф с чужим payout проваливает верификацию'; сохранён signed_payload+publish_nonce гейт против грифинга.
10. G-CEREMONY: MPC phase-2 проведена с ≥ десятками независимых участников, публичный transcript, аттестация уничтожения τ, дедлайн привязан к деплою; финальный VK вшит в genesis. Без успешной церемонии — НЕ деплоить.
11. G-CLIENT-PROVER: бенчмарк WASM-пруфа на РЕАЛЬНОМ iPhone SE2 в Safari/TMA-webview (COOP/COEP-многопоток, пиковая RAM, время фона), проверка предвычисления и ре-доказательства против живого корня — ДО фиксации схемы.
12. G-PRIVACY-GATE: живой индикатор размера набора + блокировка/предупреждение при N<порога; запуск zk-платежей гейтится за минимальным живым набором, не 'с честной пометкой' на пустом пуле.

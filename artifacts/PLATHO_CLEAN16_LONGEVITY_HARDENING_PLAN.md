# PLATHO clean-16 — План долговечности и платёжеспособности (Longevity & Solvency Hardening)

> Статус: ЖИВОЙ план. Опора для реализации Фазы-5 поверх Фазы-4 (two-lane).
> Дата: 2026-07-15. Все числа G8-provisional → финализируются из измеренного `cell.computeDataSize()` в Фазе-5.
> ИСТОЧНИК: solvency-at-scale аудит + исчерпывающий timebomb-sweep (104 агента, 89→84→19 бомб, 18 в ЖИВОМ clean-15).

## 0. Зачем этот документ

Прошлый «100-летний» аудит перед clean-15 системно пропустил ЦЕЛЫЙ класс отказов: **неограниченное never-pruned
состояние под разовым эндаументом на общем custody-балансе**, плюс использовал заниженную в **×3.6-11** ставку ренты
(комменты: ~67k нанотон/ячейка/год; канон basechain = **240 631/ячейка/год**). Методология «per-contract, fixed-state,
present-config, N=1» слепа к масштабу+горизонту+связности одновременно. Итог: заключение «век выживания» НЕНАДЁЖНО;
реальные горизонты старых эндаументов ~20-70 лет, а одна бомба (#1) — вообще near-term по масштабу.

Этот план чинит весь класс КОГЕРЕНТНО в редеплое clean-16 (живой clean-15 immutable — не патчится на цепи).

## 2. Инвентарь бомб → кластеры фиксов

Полный список в памяти (`contract-timebomb-inventory.md`). Здесь — группировка под реализацию.

### Кластер A — Pre-accept gas (#1, critical, near-term SCALE, БЛОКЕР)
**Проблема:** withdraw/replaceKeys/setAvatar/mintUsername делают `users.get`+`checkSignature`+полный parse ДО
`acceptMessage` в 10k pre-accept кредите. Стоимость ∝ глубине users-trie (~log₂N). Порог отказа ВЫВОДА — сотни-тысячи
юзеров. Живой clean-15 нельзя масштабировать к целевой юзербазе.

**ЭМПИРИКА 2026-07-15 (`tests/vault-preaccept-gas-scaling.test.ts`):** withdraw total-compute-газ N=1→256:
25581→29256→31706→36606; прирост ~**1225 газа/уровень trie для pre-accept `users.get`** (≈половина от ~2450/уровень
total; вторая половина — post-accept `users.set`). Разбор биндинг-полей = КОНСТАНТА ~1k газа (≈1 уровень).
**⇒ ВЫВОД:** паттерн-фикс PublishBatch (skip parse) даёт всего ~1 уровень запаса (**~×2 по юзерам, НЕ «×тысячи-миллионы»
как заявлял sweep** — sweep-оценка ОПРОВЕРГНУТА эмпирикой). Реальный драйвер — `users.get` O(log N), остаётся pre-accept
(нужен против спама). Абсолютный порог OOG зависит от mainnet gas_credit-конфига (в sandbox-дефолте N=256 ещё success) —
нужен замер против live `code.boc` + глубокий синтетический trie (G8).

**ФИКС (пересмотрен по эмпирике):** паттерн PublishBatch (skip parse post-accept) — необходимо, но НЕДОСТАТОЧНО. Для
реального закрытия #1 нужен ОДИН из: (a) **шардирование users-мапы** по префиксу адреса (K под-мап → мелкий per-shard
trie, pre-accept get дешевле); (b) **дешёвый pre-accept анти-спам** без полного trie-лукапа (напр. компактный commitment
+ post-accept полная сверка). Выбор — по G8-замеру реального порога.
**Гейт:** G8 ОБЯЗАН мерить pre-accept газ vs глубина users-trie против live code.boc с mainnet-конфигом (~30 уровней при 1e9), НЕ при N=1.

### Кластер B — Storage-платёжеспособность (#2,#3,#4,#5,#13,#19, critical/mod)

> **КРИТИЧЕСКАЯ СВЯЗЬ (найдено при разборе кода):** ключи лежат в общей `key_records: map<Int keyId, KeyRecord>`
> (keyId=`computeKeyId(owner,generation,…)`), а UserState хранит ТОЛЬКО `current_key_id`. Старые (revoked) key_id
> НИГДЕ не отслеживаются → эвикция (#4) физически НЕ может удалить старые записи юзера, пока ротация (#3) не
> ограничена до O(1). **Поэтому #3 (кап ротации) — жёсткий ПРЕРЕКВИЗИТ #4 (эвикция): реализовать #3 ПЕРВЫМ.**
> ReplaceMessagingKeys сейчас: `key_records.set(current, revoked)` (1802) + `set(new)` (1804) + `key_record_count++`
> (1818) — старое НЕ удаляется. Фикс #3: `key_records.del(старый current_key_id)` (после grace-окна для in-flight
> отправителей; получатель декодит своим seed-ключом, старая ЗАПИСЬ нужна лишь отправителям для fetch) → каждый юзер
> держит ровно 1 (+опц. grace) запись → эвикция удаляет current_key_id + user + декремент. Grace-политика (revoked-vs-notfound
> для отправителя) — часть дизайна #3, тестировать.

Единый механизм самофинансирования (паттерны уже в CapsuleHub):
1. **Эвикция спящих (#4):** поле `last_active` (бампать в каждом user-touching receive) + permissionless
   `EvictDormantUser`, гейт `(now-last_active > 2yr) & ton_balance==0 & ath_balance==0` → `users.del` +
   `key_records.del` + декремент счётчиков. Ключи детерминированы из seed → вернувшийся ре-регистрируется 1 tx, НОЛЬ
   крипто-потерь.
2. **Кап ротации ключей (#3):** на `ReplaceMessagingKeys` — `key_records.del(старый current)` после grace-окна (или
   держать current+1). Хранить revoked как compact hash без 1.2КБ ML-KEM-тела. Состояние ключей → O(1) на юзера.
3. **query_id вместо set (#2):** `processed_ath_deposits` заменить на per-user монотонный high-water `query_id` в
   UserState (O(1), прунится с юзером) вместо O(депозитов)-множества.
4. **Reserve-флор + fail-loud (#5):** ввести `vaultStorageReserve() = user_count×PER_USER + key_record_count×PER_KEYREC` (×1.25);
   enforce `myBalance() - context().value >= Σton_balance + vaultStorageReserve()` на Withdraw*/ATH-выводе (зеркало
   CapsuleHub `protectedReserve`/`MIN_PROTECTED`). Рента НИКОГДА не ест кастодиал; неплатёжеспособность fail-closed, не тихо.
5. **Эндаумент = рента×2г×1.25 (#4):** размерить по worst-case записи (UserState + ring + KeyRecord) из измеренного DataSize.
6. **ProfileRegistry (#13):** `avatar_records.del` предыдущей версии при апдейте (рост с юзерами, не событиями).
7. **Base code-рента реестров (#19):** явный base-code-rent эндаумент при genesis; assert `genesis_balance ≥ base_rent×горизонт`.

### Кластер C — Квант-custody (#6) — РЕШЕНО 2026-07-15: ed25519 + план миграции (НЕ PQ-подпись)
**Находка:** on-chain PQ-подпись НА КАЖДЫЙ вывод custody НЕРЕАЛИЗУЕМА на TON — Dilithium/ML-DSA (NTT+полином.арифметика)
не влезает в газ-лимит; Falcon (FFT над float) невозможен в целочисл. TVM; SPHINCS+ (~8-50КБ подпись, тысячи хешей)
слишком велик/дорог для частых выводов; нативных PQ-опкодов у TON нет. Hash-based (XMSS/Winternitz-Merkle) feasible
ТОЛЬКО для РЕДКИХ действий.
**Решение владельца:** custody остаётся **ed25519**; квант-стойкость = **МИГРАЦИЯ на PQ-преемника ДО квант-горизонта
(~2035-50)**, пока ed25519 безопасен (анонс через контроллер, pre-quantum). Контрактной правки custody НЕТ (L5 снята).
РИСК: миграцию надо успеть; иначе всё компрометируется (принятый остаток). Опц. будущее харденинг — hash-based эвак-люк.

## 4. ОБЯЗАТЕЛЬНЫЕ гейты до seal (immutable — после запечатывания не чинится)

1. **Внешний аудит storage-экономики** на 20-100 лет × миллионы юзеров (модель: рента = f(map-size × годы), НЕ fixed-state).

3. **Внешний ANO-CCA / key-privacy аудит** гибрида ML-KEM (несущий гейт разрыва графа, из Фазы-4).
4. **PQ-подпись custody** — независимый крипто-ревью выбранной схемы + газ-bench.
5. НЕ авто-деплоить; genesis-редеплой = bump `deployment_id` (форк на тех же vanity-кошельках).

## 5. Живой clean-15 — операционные меры (до миграции)

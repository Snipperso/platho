# Platho メッセージ暗号プロトコル

本ドキュメントでは、Platho PWA が実装するクライアントサイドのメッセージ暗号化について説明します。

## 暗号化

プライベートメッセージは X25519 + ML-KEM-768 + AES-GCM を使用します。これが唯一のプライベートメッセージ用スイートです（`hybrid-v1`、コントラクト値 `2`）。

## 鍵バンドル

PWA が作成またはインポートするすべての 24 単語の GRAM リカバリーフレーズは、暗号化鍵ペアと Ed25519 署名鍵を持つメッセージング識別子を決定論的に導出します。公開暗号化鍵の素材は、公開鍵バンドルとしてエクスポートされます。

- `keyId`: 公開鍵素材に対する SHA-256 ベースの識別子。
- `x25519PublicKey`: 32 バイトの古典的 ECDH 公開鍵。
- `mlKem768PublicKey`: `hybrid-v1` 用の 1184 バイトの ML-KEM-768 公開鍵。
- `mlKem768PublicKeyHash`: ML-KEM-768 公開鍵の SHA-256。
- `mlKem768PublicKeyLen`: `hybrid-v1` では常に `1184`。

PWA は暗号化の前に `keyId`、`mlKem768PublicKeyHash`、`mlKem768PublicKeyLen` を再計算します。id、スイート、コントラクトスイート、ハッシュ、または長さが一致しないと主張するバンドルは拒否されます。

受信者の検索は、アクティブな Vault 鍵レコードに保存されたオンチェーンの `enc_pubkey`、`sign_pubkey`、および完全なオンチェーン `pq_kem_pubkey` セルによって定義されます。ハッシュと長さはコンパクトなバインディングフィールドとしてレコードに残りますが、別のクライアントが実際に `hybrid-v1` カプセルを暗号化できるのは、完全な ML-KEM-768 公開鍵があるからです。

## 署名済みバンドル

PWA は署名済みの公開鍵バンドルをエクスポートできます。署名済みペイロードには次の内容が含まれます。

- プロトコルドメイン `PLATHO.MESSAGING.KEY_BUNDLE.SIGNATURE.V1`;
- 発行タイムスタンプおよび任意の有効期限タイムスタンプ;
- 任意のオーナーウォレットおよび Vault アドレスのプレースホルダー;
- 公開暗号化バンドル;
- 32 バイトの Ed25519 署名公開鍵。

署名は安定した JSON ペイロードを対象とし、バンドルが信頼される前に検証されます。これにより、ローカルバンドルの静かな改ざんが防止され、Vault が `KeyRecord` に保存する正確な `sign_pubkey` がクライアントに与えられます。

PWA の `keyId` はクライアントバンドルの識別子です。これは、オーナーアドレス、鍵世代、署名鍵、暗号化鍵、PQ ハッシュ、PQ 長、暗号スイートからオンチェーンで計算される Vault コントラクトの `current_key_id` を置き換えるものではありません。本番クライアントは、ウォレット識別子として信頼する前に、Vault 鍵レコードに対してバンドルを検証しなければなりません。

署名済みバンドルは、メッセージング鍵の自己署名です。ウォレットの所有権は Vault のアクティベーションによって固定されます。組み込みの Platho ウォレットが `RegisterMessagingKeys` を送信し、後の `ReplaceMessagingKeys` ローテーションは Vault 認証で署名された外部メッセージとなり、受信者はそのウォレットのアクティブなオンチェーン鍵レコードに対して署名済みバンドルを検証します。

## ウォレットの所有権

本番 PWA は外部ウォレットコネクターを使用しません。ユーザーは通常の 24 単語の GRAM リカバリーフレーズを作成またはインポートし、PWA は
そのフレーズから GRAM ウォレット鍵、別個の Vault 認証鍵、およびメッセージング用の暗号化/署名鍵を決定論的に導出します。Vault の
アクティベーションが所有権のアンカーです。組み込みウォレットは、オンチェーン鍵レコードを所有するのと同じウォレットから `RegisterMessagingKeys` に署名して送信します。
`ReplaceMessagingKeys` は公開受信/メッセージング鍵レコードのみをローテーションし、Vault 認証鍵はローテーションしません。

受信者は、そのウォレットのアクティブな Vault 鍵レコードに対して照合した後にのみ、メッセージングバンドルを信頼します。

- レコードのオーナーが期待されるウォレットである;
- `enc_pubkey` と `sign_pubkey` が署名済みバンドルと一致する;
- ハイブリッドレコードが、ハッシュだけでなく完全な `pq_kem_pubkey` セルを公開している;
- デコードされた ML-KEM-768 鍵バイトのハッシュが `pq_kem_pubkey_hash` になる;
- アクティブな `current_key_id` が検証済みの鍵レコードを指している。

プロフィールのエクスポート/インポートフローは、24 単語の GRAM リカバリーフレーズを扱います。別個のメッセージング鍵のバックアップも、
外部ウォレット接続モードもありません。

## コンパクトバイトレイアウト

プライベートカプセルのオンチェーンセルは、最終版の `platho.byte-layout.v1` バイナリレイアウトを使用します。PWA はエクスポート/共有 UI 用にカプセルを JSON でラップすることがありますが、プロトコルペイロードはバイナリバイトであり、JSON でもオフチェーンポインターでもありません。`CapsuleHub` はコンパクトな認証済みヘッダー/インデックスとボディハッシュを保存します。暗号化されたボディセルは、受理された公開トランザクションのボディに残り、TON メッセージ履歴から再構築され、その後保存されたハッシュに対して検証されます。

すべての公開は、Vault 残高で資金供給される署名済み外部メッセージとして Vault を経由します。ユーザーはまず内部の
Vault GRAM 残高に資金を供給し、次に PWA がアクティブな `auth_pubkey` で公開リクエストに署名します。リレーヤーは、
ウォレット鍵やメッセージング署名鍵を保持せずに外部メッセージを送信できます。署名済みペイロードは、オーナー、ノンス、最大課金額、ペイロードの前に、`VPB1`、
`deployment_manifest_hash`、対象の Vault アドレス、公開種別でドメイン分離されています。
CapsuleHub が ACK またはバウンスで実際に返送する GRAM 値は、追跡されている保留中の公開返金額を上限として、ユーザーの内部 Vault GRAM
残高に入金されます。Vault 残高またはチェーンアクセスが利用できない場合、PWA は
フェイルクローズし、公開アクションを表示してはなりません。

`auth_pubkey` が Vault 残高の支出を承認するため、ローカルのメッセージング署名鍵だけが侵害されても、Vault の公開、支払いチェック、
ユーザー名、アバターのアクションは承認されません。メッセージング署名鍵の侵害は、それでもメッセージレベルの識別署名に
影響を与える可能性があるため、鍵の置き換えは、将来の受信暗号化チェックに向けて古い公開受信鍵レコードを失効させます。

PWA のメッセージ料金はカプセル単位です。現在のリザーブで ATH 割引がない場合、正確な正準の例は、1 KiB の公開エントリーが `0.0337 GRAM` から、`hybrid-v1` の 1 KiB プライベート
カプセルが `0.0347 GRAM` からとなります。より大きな公開またはプライベートのサイズクラスは、正準クラスに応じてコストが高くなります。これには、
`0.01 GRAM` の完全な Platho プロトコル手数料、CapsuleHub のコンパクトインデックスストレージ基金、Vault のローカル実行リザーブ、および
予想される ACK 返金が含まれます。別途、PWA の保守的な手数料見積もりが、含まれるネットワーク手数料の
許容額 `0.005 GRAM` を上回る場合は、
切り上げた超過分をサーチャージとして追加します。コントラクト呼び出しは、依然としてそれぞれの正準の
必要値から始まります。Vault の公開は `maxCharge = canonical_max_charge + surcharge` を送信します。CapsuleHub には直接的なユーザー
公開 ABI はなく、すべての公開は Vault -> CapsuleHub です。ATH 割引は、Vault のアクティビティエアドロップが
15,000,000 ATH を配布した後にのみ適用されます。そのゲートより前は、メッセージのプロトコル手数料は完全な `0.01 GRAM` の手数料を使用します。PWA は、署名の前に、選択されたコンテンツサイズについて最終的な
ホールドと正味コストを表示しなければなりません。

サーチャージは、署名されたネットワーク/ストレージの安全マージンであり、返金可能な手数料バケットではありません。CapsuleHub は、
添付された値が正準の必要値以上である場合に Vault の公開を受理しますが、公開が成功した ACK は、固定された
公開 ACK リザーブの `30,000,000` ナノトン（`0.030 GRAM`）のみを返します。Vault がその ACK を処理した後、ユーザーにはおよそ
`25,800,000` ナノトンが内部 Vault GRAM 残高に入金されます。正準の必要値を超える署名済みサーチャージは、
ネットワーク/ストレージリザーブの超過分として CapsuleHub に残ります。それは Vault に返されず、
`accrued_plato_fee_ton` としてもカウントされません。

CapsuleHub は、`accrued_plato_fee_ton + max(100 GRAM, 1.25 * live_index_1y_storage_reserve)` に等しい生の GRAM リザーブを保護します。
ライブリザーブは、履歴上の `latest_id` カウンターではなく、プルーニングされていないプライベート/パブリックエントリーカウンターを使用します。別個の
パーミッションレスな `SweepExcessReserve` 呼び出しは、その保護された金額を超える余剰分のみを `DepositProtocolFee` として FeeAccumulator に移動でき、
そこで通常のトレジャリー/バイバック分配に従います。通常のメッセージ送信は、この
スイープを実行しません。そのスイープの入金がバウンスした場合、返された金額は意図的に裏付けのある
`accrued_plato_fee_ton` として再分類され、通常の手数料フラッシュパスを通じて再試行できるようになります。
通常の部分的な `FlushFees` 呼び出しは、少なくとも現在の公開プロトコル手数料（`0.010 GRAM`）でなければなりません。それより小さい金額は、
残っている発生分バケット全体である場合にのみ有効であり、割引されたダストも最終確定できます。

CapsuleHub は、すべてのプライベートおよびパブリックエントリーに対して `created_at = now()` を記録します。PWA は、そのコントラクトのタイムスタンプを順序付けと、範囲を限定したトランザクション履歴の検索に使用します。クライアントのヘッダータイムスタンプは、認証済みのペイロードメタデータのままであり、ディスカバリーの権威ではありません。コンパクトなエントリーメタデータは、設定された 1 年の保持ウィンドウの後にパーミッションレスにプルーニングできますが、ボディの可用性は、選択された TON プロバイダーのメッセージ履歴のカバレッジとユーザーのローカル暗号化キャッシュに依存します。

Vault の ATH 残高は、生の公式ウォレット残高をスキャンするのではなく、明示的な notify フローの会計処理を通じて入金されます。
サポートされている入金パスは、ユーザーの ATHWallet から Vault への `ATHTransferRequestWithNotify` です。公式の Vault ATHWallet への手動の通常 ATH
送金はサポートされておらず、入金アドレスとして表示したり、Vault の台帳への入金として扱ったりしてはなりません。Vault からの ATH 引き出しは、署名された外部 Vault コマンドです。その下流の ATHWallet の
デプロイ/送金/ACK リザーブは、ユーザーの内部 Vault GRAM 残高から支払われ、Vault は、受け取った認証済みの ACK/失敗/バウンス値のみを、
ローカル返金リザーブを差し引き、予約済みの内部値を上限として、返金します。

公開投稿とコメントは、暗号化のないプライベートカプセルではなく、別個のオープンなプロフィールです。これらは、コンパクトな
`PPH1` 公開ヘッダーセルと生の公開ボディセルを保存します。公開ボディのテキストと公開画像/アバターのバイトは、ユーザーに見えるボディ予算として、プライベートと同じ
1、2、4、8、16、または 32 KiB の公開カプセルサイズクラスを使用します。ヘッダーメタデータがそのボディ予算を減らすことは決してありません。公開投稿にはポスト量子オプションはありません。公開メッセージは `0.0337 GRAM` から始まり、
現在の正確な公開ベースの例は `0.0337 GRAM` に同じ
ネットワーク手数料サーチャージルールを加えたものです。`kind = 1` は公開投稿です。投稿の `flags` のビット 0 は、その投稿へのコメントを閉じます。`kind = 2` は、ヘッダーに
`parent_entry_id:uint64` と `parent_body_hash:uint256` を持つ 1 階層の公開コメントです。`kind = 3` は
公開画像投稿、`kind = 4` は公開画像コメント、`kind = 5` は公開ウォレットアバターメディアです。公開ヘッダーはさらに `stream_id:uint128`、
`part_index:uint16`、`part_count:uint16`、`media_format:u8` を持ちます。公開ヘッダーは、テキストには `media_format = 0` を、
WebP 画像/アバターパーツには `media_format = 1` を使用します。公開投稿、画像投稿、アバターのヘッダーはさらに
`profile_version:uint32` と `avatar_hash:uint256` を持ちます。ゼロはアバターポインターがないことを意味します。長い公開テキストまたは画像データは、各エントリーが
32 KiB までの最小適合公開サイズクラスを使用した後にのみ、複数のエントリーから再構築されます。公式 PWA は、選択された画像を分割前に、8 KiB
（`low`）、16 KiB（`medium`）、32 KiB（`good`、デフォルト）、または 64 KiB（`maximum`）の WebP ターゲットに圧縮します。編集/削除/リアクション/モデレーションやカウンターのレイヤーはありません。

ウォレットアバターは、オフチェーンアセットではなく、有料のプロフィール更新です。アバターのバイトは `kind = 5` の公開
CapsuleHub エントリーとして公開され、その後 `ProfileRegistry` が認証済みのウォレットポインターを記録します。
`version`、`avatar_hash`、最初の `avatar_entry_id`、`avatar_stream_id`、`avatar_part_count`、`media_format` です。読み手は、
署名済みのプライベートヘッダーまたは公開投稿ヘッダーからプロフィールポインターを解決し、対応する ProfileRegistry
レコードを検証し、CapsuleHub からアバターの公開エントリーを取得し、パーツをインデックス順に連結し、再構築された
WebP バイトのハッシュが `avatar_hash` になることを要求します。ローカルのアバターキャッシュは高速化のためだけのものです。真実の源は CapsuleHub と
ProfileRegistry です。

`header0_cell` は正確に 140 バイトを保存します。

```text
PH0B
|| version:u8
|| publish_kind:u8
|| size_class:u8
|| crypto_suite:u8
|| sender_key_id:32 bytes
|| recipient_key_id:32 bytes
|| sender_sign_pubkey:32 bytes
|| profile_version:uint32
|| avatar_hash:uint256
```

`header1_cell` は正確に 30 バイトを保存します。

```text
PH1B
|| version:u8
|| flags:u8 = 0
|| created_at_s:u32
|| expires_at_s:u32
|| client_nonce:16 bytes
```

`size_class + crypto_suite` はスイートを暗示します。`profile_version` と `avatar_hash` は送信時の送信者ウォレットアバターを指し、
ヘッダーハッシュと送信者署名によってカバーされます。`recipient_sign_pubkey` とスレッドハッシュは、
意図的に公開ヘッダーセルには保存されません。スレッド/グループ化データは、暗号化されたカプセルメタデータの内部に属します。

各暗号化ボディは次のように組み立てられます。

```text
PLB1 || version:u8 || suite:u8 || flags:u8 || reserved:u8
     || message_id:u128
     || aes_gcm_nonce:12 bytes
     || x25519_ephemeral_public:32 bytes
     || ml_kem_768_ciphertext:1088 bytes, only for hybrid-v1
     || aes_gcm_ciphertext_and_tag
```

AES-GCM の平文は、`size_class` によって選択される 1 つの固定カプセルスロットです。

```text
PCP1
|| version:u8
|| kind:u8
|| flags:u8
|| media_format:u8
|| stream_id:u128
|| part_index:u16
|| part_count:u16
|| content_len:u16
|| reserved:u16
|| payload[useful_size]
```

有用なコンテンツ領域は、選択された 1、2、4、8、16、または 32 KiB のプライベートカプセルクラスにパディングされます。1 バイト、500 バイト、または 1024 バイトの有用なテキストを持つメッセージは、1 KiB クラスでは同じ暗号化平文サイズになります。選択されたクラスを超えるメッセージは、暗号化された `stream_id`、`part_index`、`part_count` メタデータを持つ独立したカプセルに分割されます。1 つのカプセルが無関係なテキスト/画像ユニットを混在させることは決してありません。受信者は、独立したカプセルを元のメッセージへと組み立て直します。

コンテンツ種別:

- `1` テキスト: UTF-8 バイト、選択された有用なプライベートカプセルサイズまで。
- `2` 画像: 圧縮された WebP 画像バイト、選択された有用なプライベートカプセルサイズまで（`media_format = 1`）。
- `3` 支払いチェック: `asset:u8 || reserved:u8 || amount:u128 || intent_id:uint256 || secret32:uint256`。

支払いチェックのボディは、意図的に `tx`、アクティベーション時刻、または有効期限を含みません。受信者は `intent_id + secret32` によってクレームします。送信者がすでにチェックをキャンセルしていた場合、またはすでにクレームされていた場合、UI はチェックがすでにクレーム済みであるか、送信者によってキャンセルされたと表示します。

暗号化ボディは、エクスポート/共有のために次のようにラップされることがあります。

```text
PLC1 || version:u8 || suite:u8 || chunk_index:u8 || chunk_total:u8 || message_id:u128 || body_slice
```

最終的なカプセルボディでは、`chunk_total` は常に `1` です。`PLC1` はパッケージ/エクスポートのフレーミングのみです。受理された Vault -> CapsuleHub 公開トランザクションは、組み立てられた `PLB1` ボディバイトをスネークセルで運びます。CapsuleHub は、コンパクトな認証済みメタデータとハッシュのみを永続化します。

最終的なプライベート制限:

| スイート | カプセルあたりの有用な上限 | ボディバイト | エクスポートチャンクバイト |
| --- | ---: | ---: | ---: |
| `hybrid-v1` | 1 KiB | 2,228 バイト | 2,252 バイト |
| `hybrid-v1` | 2 KiB | 3,252 バイト | 3,276 バイト |
| `hybrid-v1` | 4 KiB | 5,300 バイト | 5,324 バイト |
| `hybrid-v1` | 8 KiB | 9,396 バイト | 9,420 バイト |
| `hybrid-v1` | 16 KiB | 17,588 バイト | 17,612 バイト |
| `hybrid-v1` | 32 KiB | 33,972 バイト | 33,996 バイト |

このレイアウトの正準のソースは `artifacts/PLATHO_CAPSULE_V1_FINAL_SPEC.md` です。

AES-GCM は 12 バイトのノンスと 16 バイトのタグを使用します。暗号文の長さは、平文の長さにタグを加えたものに等しくなります。

コンパクトなボディプレフィックス、`header0Hash`、`header1Hash` は、AES-GCM の追加認証データとして渡されます。バイナリルーティングヘッダー、スイート、ノンス、KEM 暗号文、チャンクバイト、または送信者署名を変更すると、検証または復号が失敗します。

復号の前に、クライアントは次の点も確認します。

- コンパクトなボディのスイートが `header0` と一致する;
- 受信者の鍵 id が `header0.recipientKeyId` と一致する;
- `hybrid-v1` のボディが 1088 バイトの ML-KEM 暗号文を確かに運んでいる;
- すべてのチャンクが同じスイート、メッセージ id、チャンク合計を持つ。

## 鍵導出

`hybrid-v1` の場合:

```text
x25519_secret = X25519(sender_ephemeral_secret, recipient_x25519_public)
mlkem_secret  = ML-KEM-768.Encapsulate(recipient_mlkem_public)
message_key   = HKDF-SHA-256(x25519_secret || mlkem_secret, compact_aad_hash)
```

平文は AES-256-GCM で暗号化されます。

実装は、低位数の公開鍵を受け入れることを避けるため、すべてゼロの X25519 共有秘密を拒否します。

## プライベート暗号化カプセル

クライアントは、公開の前に、コンパクトな暗号化ボディをプライベートカプセルでラップします。プライベートカプセルには次の内容があります。

- `header0`: 上記で説明した 140 バイトの `PH0B` バイナリルーティングヘッダー。
- `header1`: 上記で説明した 30 バイトの `PH1B` バイナリリプレイヘッダー。
- `body`: `platho.byte-layout.v1` のチャンクメタデータと base64url エンコードされたバイナリチャンク。
- `hashes`: `header0`、`header1`、暗号化されたボディバイトを含む正確なオンチェーンセルの TON `Cell.hash()` 値。
- `chainCells`: `ton-snake-byte-cell.v1` を使用した base64 BOC ペイロード。これらは、Vault -> CapsuleHub 公開トランザクションで受理され、`CapsuleHub` によって認証されるセルであり、オフチェーンポインターではありません。
- `senderSignature`: カプセル id と 3 つのハッシュすべてに対する Ed25519 署名。

`hybrid-v1` の場合、カプセルは CapsuleHub のハイブリッドプロフィールを使用します。

```text
size_class   in {1,2,4,8,16,32}
crypto_suite = 2
```

プライベートカプセルのドラフトは、署名済みの `PublishPrivateFromVaultBalance` 外部リクエストが Vault によって受理された後、Vault -> CapsuleHub の
`PublishPrivateFromVault` ボディにマッピングされます。

```text
header_0_hash = Cell.hash(header_0_cell)
header_1_hash = Cell.hash(header_1_cell)
body_hash     = Cell.hash(body_cell)
header_0_cell = snake-cell(header0 bytes)
header_1_cell = snake-cell(header1 bytes)
body_cell     = snake-cell(compact encrypted body bytes)
```

Vault の公開メッセージは `protocol_fee_paid` を運びます。Vault が ATH 裏付け価格の割引権限だからです。

有用なペイロード容量は、実際に `body_cell` にシリアライズされ、`CapsuleHub` によって受理される暗号化ボディバイトの容量です。対応する受理済みの公開トランザクションボディを伴わないハッシュは、読み取り可能なメッセージではありません。ローカル履歴はキャッシュのみであり、配信を定義しません。

Vault の外部公開署名では、hashes-ref の順序はコントラクト互換のままです。

```text
body_hash || header_0_hash || header_1_hash
```

コンパクトなボディは、AES-GCM の AAD を通じて `header0Hash` と `header1Hash` にバインドされます。ヘッダー、ボディチャンク、スイートメタデータ、送信者署名、カプセルコンテキスト、または BOC ペイロードセルを置き換えると、メッセージが受理される前に検証が失敗します。

## 配信の真実の源

受理されたプライベートメッセージは、コンパクトな CapsuleHub エントリーと、受理された公開トランザクションボディが運ぶ暗号化ペイロードセルです。PWA は、これらのセルを TON メッセージ履歴から取得し、復号の前に CapsuleHub ハッシュに対して検証します。本番 PWA は、手動の公開バンドルまたは暗号化カプセルの JSON パッケージ交換を公開しません。

公開メッセージング鍵は、`Vault` の鍵レコードに登録されます。送信者は、プライベートカプセルを暗号化する前に、受信者の鍵レコードを解決して検証しなければなりません。ローカルの暗号化履歴はデバイスキャッシュのみであり、配信を定義しません。

`.ath` ユーザー名の権限には 2 つの部分があります。`UsernameRegistry.get_name_record` は、名前が存在し、その名前に対応する
正確な `UsernameNFTItem` を指していることを証明します。次に、現在のオーナーがそのアイテムの状態から読み取られます。転送はアイテムの
オーナーを変更します。レジストリレコードは、名前からアイテムへのアンカーのままです。アイテムは、標準的な NFT データと TEP-64 オンチェーン
メタデータを、サーバーホストのメタデータ URI なしで、`name = <username>.ath` を含めて公開します。ユーザー名のバイトは意図的に
文字通りです。すべてのバイトが許可された `a-z`、`0-9`、`_`、`-` のセットに含まれ、長さが 4..16 である場合、先頭、末尾、連続、およびすべてが区切り文字の名前も有効です。保留中のミントが、
アイテム ACK の欠落の後に古くなった場合、`PrunePendingUsernameMint` は非破壊的です。それは古い状態であることを証明しますが、
保留状態を削除したり、返金義務を作成したりはしません。デプロイされたアイテムは、レジストリが有効な遅延 ACK または `ResendDeployedAck` を通じて
対応する名前レコードを最終確定した後にのみ、権威あるユーザー名になります。クライアントとインデクサーは、アイテムのみの
所有権主張を無視しなければならず、転送後にレジストリレコードのオーナーを現在のオーナーとして使用してはなりません。

24 単語の GRAM リカバリーフレーズは、唯一のユーザーシークレットです。PWA は、そのフレーズから GRAM ウォレット鍵とメッセージング用の暗号化/署名鍵を決定論的に導出します。したがって、プロフィールのエクスポート/インポートフローはリカバリーフレーズのみを扱います。別個のメッセージング鍵のバックアップはありません。

## リプレイと有効期限のポリシー

プライベートカプセルはデフォルトで 24 時間の TTL を持ち、30 日を上限とします。ライブ/オフチェーンのカプセルパッケージ検証は、次のものを拒否します。

- あまりにも未来に作成されたカプセル;
- 有効期限切れのカプセル;
- ポリシーの上限を超える TTL;
- 呼び出し元が提供するリプレイキャッシュ内の重複したカプセル id。

チェーン履歴のインポートは異なります。プライベートエントリーがすでに CapsuleHub によって受理されており、ボディが受理された TON トランザクション履歴または
ローカルの暗号化キャッシュから復元される場合、PWA はエントリーのハッシュ、ボディ/ヘッダーセル、および
復号を検証しますが、ヘッダーの有効期限が過去であるという理由だけで拒否することはありません。そうでなければ、保持されているチェーン履歴が
設計上読み取り不能になってしまうからです。

リプレイキャッシュはローカル状態です。本番クライアントは、IndexedDB または別のデバイスローカルストアでこれを裏付けることができます。バックエンドは不要です。

## バックエンド不要のルール

暗号化レイヤーは Platho バックエンドを必要としません。サーバーは静的ファイルをホストする場合がありますが、プライベート配信は `CapsuleHub` のチェーン状態と受理された公開トランザクションボディによって固定されます。コンパクトなエントリーがハッシュを証明し、ボディは依然として TON メッセージ履歴またはユーザーのローカル暗号化キャッシュから利用可能でなければなりません。サーバーは、平文、秘密鍵、またはサーバーサイドのセッションシークレットを決して受け取りません。

## Vault 登録ドラフト

クライアントは、検証済みの署名バンドルから `RegisterMessagingKeys` ドラフトを導出できます。

- `enc_pubkey`: uint256 としての 32 バイトの X25519 公開鍵。
- `sign_pubkey`: uint256 としての 32 バイトの Ed25519 署名公開鍵。
- `auth_pubkey`: uint256 としての別個の 32 バイトの Ed25519 Vault 認証公開鍵。
- `pq_kem_pubkey_hash`: ML-KEM-768 公開鍵の SHA-256。
- `pq_kem_pubkey_len`: `1184`。
- `pq_kem_pubkey`: 正確に 1184 の ML-KEM-768 公開鍵バイトを含む正準のスネークセル。
- `crypto_suite_mask`: `hybrid-v1` では `2`。

このドラフトは、組み込みの Platho ウォレットのアクティベーションフローによって送信されます。ウォレットが Vault でアクティベートされると、他のアクティベート済みユーザーは、その公開メッセージング鍵レコードを解決し、それに向けてプライベートカプセルを暗号化できます。

## Vault 鍵レコードのバインディング

ウォレットがオンチェーンで鍵を登録した後、クライアントは次のものを取得しなければなりません。

- ウォレットの `UserState.current_key_id`;
- ユーザー自身のアンロックされたウォレットについては、ローカルで導出された Vault 認証公開鍵と一致する `UserState.auth_pubkey`;
- その鍵 id に対する `VaultKeyRecordView`。

> **clean-17.** この章で説明する Vault コントラクトは clean-15 のものです。clean-17 では同じバインディングをウォレット自身の KeyShard コントラクト（`web/key-shard-ton-rpc-provider.mjs`）から読み取ります。そのアドレスはウォレットから導出されるため、レコードはそのウォレットが登録した鍵しか保持できません。プロバイダーブリッジ `web/vault-chain-provider.mjs` は Vault とともに削除されました。

```js
{
  async getUser(ownerWallet) {},
  async getKeyRecord(currentKeyId) {},
}
```

プロバイダーが設定されていない場合、Vault のバインディングは、ローカルのドラフトや UI のプレースホルダーを受け入れるのではなく、利用不可のままとなります。本番/静的デプロイメントは、TON API ミラーまたはライトクライアント互換のトランスポートを通じてデプロイされた Vault を読み取るプロバイダーを `globalThis.plathoVaultChainProvider` にインストールできます。

静的ランタイムには、本番プロバイダーのスケルトンとして `web/vault-ton-rpc-provider.mjs` が含まれています。これは、TON Center v3 互換のエンドポイント、またはホストバンドルによってインストールされたカスタムの `globalThis.plathoTonRpcTransport` をラップできます。現在の PWA は、組み込みのユーザー RPC 設定画面を公開していません。プロバイダーは次のことを行います。

- `get_user(owner)` のオーナーアドレスを `slice` BoC スタックアイテムとしてエンコードする;
- `get_key_record(current_key_id)` を数値スタックアイテムで呼び出す;
- ゲッタースタックを `VaultUserView` と `VaultKeyRecordView` にデコードする;
- RPC トランスポート、Vault アドレス、ゲッターレスポンス、または鍵レコードのバインディングが利用できない場合、フェイルクローズする。

クライアントサイドの検証器は、アクティブな Vault レコードが検証済みの署名バンドルと一致することを確認します。

- `owner_wallet` が組み込みの Platho ウォレットアドレスと一致する;
- `enc_pubkey` が X25519 公開鍵と一致する;
- `sign_pubkey` がバンドルの署名公開鍵と一致する;
- `pq_kem_pubkey`、`pq_kem_pubkey_hash`、`pq_kem_pubkey_len` が ML-KEM-768 素材と一致する;
- `crypto_suite_mask` がスイートと一致する;
- `revoked_lt` がゼロである;
- 任意の `current_key_id` が、取得されたレコード id を指している。

クライアントはオンチェーンの鍵 id を独自に生成しません。Vault は、オーナーアドレス、鍵世代、鍵フィールド、PQ 長、スイートからそれを計算します。代わりに、クライアントは取得したレコードを検証します。

## 永続的リプレイストア

PWA は、利用可能な場合、プライベートカプセルのリプレイ保護に IndexedDB を使用し、メモリのフォールバックを備えています。ストアは、カプセルの有効期限までカプセル id を保持し、有効期限切れのエントリーをローカルでプルーニングします。これはデバイスローカルの状態であり、サーバーを必要としません。

## 暗号化されたローカルメッセージ履歴

PWA には、デバイスローカルの暗号化メッセージ履歴ストアもあります。これは、IndexedDB に保存された抽出不可能な WebCrypto の AES-GCM-256 鍵を使用し、すべてのメッセージボディを認証済みの暗号文として保存します。レコードヘッダーは、ローカルクエリメタデータのみを保持します。id、スレッド id、タイムスタンプ、方向、任意のカプセル id です。

ヘッダーは、AES-GCM の追加認証データとしてバインドされます。スレッド id、タイムスタンプ、方向、カプセル id、ノンス、または暗号文を変更すると、レコードを開けなくなります。IndexedDB が利用できない場合、アプリはそのセッションについて暗号化されたインメモリ履歴にフォールバックし、永続的なブラウザストレージへの平文の書き込みを避けます。

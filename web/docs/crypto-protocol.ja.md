# Platho メッセージ暗号プロトコル

このドキュメントでは、静的な PWA プロトタイプによって実装されているクライアントサイドのメッセージ暗号化について説明します。

## スイート

| スイート | コントラクト値 | 目的 |
| --- | ---: | --- |
| `hybrid-v1` | `2` | X25519 と ML-KEM-768 と AES-GCM を使用するプライベートメッセージ。 |

V1 のプライベート公開は `CRYPTO_SUITE_HYBRID = 2` のみを受け入れます。

## 鍵バンドル

PWA によって作成またはインポートされるすべての 24 語の GRAM リカバリーフレーズは、暗号化鍵ペアと Ed25519 署名鍵を備えたメッセージング用アイデンティティを決定論的に導出します。公開暗号化鍵素材は公開鍵バンドルとしてエクスポートされます。

- `keyId`: 公開鍵素材に対する SHA-256 ベースの識別子。
- `x25519PublicKey`: 32 バイトの古典的な ECDH 公開鍵。
- `mlKem768PublicKey`: `hybrid-v1` 用の 1184 バイトの ML-KEM-768 公開鍵。
- `mlKem768PublicKeyHash`: ML-KEM-768 公開鍵の SHA-256。
- `mlKem768PublicKeyLen`: `hybrid-v1` では常に `1184`。

PWA は暗号化の前に `keyId`、`mlKem768PublicKeyHash`、`mlKem768PublicKeyLen` を再計算します。id、スイート、コントラクトスイート、ハッシュ、または長さが一致しないと主張するバンドルは拒否されます。

受信者の検索は、オンチェーンの `enc_pubkey`、`sign_pubkey`、およびアクティブな Vault 鍵レコードに保存されているオンチェーンの完全な `pq_kem_pubkey` セルによって定義されます。ハッシュと長さはコンパクトなバインディングフィールドとしてレコード内に残りますが、別のクライアントが実際に `hybrid-v1` カプセルを暗号化できるようにするのは完全な ML-KEM-768 公開鍵です。

## 署名付きバンドル

PWA は署名付き公開鍵バンドルをエクスポートできます。署名対象のペイロードには次のものが含まれます。

- プロトコルドメイン `PLATHO.MESSAGING.KEY_BUNDLE.SIGNATURE.V1`。
- 発行タイムスタンプおよびオプションの有効期限タイムスタンプ。
- オプションの所有者ウォレットと Vault アドレスのプレースホルダー。
- 公開暗号化バンドル。
- 32 バイトの Ed25519 署名公開鍵。

署名は安定した JSON ペイロードを対象としており、バンドルが信頼される前に検証されます。これにより、ローカルでのバンドルの静かな改ざんが防止され、Vault が `KeyRecord` に保存する正確な `sign_pubkey` がクライアントに与えられます。

PWA の `keyId` はクライアントバンドルの識別子です。これは、所有者アドレス、鍵世代、署名鍵、暗号化鍵、PQ ハッシュ、PQ 長、暗号スイートからオンチェーンで計算される Vault コントラクトの `current_key_id` を置き換えるものではありません。本番クライアントは、ウォレットアイデンティティとして信頼する前に、バンドルを Vault 鍵レコードと照合して検証する必要があります。

署名付きバンドルはメッセージング鍵の自己署名です。ウォレットの所有権は Vault のアクティベーションによってアンカーされます。すなわち、組み込みの Platho ウォレットが `RegisterMessagingKeys` を送信し、その後の `ReplaceMessagingKeys` ローテーションは Vault 認証署名済みの外部メッセージであり、受信者はそのウォレットのアクティブなオンチェーン鍵レコードに対して署名付きバンドルを検証します。

## ウォレットの所有権

本番の PWA は外部ウォレットコネクターを使用しません。ユーザーは通常の 24 語の GRAM リカバリーフレーズを作成またはインポートし、PWA は
そのフレーズから GRAM ウォレット鍵、別個の Vault 認証鍵、およびメッセージングの暗号化/署名鍵を決定論的に導出します。Vault
のアクティベーションが所有権のアンカーです。すなわち、組み込みウォレットが、オンチェーン鍵レコードを所有するのと同じウォレットから `RegisterMessagingKeys` に署名して送信します。
`ReplaceMessagingKeys` は公開の受信/メッセージング鍵レコードのみをローテーションし、Vault 認証鍵はローテーションしません。

受信者は、そのウォレットのアクティブな Vault 鍵レコードと照合した後にのみメッセージングバンドルを信頼します。

- レコードの所有者が期待されるウォレットであること。
- `enc_pubkey` と `sign_pubkey` が署名付きバンドルと一致すること。
- ハイブリッドレコードは、そのハッシュだけでなく完全な `pq_kem_pubkey` セルを公開すること。
- デコードされた ML-KEM-768 鍵バイトが `pq_kem_pubkey_hash` にハッシュされること。
- アクティブな `current_key_id` が検証済みの鍵レコードを指していること。

プロフィールのエクスポート/インポートフローは 24 語の GRAM リカバリーフレーズを扱います。最終版 v1 には、別個のメッセージング鍵バックアップも
外部ウォレット接続モードもありません。

## コンパクトなバイトレイアウト

プライベートカプセルのオンチェーンセルは、最終版の `platho.byte-layout.v1` バイナリレイアウトを使用します。PWA はエクスポート/共有 UI のためにカプセルを JSON でラップすることがありますが、プロトコルのペイロードはバイナリバイトであり、JSON でもオフチェーンポインタでもありません。`CapsuleHub` はコンパクトな認証済みヘッダー/インデックスとボディハッシュを保存します。暗号化されたボディセルは、受理された公開トランザクションのボディ内に残り、TON メッセージ履歴から再構築され、その後、保存されたハッシュと照合して検証されます。

すべての公開は、Vault 残高で資金提供された署名付き外部メッセージとして Vault を経由します。ユーザーはまず内部の
Vault GRAM 残高に資金を投入し、その後 PWA はアクティブな `auth_pubkey` で公開リクエストに署名します。リレーヤーは、ウォレット鍵やメッセージング署名鍵を保持せずに
外部メッセージを送信できます。署名対象のペイロードは、所有者、ノンス、最大課金額、ペイロードの前に、`VPB1`、
`deployment_manifest_hash`、対象の Vault アドレス、および公開種別によってドメイン分離されています。
CapsuleHub が実際に ACK またはバウンスで返送する GRAM 値は、追跡されている保留中の公開返金額を上限として、ユーザーの内部 Vault GRAM
残高にクレジットされます。Vault 残高またはチェーンアクセスが利用できない場合、
PWA はフェイルクローズし、公開アクションを公開してはなりません。

`auth_pubkey` が Vault 残高の支出を認可するため、ローカルのメッセージング署名鍵単独が侵害されても、
Vault の公開、支払い確認、ユーザー名、またはアバターのアクションは認可されません。メッセージング署名鍵の侵害はメッセージレベルの
アイデンティティ署名に影響を与える可能性が依然としてあるため、鍵の置き換えは、将来の受信暗号化チェックに対して古い公開受信鍵レコードを失効させます。

PWA のメッセージ価格はカプセル単位です。現行の準備金で ATH 割引がない場合、正確な標準的な例では、1 KiB のパブリックエントリは `0.0337 GRAM` から、`hybrid-v1` の 1 KiB のプライベート
カプセルは `0.0347 GRAM` からです。より大きなパブリックまたはプライベートのサイズクラスは、標準クラスに応じてより多くの費用がかかります。これには、
Platho プロトコル手数料 `0.01 GRAM` 全額、CapsuleHub のコンパクトインデックス保存の元本、Vault のローカル実行準備金、および
予想される ACK 返金が含まれます。別途、PWA の保守的な手数料見積もりが、含まれるネットワーク手数料
許容額 `0.005 GRAM` を上回る場合、
丸めた超過分を割増料金として追加します。コントラクト呼び出しは依然としてその標準的な
必要値から開始されます。すなわち、Vault の公開は `maxCharge = canonical_max_charge + surcharge` を送信します。最終版 v1 では CapsuleHub にユーザーが直接
公開するための ABI はありません。すべての公開は Vault -> CapsuleHub です。ATH 割引は、Vault アクティビティエアドロップが
15,000,000 ATH を配布した後にのみ適用されます。そのゲートより前は、メッセージプロトコル手数料は `0.01 GRAM` 全額の手数料を使用します。PWA は、署名の前に、選択されたコンテンツサイズについて最終的な
ホールドと正味コストを表示しなければなりません。

割増料金は署名付きのネットワーク/ストレージ安全マージンであり、返金可能な手数料バケットではありません。CapsuleHub は、
添付された値が少なくとも標準的な必要値である場合に Vault の公開を受け入れますが、公開が成功した ACK は固定の
公開 ACK 準備金 `30,000,000` nanotons (`0.030 GRAM`) のみを返します。Vault がその ACK を処理した後、ユーザーには内部 Vault GRAM 残高でおおよそ
`25,800,000` nanotons がクレジットされます。標準的な必要値を超える署名付き割増料金は、
ネットワーク/ストレージ準備金の超過分として CapsuleHub に残ります。これは Vault に返送されず、
`accrued_plato_fee_ton` としてもカウントされません。

CapsuleHub は、`accrued_plato_fee_ton + max(100 GRAM, 1.25 * live_index_1y_storage_reserve)` に等しい生の GRAM 準備金を保護します。
ライブ準備金は、履歴上の `latest_id` カウンターではなく、プルーニングされていないプライベート/パブリックエントリカウンターを使用します。別個の
パーミッションレスな `SweepExcessReserve` 呼び出しは、その保護された金額を超える余剰分のみを `DepositProtocolFee` として FeeAccumulator に移動できます。
そこでは通常のトレジャリー/バイバック分割に従います。通常のメッセージ送信はこの
スイープを実行しません。そのスイープデポジットがバウンスした場合、返却された金額は意図的にバックされた
`accrued_plato_fee_ton` として再分類され、通常の手数料フラッシュパスを通じて再試行できるようになります。
通常の部分的な `FlushFees` 呼び出しは、少なくとも現行のパブリックプロトコル手数料 (`0.010 GRAM`) でなければなりません。より少ない金額は、
残っている累積バケット全体である場合にのみ有効であり、これにより割引されたダストも確定できます。

CapsuleHub は、すべてのプライベートおよびパブリックのエントリについて `created_at = now()` を記録します。PWA は、順序付けと限定的なトランザクション履歴の検索のために、そのコントラクトのタイムスタンプを使用します。クライアントヘッダーのタイムスタンプは認証済みのペイロードメタデータのままであり、ディスカバリーの権威ではありません。コンパクトなエントリメタデータは、設定された 1 年間の保持期間の後にパーミッションレスにプルーニングできますが、ボディの可用性は、選択された TON プロバイダーのメッセージ履歴のカバレッジとユーザーのローカルの暗号化キャッシュに依存します。

Vault の ATH 残高は、生の公式ウォレット残高をスキャンするのではなく、明示的な notify フローの会計処理を通じてクレジットされます。
サポートされているデポジットパスは、ユーザーの ATHWallet から Vault への `ATHTransferRequestWithNotify` です。公式の Vault ATHWallet への手動の通常の ATH
転送はサポートされておらず、デポジットアドレスとして表示したり、
Vault の台帳クレジットとして扱ったりしてはなりません。Vault からの ATH の引き出しは、署名付きの外部 Vault コマンドです。その下流の ATHWallet
のデプロイ/転送/ACK 準備金は、ユーザーの内部 Vault GRAM 残高から支払われ、Vault は、
受け取った認証済みの ACK/失敗/バウンス値から、ローカルの返金準備金を差し引き、予約された内部値を上限として、クレジットバックのみを行います。

パブリックの投稿とコメントは、暗号化のないプライベートカプセルではなく、別個のオープンなプロフィールです。これらは、コンパクトな
`PPH1` パブリックヘッダーセルと生のパブリックボディセルを保存します。パブリックのボディテキストとパブリックの画像/アバターバイトは、ユーザーに見えるボディ予算と同じ
1、2、4、8、16、または 32 KiB のパブリックカプセルサイズクラスを使用します。ヘッダーメタデータがその
ボディ予算を削減することはありません。パブリック投稿にはポスト量子オプションはありません。パブリックのコピーは `from 0.0337 GRAM` の製品ラベルを使用し、
現行の正確なパブリックのベース例は `0.0337 GRAM` に同じ
ネットワーク手数料の割増料金ルールを加えたものです。`kind = 1` はパブリック投稿です。投稿の `flags` のビット 0 は、その投稿のコメントを閉じます。`kind = 2` は
ヘッダーに `parent_entry_id:uint64` と `parent_body_hash:uint256` を持つ 1 レベルのパブリックコメントです。`kind = 3` は
パブリック画像投稿、`kind = 4` はパブリック画像コメント、`kind = 5` はパブリックのウォレットアバターメディアです。パブリックヘッダーは、
`stream_id:uint128`、`part_index:uint16`、`part_count:uint16`、および `media_format:u8` も持ちます。パブリック v1 は、テキストには `media_format = 0` を、
WebP 画像/アバターパートには `media_format = 1` を使用します。パブリックの投稿、画像投稿、アバターのヘッダーは、
`profile_version:uint32` と `avatar_hash:uint256` も持ちます。ゼロはアバターポインタがないことを意味します。長いパブリックテキストまたは画像データは、各エントリが 32 KiB までの最小の適合するパブリックサイズクラスを使用した後にのみ、
複数のエントリから再構築されます。公式の PWA は、分割する前に、選択された画像を 8 KiB
(`low`)、16 KiB (`medium`)、32 KiB (`good`、デフォルト)、または 64 KiB (`maximum`) の WebP ターゲットに圧縮します。v1 には編集/削除/リアクション/モデレーションやカウンター層はありません。

ウォレットアバターは、オフチェーンアセットではなく、有料のプロフィール更新です。アバターバイトは `kind = 5` のパブリック
CapsuleHub エントリとして公開され、その後 `ProfileRegistry` が認証済みのウォレットポインタを記録します。すなわち、
`version`、`avatar_hash`、最初の `avatar_entry_id`、`avatar_stream_id`、`avatar_part_count`、および `media_format` です。読者は、
署名付きのプライベートヘッダーまたはパブリック投稿ヘッダーからプロフィールポインタを解決し、一致する ProfileRegistry
レコードを検証し、CapsuleHub からアバターのパブリックエントリを取得し、パートをインデックス順に連結し、再構築された
WebP バイトが `avatar_hash` にハッシュされることを要求します。ローカルのアバターキャッシュは高速化のためだけのものです。信頼できる情報源は CapsuleHub と
ProfileRegistry です。

`header0_cell` は正確に 140 バイトを保存します。

```text
PH0B
|| version:u8
|| publish_kind:u8
|| size_class:u8
|| crypto_suite:u8
|| sender_key_id:32 bytes
|| recipient_key_id:32 bytes
|| sender_sign_pubkey:32 bytes
|| profile_version:uint32
|| avatar_hash:uint256
```

`header1_cell` は正確に 30 バイトを保存します。

```text
PH1B
|| version:u8
|| flags:u8 = 0
|| created_at_s:u32
|| expires_at_s:u32
|| client_nonce:16 bytes
```

`size_class + crypto_suite` はスイートを暗示します。`profile_version` と `avatar_hash` は、送信時点での送信者ウォレットアバターを指し、
ヘッダーハッシュと送信者署名によってカバーされます。`recipient_sign_pubkey` とスレッドハッシュは、
意図的にパブリックヘッダーセルに保存されません。スレッド/グループ化データは、暗号化されたカプセルメタデータの内部に属します。

各暗号化ボディは次のように組み立てられます。

```text
PLB1 || version:u8 || suite:u8 || flags:u8 || reserved:u8
     || message_id:u128
     || aes_gcm_nonce:12 bytes
     || x25519_ephemeral_public:32 bytes
     || ml_kem_768_ciphertext:1088 bytes, only for hybrid-v1
     || aes_gcm_ciphertext_and_tag
```

AES-GCM の平文は、`size_class` によって選択される 1 つの固定カプセルスロットです。

```text
PCP1
|| version:u8
|| kind:u8
|| flags:u8
|| media_format:u8
|| stream_id:u128
|| part_index:u16
|| part_count:u16
|| content_len:u16
|| reserved:u16
|| payload[useful_size]
```

有用なコンテンツ領域は、選択された 1、2、4、8、16、または 32 KiB のプライベートカプセルクラスにパディングされます。1 バイト、500 バイト、または 1024 バイトの有用なテキストを持つメッセージは、1 KiB クラスにおいて同じ暗号化された平文サイズを持ちます。選択されたクラスを超えるメッセージは、暗号化された `stream_id`、`part_index`、`part_count` メタデータを持つ独立したカプセルに分割されます。1 つのカプセルが無関係なテキスト/画像ユニットを混在させることは決してありません。受信者は独立したカプセルを元のメッセージに組み立て直します。

コンテンツの種類:

- `1` テキスト: UTF-8 バイト、選択された有用なプライベートカプセルサイズまで。
- `2` 画像: 圧縮された画像バイト、選択された有用なプライベートカプセルサイズまで。`media_format` は `1` WebP、`2` AVIF、`3` JPEG、または `4` PNG。
- `3` 支払い確認: `asset:u8 || reserved:u8 || amount:u128 || intent_id:uint256 || secret32:uint256`。

支払い確認ボディは、意図的に `tx`、アクティベーション時刻、または有効期限を含みません。受信者は `intent_id + secret32` によって請求します。送信者がすでに確認をキャンセルしたか、すでに請求されている場合、UI は、その確認が送信者によってすでに請求またはキャンセルされたと表示します。

暗号化ボディは、エクスポート/共有のために次のようにラップされることがあります。

```text
PLC1 || version:u8 || suite:u8 || chunk_index:u8 || chunk_total:u8 || message_id:u128 || body_slice
```

最終カプセルボディでは、`chunk_total` は常に `1` です。`PLC1` はパッケージ/エクスポートのフレーミングのみです。受理された Vault -> CapsuleHub の公開トランザクションは、組み立てられた `PLB1` ボディバイトをスネークセルで運びます。CapsuleHub は、コンパクトな認証済みメタデータとハッシュのみを永続化します。

最終版 v1 のプライベート制限:

| スイート | カプセルあたりの有用な上限 | ボディバイト | エクスポートチャンクバイト |
| --- | ---: | ---: | ---: |
| `hybrid-v1` | 1 KiB | 2,228 bytes | 2,252 bytes |
| `hybrid-v1` | 2 KiB | 3,252 bytes | 3,276 bytes |
| `hybrid-v1` | 4 KiB | 5,300 bytes | 5,324 bytes |
| `hybrid-v1` | 8 KiB | 9,396 bytes | 9,420 bytes |
| `hybrid-v1` | 16 KiB | 17,588 bytes | 17,612 bytes |
| `hybrid-v1` | 32 KiB | 33,972 bytes | 33,996 bytes |

このレイアウトの標準的な情報源は `artifacts/PLATHO_CAPSULE_V1_FINAL_SPEC.md` です。

AES-GCM は 12 バイトのノンスと 16 バイトのタグを使用します。暗号文の長さは、平文の長さにタグを加えたものに等しくなります。

コンパクトなボディプレフィックス、`header0Hash`、および `header1Hash` は、AES-GCM の追加認証データとして渡されます。バイナリのルーティングヘッダー、スイート、ノンス、KEM 暗号文、チャンクバイト、または送信者署名を変更すると、検証または復号が失敗します。

復号の前に、クライアントは次のこともチェックします。

- コンパクトなボディのスイートが `header0` と一致すること。
- 受信者の鍵 id が `header0.recipientKeyId` と一致すること。
- `hybrid-v1` のボディが 1088 バイトの ML-KEM 暗号文を運んでいること。
- すべてのチャンクが同じスイート、メッセージ id、およびチャンク合計を持つこと。

## 鍵導出

`hybrid-v1` の場合:

```text
x25519_secret = X25519(sender_ephemeral_secret, recipient_x25519_public)
mlkem_secret  = ML-KEM-768.Encapsulate(recipient_mlkem_public)
message_key   = HKDF-SHA-256(x25519_secret || mlkem_secret, compact_aad_hash)
```

平文は AES-256-GCM で暗号化されます。

実装は、低位数の公開鍵を受け入れることを避けるため、すべてゼロの X25519 共有秘密を拒否します。

## プライベート暗号化カプセル

クライアントは、公開の前にコンパクトな暗号化ボディをプライベートカプセルでラップします。プライベートカプセルは次のものを持ちます。

- `header0`: 上記の 140 バイトの `PH0B` バイナリルーティングヘッダー。
- `header1`: 上記の 30 バイトの `PH1B` バイナリリプレイヘッダー。
- `body`: `platho.byte-layout.v1` のチャンクメタデータと base64url エンコードされたバイナリチャンク。
- `hashes`: `header0`、`header1`、および暗号化ボディバイトを含む正確なオンチェーンセルに対する TON の `Cell.hash()` 値。
- `chainCells`: `ton-snake-byte-cell.v1` を使用する base64 の BOC ペイロード。これらは Vault -> CapsuleHub の公開トランザクションで受理され、`CapsuleHub` によって認証されるセルであり、オフチェーンポインタではありません。
- `senderSignature`: カプセル id と 3 つすべてのハッシュに対する Ed25519 署名。

`hybrid-v1` の場合、カプセルは CapsuleHub のハイブリッドプロフィールを使用します。

```text
size_class   in {1,2,4,8,16,32}
crypto_suite = 2
```

プライベートカプセルのドラフトは、署名付きの
`PublishPrivateFromVaultBalance` 外部リクエストが Vault によって受理された後、Vault -> CapsuleHub の `PublishPrivateFromVault` ボディにマッピングされます。

```text
header_0_hash = Cell.hash(header_0_cell)
header_1_hash = Cell.hash(header_1_cell)
body_hash     = Cell.hash(body_cell)
header_0_cell = snake-cell(header0 bytes)
header_1_cell = snake-cell(header1 bytes)
body_cell     = snake-cell(compact encrypted body bytes)
```

Vault の公開メッセージは `protocol_fee_paid` を運びます。なぜなら、Vault は ATH ベースの価格設定の割引権限だからです。

有用なペイロード容量は、実際に `body_cell` にシリアライズされ、`CapsuleHub` によって受理される暗号化ボディバイトの容量です。一致する受理された公開トランザクションのボディを持たないハッシュは、読み取り可能な v1 メッセージではありません。ローカル履歴はキャッシュのみです。それは v1 における配信を定義しません。

Vault の外部公開署名の場合、ハッシュ参照の順序はコントラクト互換のままです。

```text
body_hash || header_0_hash || header_1_hash
```

コンパクトなボディは、AES-GCM の AAD を通じて `header0Hash` と `header1Hash` にバインドされます。ヘッダー、ボディチャンク、スイートメタデータ、送信者署名、カプセルのコンテキスト、または BOC ペイロードセルを置き換えると、メッセージが受理される前に検証が失敗します。

## 配信の信頼できる情報源

受理された v1 のプライベートメッセージは、コンパクトな CapsuleHub エントリと、受理された公開トランザクションのボディによって運ばれる暗号化ペイロードセルです。PWA は、TON メッセージ履歴からそれらのセルを取得し、復号する前に CapsuleHub のハッシュと照合して検証します。本番の PWA は、手動のパブリックバンドルまたは暗号化カプセルの JSON パッケージ交換を公開しません。

パブリックのメッセージング鍵は `Vault` 鍵レコードに登録されます。送信者は、プライベートカプセルを暗号化する前に、受信者の鍵レコードを解決して検証しなければなりません。ローカルの暗号化履歴はデバイスキャッシュのみです。それは配信を定義しません。

`.ath` ユーザー名の権限には 2 つの部分があります。`UsernameRegistry.get_name_record` は、名前が存在し、その名前に対応する正確な
`UsernameNFTItem` を指すことを証明します。現行の所有者は、そのアイテムの状態から読み取られます。転送はアイテムの
所有者を変更します。レジストリレコードは、名前からアイテムへのアンカーのままです。アイテムは、標準的な NFT データと TEP-64 のオンチェーン
メタデータを公開します。これには、サーバーホスト型のメタデータ URI なしで `name = <username>.ath` が含まれます。V1 のユーザー名バイトは意図的に
リテラルです。すなわち、すべてのバイトが許可された `a-z`、`0-9`、`_`、`-` のセットにあり、長さが 4..16 である場合、先頭、末尾、連続、およびすべて区切り文字の名前は有効です。保留中のミントが
アイテム ACK の欠落後に古くなった場合、`PrunePendingUsernameMint` は v1 では非破壊的です。すなわち、古い状態を証明しますが、
保留中の状態を削除したり、返金債務を作成したりはしません。デプロイされたアイテムは、レジストリが有効な遅延 ACK または `ResendDeployedAck` を通じて
一致する名前レコードを確定した後にのみ、権威あるユーザー名になります。クライアントとインデクサーは、アイテムのみの
所有権の主張を無視しなければならず、転送後にレジストリレコードの所有者を現行の所有者として使用してはなりません。

24 語の GRAM リカバリーフレーズは、単一のユーザー秘密です。PWA は、そのフレーズから GRAM ウォレット鍵とメッセージングの暗号化/署名鍵を決定論的に導出します。したがって、プロフィールのエクスポート/インポートフローはリカバリーフレーズのみを扱います。別個のメッセージング鍵バックアップはありません。

## リプレイと有効期限のポリシー

プライベートカプセルはデフォルトで 24 時間の TTL を持ち、30 日を上限とします。ライブ/オフチェーンのカプセルパッケージ検証は、次のものを拒否します。

- あまりにも未来に作成されたカプセル。
- 期限切れのカプセル。
- ポリシー上限を超える TTL。
- 呼び出し元が提供したリプレイキャッシュ内で重複したカプセル id。

チェーン履歴のインポートは異なります。プライベートエントリがすでに CapsuleHub によって受理され、ボディが
受理された TON トランザクション履歴またはローカルの暗号化キャッシュから復元される場合、PWA はエントリのハッシュ、ボディ/ヘッダーセル、および
復号を検証しますが、ヘッダーの有効期限が過去にあるという理由だけでは拒否しません。そうでなければ、保持されたチェーン履歴が
設計上、読み取り不能になってしまうからです。

リプレイキャッシュはローカル状態です。本番クライアントは、IndexedDB または別のデバイスローカルストアでそれをバックできます。バックエンドは不要です。

## バックエンド不要ルール

暗号化層は Platho バックエンドを必要としません。サーバーは静的ファイルをホストしてもよいですが、プライベート配信は `CapsuleHub` のチェーン状態と受理された公開トランザクションのボディによってアンカーされます。すなわち、コンパクトなエントリがハッシュを証明し、ボディは依然として TON メッセージ履歴またはユーザーのローカルの暗号化キャッシュから利用可能でなければなりません。サーバーは、平文、秘密鍵、またはサーバーサイドのセッション秘密を決して受け取りません。

## Vault 登録ドラフト

クライアントは、検証済みの署名付きバンドルから `RegisterMessagingKeys` ドラフトを導出できます。

- `enc_pubkey`: uint256 としての 32 バイトの X25519 公開鍵。
- `sign_pubkey`: uint256 としての 32 バイトの Ed25519 署名公開鍵。
- `auth_pubkey`: uint256 としての別個の 32 バイトの Ed25519 Vault 認証公開鍵。
- `pq_kem_pubkey_hash`: ML-KEM-768 公開鍵の SHA-256。
- `pq_kem_pubkey_len`: `1184`。
- `pq_kem_pubkey`: 正確に 1184 の ML-KEM-768 公開鍵バイトを含む標準的なスネークセル。
- `crypto_suite_mask`: `hybrid-v1` の場合は `2`。

このドラフトは、組み込みの Platho ウォレットのアクティベーションフローによって送信されます。ウォレットが Vault でアクティベートされると、他のアクティベート済みユーザーは、その公開メッセージング鍵レコードを解決し、それに対してプライベートカプセルを暗号化できます。

## Vault 鍵レコードのバインディング

ウォレットがオンチェーンで鍵を登録した後、クライアントは次のものを取得しなければなりません。

- ウォレットの `UserState.current_key_id`。
- ユーザー自身のアンロック済みウォレットについては、ローカルで導出された Vault 認証公開鍵に一致する `UserState.auth_pubkey`。
- その鍵 id に対する `VaultKeyRecordView`。

PWA は、これを `web/vault-chain-provider.mjs` 内のフェイルクローズのプロバイダーブリッジとして公開します。ブリッジは、次を持つプロバイダーを期待します。

```js
{
  async getUser(ownerWallet) {},
  async getKeyRecord(currentKeyId) {},
}
```

プロバイダーが構成されていない場合、Vault のバインディングは、ローカルドラフトや UI プレースホルダーを受け入れるのではなく、利用不可のままになります。本番/静的デプロイでは、TON API ミラーまたはライトクライアント互換のトランスポートを通じて、デプロイ済みの Vault を読み取るプロバイダーを `globalThis.plathoVaultChainProvider` にインストールできます。

静的ランタイムには、本番プロバイダーのスケルトンとして `web/vault-ton-rpc-provider.mjs` が含まれます。これは、TON Center v3 互換のエンドポイント、またはホストバンドルによってインストールされたカスタムの `globalThis.plathoTonRpcTransport` をラップできます。現行の PWA は、組み込みのユーザー RPC 設定画面を公開しません。ドキュメントがユーザー選択の RPC を主張する場合、その UI が存在しなければなりません。プロバイダーは:

- `get_user(owner)` の所有者アドレスを `slice` BoC スタックアイテムとしてエンコードします。
- 数値のスタックアイテムで `get_key_record(current_key_id)` を呼び出します。
- ゲッタースタックを `VaultUserView` と `VaultKeyRecordView` にデコードします。
- RPC トランスポート、Vault アドレス、ゲッター応答、または鍵レコードのバインディングが利用不可の場合、フェイルクローズします。

クライアントサイドの検証器は、アクティブな Vault レコードが検証済みの署名付きバンドルと一致することをチェックします。

- `owner_wallet` が組み込みの Platho ウォレットアドレスと一致すること。
- `enc_pubkey` が X25519 公開鍵と一致すること。
- `sign_pubkey` がバンドルの署名公開鍵と一致すること。
- `pq_kem_pubkey`、`pq_kem_pubkey_hash`、および `pq_kem_pubkey_len` が ML-KEM-768 素材と一致すること。
- `crypto_suite_mask` がスイートと一致すること。
- `revoked_lt` がゼロであること。
- オプションの `current_key_id` が取得されたレコード id を指していること。

クライアントはオンチェーンの鍵 id を捏造しません。Vault は、所有者アドレス、鍵世代、鍵フィールド、PQ 長、およびスイートからそれを計算します。代わりに、クライアントは取得されたレコードを検証します。

## 耐久性のあるリプレイストア

PWA は、利用可能な場合にプライベートカプセルのリプレイ保護のために IndexedDB を使用し、メモリフォールバックを備えています。ストアは、カプセルの有効期限までカプセル id を保持し、期限切れのエントリをローカルでプルーニングします。これはデバイスローカルの状態であり、サーバーを必要としません。

## 暗号化されたローカルメッセージ履歴

PWA には、デバイスローカルの暗号化メッセージ履歴ストアもあります。これは、IndexedDB に保存された抽出不可能な WebCrypto AES-GCM-256 鍵を使用し、すべてのメッセージボディを認証済みの暗号文として保存します。レコードヘッダーは、ローカルクエリのメタデータのみを保持します。すなわち、id、スレッド id、タイムスタンプ、方向、およびオプションのカプセル id です。

ヘッダーは AES-GCM の追加認証データとしてバインドされます。スレッド id、タイムスタンプ、方向、カプセル id、ノンス、または暗号文を変更すると、レコードが開けなくなります。IndexedDB が利用不可の場合、アプリはそのセッションについて暗号化されたインメモリ履歴にフォールバックし、平文を永続的なブラウザストレージに書き込むことを避けます。

## 本番ステータス

メインネットのリリースパスは、組み込みの GRAM ウォレット導出、Vault アンカーのメッセージング鍵、署名付きバンドルの検証、フェイルクローズの Vault チェーンバインディング、プライベートカプセルのセルハッシュ、送信者署名、耐久性のあるリプレイストレージ、暗号化されたローカルメッセージ履歴、およびリカバリーフレーズのエクスポート/インポートを使用します。本番デプロイでは、PWA の構成を検証済みのメインネットマニフェストと承認された TON RPC プロバイダーに固定したままにしなければなりません。長期的な保証のために、独立した暗号レビューは引き続き推奨されます。

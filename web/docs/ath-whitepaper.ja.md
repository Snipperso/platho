# ATH ホワイトペーパー

## Platho プロトコルトークン

ATH は Platho のユーティリティトークンです。アクティビティ報酬、エアドロップ後のプロトコル手数料割引、`.ath` ユーザーネーム、プロフィールアバターの更新、マーケット安定化販売、バイバック、およびバーンに使用されます。

ATH は管理用トークンではありません。残高の書き換え、オペレーションの一時停止、新規供給のミント、ユーザー所有権ルールの変更を行う権限を付与するものではありません。その役割は、アプリケーション経済を動かし、Platho の利用状況をオンチェーンの会計と結びつけることにあります。

本ドキュメントでは、Platho v1 における ATH モデルについて説明します。

## コアパラメータ

ATH の総供給量は固定されています。

```text
100,000,000 ATH
```

ATH は 9 桁の小数を使用します。

```text
1 ATH = 1,000,000,000 atomic units
```

atomic units 単位での総供給量:

```text
100,000,000,000,000,000
```

ローンチ時の基準価格:

```text
1 ATH = 0.001 GRAM
```

ローンチ時の完全希薄化評価額:

```text
100,000,000 ATH * 0.001 GRAM = 100,000 GRAM
```

ATH は `100,000 GRAM` の基準時価総額からスタートします。

## 固定供給量

ATH は `ATHMaster` によって発行されます。初期化時に、`ATHMaster` は固定総供給量を `100,000,000 ATH` に設定します。

ジェネシス後のミント機能は存在しません。`ATHMaster` は、管理者ミント、一時停止、ブラックリスト、送金税、強制送金、レスキュードレインを実装していません。

初期供給のデプロイは `DeployTreasurySupply` を通じて一度だけ実行されます。これは全供給量をトレジャリー ATH ウォレットに送ります。ジェネシス供給デプロイは繰り返すことができません。

総供給量はバーンによってのみ減少します。`ATHMaster` は、オーナーアドレスの決定論的 ATH ウォレットから認証済みのバーン通知を受け取った後にのみバーンを受け付けます。検証後、`ATHMaster` は `total_supply` を減少させ、`ATHBurnFinalized` を送信します。

ATH バーンは、使用されていないアドレスへの送金ではなく、総供給量の実際の削減です。

## 供給量の割り当て

ATH の供給量は 4 つのカテゴリに割り当てられます。

| カテゴリ | 割合 | 数量 |
| --- | ---: | ---: |
| アクティビティエアドロップ | 15% | 15,000,000 ATH |
| 初期流動性 | 15% | 15,000,000 ATH |
| 長期プロトコルベスティング | 10% | 10,000,000 ATH |
| マーケット安定化リザーブ | 60% | 60,000,000 ATH |

この割り当てが Platho の経済構造を定義します。

- 供給量の 15% は、プールローンチ前のアプリケーションアクティビティを通じてユーザーに配布されます。
- 供給量の 15% は初期流動性に使用されます。
- 供給量の 10% は変更不可能な長期ベスティングにロックされます。
- 供給量の 60% は MarketStabilitySeller のために予約され、プール後の価格フリーズおよびリザーブ資金供給準備ゲートの後に、ローンチ価格を上回るトランシェで販売されます。

アクティビティエアドロップと長期ベスティングリザーブは、最終ジェネシス時に Vault と ATHVesting の公式 ATH ウォレットによって裏付けられ、リリース検証者は本番リリース前にそれらの残高をチェックします。`60,000,000 ATH` のマーケット安定化割り当ては MarketStabilitySeller のために予約されますが、最終ジェネシス時にはセラーへ資金供給されません。セラーへの資金供給は、プールローンチ、一度限りのエビデンスに紐づく価格フリーズ、および紐づけられたリザーブファンダーの notify フローの後にのみ行われます。セラーの準備状態は、`reserve_due_ath`、`reserve_funded_total_ath`、および公式セラー ATH ウォレットの裏付けが検証された後にのみ有効となります。

## 長期プロトコルベスティング

長期ベスティングリザーブは以下の通りです。

```text
10,000,000 ATH
```

これは可変のトレジャリーバケットではなく、`ATHVesting` によって保有されます。ベスティングスケジュールはコントラクト内で固定されています。

```text
100,000 ATH per 365-day period
100 periods
10,000,000 ATH total
```

ATH がベスティングされた後は誰でもクレームをトリガーできますが、受益者は変更不可能です。このコントラクトには、加速、受益者変更、一時停止、管理者スイープ、レスキュードレイン、または裁量的なリリース機能はありません。

最終ジェネシス時に、公式の `ATHWallet(owner = ATHVesting, master = ATHMaster)` は正確に `10,000,000 ATH` を保持していなければなりません。検証者はまた、ローンチ前にクレーム済み ATH がゼロであること、アイドルフェーズであること、保留中の送金がないことを要求します。

このリザーブは意図的に遅く設定されています。ローンチ時に流動的な 10M ATH バケットをマーケットの上に置くことなく、プロトコル開発のための長い時間軸を作り出します。

## アクティビティエアドロップ

アクティビティエアドロップは以下の通りです。

```text
15,000,000 ATH
```

パブリッシュ成功ごとの報酬:

```text
10 ATH
```

報酬は、パブリッシュ成功後にユーザーの Vault 内部 ATH 残高にクレジットされます。パブリッシュ成功とは、Vault がペイロードを CapsuleHub に送信し、CapsuleHub がエントリを受理し、Vault が確認応答を受け取ったことを意味します。

パブリッシュの失敗はアクティビティ報酬を生成しません。

報酬の会計:

```text
user.ath_balance += 10 ATH
airdrop_remaining -= 10 ATH
```

残りのエアドロップバケットが 10 ATH を下回る場合、残りの数量がクレジットされます。バケットが枯渇すると、新しいアクティビティ報酬は停止します。

アクティビティエアドロップは Vault で会計処理され、事前に資金供給された公式 Vault ATH ウォレットによって裏付けられます。

Vault への ATH デポジットは、ユーザーの ATHWallet の transfer-with-notify フロー
（`ATHTransferRequestWithNotify`）を通じて Vault へ行う場合にのみサポートされます。公式 Vault ATHWallet への手動の通常 ATH 送金は
サポートされていません。これは公式ウォレットの生の残高を増加させることはできますが、`Vault.user.ath_balance` を生成せず、
PWA がデポジット経路として表示してはなりません。

Vault からの ATH 引き出しは、署名済みの外部 Vault コマンドです。下流の ATHWallet のデプロイ、送金、ストレージ、
ACK 実行のためのリザーブは、ユーザーの Vault 内部 GRAM 残高から支払われます。Vault は、受け取った認証済みの
ACK/失敗/バウンス価値から、ローカルの払い戻しリザーブを差し引き、予約された内部価値を上限としてのみ払い戻しクレジットを行います。プロダクトの
文言は、余剰 GRAM の完全な払い戻しを約束してはなりません。

## アクティビティ価格

パブリックなプロダクト文言では、メッセージは現在の正確なパブリックベース価格から始まると表記してもかまいません。

```text
from 0.0337 GRAM
```

ATH 割引前の現在の正確な標準例は以下の通りです。

```text
public post: 0.0337 GRAM
hybrid private 1 KiB capsule: 0.0347 GRAM
```

パブリッシュ成功に対して、ユーザーは以下を受け取ります。

```text
10 ATH
```

ローンチ基準価格では:

```text
10 ATH * 0.001 GRAM = 0.01 GRAM
```

これは初期の ATH 配布を実際のアプリケーション利用と結びつけます。報酬はアクティビティボーナスであり、払い戻し、キャッシュバック、
リベート、または ATH がパブリッシュの GRAM コストを補償するという約束ではありません。`10 ATH` のローンチ基準価値はカプセルの
GRAM コストを下回ることがあり、それは意図的なものです。ユーザーは保証された払い戻しではなく、実際の利用に対して初期のネットワーク
所有権を受け取ります。

プロダクト文言では、カプセルの価格をメッセージが `0.0337 GRAM` からと要約してもかまいません。現在の正確な標準例は、1 KiB のパブリック投稿が `0.0337 GRAM` から、ハイブリッドプライベート 1 KiB カプセルが `0.0347 GRAM` からです。選択した 1、2、4、8、16、または 32 KiB の
ボディが Vault/CapsuleHub の実行およびストレージリザーブを変更するため、より大きなパブリックまたはプライベートのカプセルブロックはより高コストになります。報酬は、カプセルサイズに関わらず、正常に確定したカプセルごとに `10 ATH` のままです。

プライベートのパブリッシュはデフォルトでハイブリッドセキュリティプロファイルを使用します: X25519 + ML-KEM-768 + AES-GCM。V1 にはより安価な古典的プライベートメッセージモードは存在しません。

公式プールが存在した後、ATH はローンチ基準価格を上回るまたは下回る価格で取引される可能性があります。プロトコルドキュメントは、
アクティビティ報酬を投資リターン、利益期待、または価格保証として提示してはなりません。

## プロトコル手数料とユーザー価格

Vault 内部では、プロトコル手数料はユーザー向けの完全なコストとは別物です。

プロトコル手数料:

| パブリッシュタイプ | プロトコル手数料 |
| --- | ---: |
| パブリック投稿 | 0.010 GRAM |
| ハイブリッドプライベートメッセージ | 0.010 GRAM |

ユーザー向け価格には、プロトコル手数料、コンパクトなインデックス/ヘッダーストレージのエンダウメント、Vault のローカル実行リザーブ、および想定される ACK 払い戻しが含まれます。

| パブリッシュタイプ | ユーザー向け価格 |
| --- | ---: |
| パブリック/プロダクトラベル | from 0.0337 GRAM |
| 現在のパブリック投稿の正確な例 | 0.0337 GRAM |
| 現在のハイブリッドプライベート 1 KiB の正確な例 | 0.0347 GRAM |

PWA がより高い保守的なネットワーク見積もりを受け取った場合、見積もり超過分を標準の最大請求額に加算し、`0.001 GRAM` のきれいな刻みに切り上げます。ATH 割引はプロトコル手数料に適用され、ネットワークコストやストレージリザーブには適用されません。この追加料金は署名済みの安全マージンです。CapsuleHub がパブリッシュを受理した場合、成功 ACK は `30,000,000` ナノトン（`0.030 GRAM`）の固定パブリッシュ ACK リザーブのみを返します。Vault がその ACK を処理した後、ユーザーは Vault 内部 GRAM 残高におよそ `25,800,000` ナノトンがクレジットされます。標準の必要価値を上回る部分は、ネットワーク/ストレージリザーブの超過分として CapsuleHub に残ります。それは Vault に返されず、パブリッシュ時点で `accrued_plato_fee_ton` としてカウントされません。CapsuleHub の保護されたリザーブを上回る生の余剰のみが、後でパーミッションレスに FeeAccumulator へスイープされ、そこで通常のトレジャリー/バイバック会計に従います。CapsuleHub はコンパクトな認証済みエントリメタデータとボディハッシュを保存し、重いボディは受理済みパブリッシュトランザクション履歴から復元され、ローカルで検証されます。

## ATH 割引

ATH は、アクティビティエアドロップが完全に配布された後にメッセージのプロトコル手数料を削減します。

割引は、残りのアクティビティエアドロップが以下の場合にのみ解除されます。

```text
airdrop_remaining_ath == 0 ATH
```

この時点より前は、プロトコル手数料は全額支払われます。

完全割引しきい値:

```text
10,000 ATH
```

ユーザーの Vault 内部 ATH 残高が少なくとも `10,000 ATH` である場合、ユーザーは Platho 手数料コンポーネントについて完全なプロトコル手数料割引ティアに到達します。ネットワークコストとストレージリザーブは引き続き支払われます。

残高が `10,000 ATH` を下回る場合、手数料は線形に減少します。

```text
raw_discounted_fee = ceil(full_fee * (10,000 ATH - min(user_ath_balance, 10,000 ATH)) / 10,000 ATH)
discounted_fee = raw_discounted_fee
```

計算は切り上げられます。現在の定数では、フルのプロトコル手数料はパブリックカプセルとプライベートカプセルの両方で `0.010 GRAM`（`10,000,000 nanotons`）であり、最大削減量はカプセルごとに `0.010 GRAM` です。

## プールローンチ

ATH/GRAM プールは、`15,000,000 ATH` のアクティビティエアドロップが完全に配布された後にローンチします。

ローンチシーケンスは以下の通りです。

1. ユーザーは実際の Platho 利用を通じて ATH を受け取ります。
2. アクティビティエアドロップが完全に配布されます。
3. ATH 割引が解除されます。
4. ATH/GRAM プールがローンチします。
5. プール後のルートエビデンスと価格エビデンスがフリーズされます。
6. バイバックスプリットが有効化されます。

プールは基準価格からスタートします。

```text
1 ATH = 0.001 GRAM
```

初期流動性の割り当て:

```text
15,000,000 ATH
```

ローンチ価格での GRAM 側:

```text
15,000,000 ATH * 0.001 GRAM = 15,000 GRAM
```

プールローンチ前に徴収されたプロトコル手数料は、初期流動性の GRAM 側を完全に賄うとは想定されていません。
初期流動性計画は、プロトコル収益に加えてプロジェクト/トレジャリーの資金供給を必要とする場合があります。これはローンチ
ブートストラップの一部であり、アクティビティ報酬を GRAM 建てのクレームに変えるものではありません。

プールは、既にアプリケーション利用を通じて配布されたトークンを中心にローンチします。これにより ATH は、ユーザーベースのない空の
リスティングと区別されます。

## FeeAccumulator

GRAM のプロトコル手数料は `FeeAccumulator` で徴収されます。

バイバックスプリットが有効化される前は、蓄積されたすべての GRAM はトレジャリーバケットに移動します。

```text
accumulated_ton -> treasury_due_ton
```

`buyback_due_ton` はスプリットが有効化される前は増加しません。

`EnableBuybackSplit` の後、蓄積された GRAM は分割されます。

```text
50% -> treasury_due_ton
50% -> buyback_due_ton
```

ナノトンで奇数の場合、剰余はバイバック側に残ります。

```text
treasury_amount = floor(amount * 50%)
buyback_amount = amount - treasury_amount
```

`EnableBuybackSplit` は、プールローンチとバイバックルートフリーズの後に変更不可能なトレジャリーレシーバーによって実行される一方向のアクションです。これは実際の一度限りの権限です。資金の窃取、一時停止、レスキュー、アドレスの変更はできませんが、
FeeAccumulator の経済をブートストラップのトレジャリー専用蓄積から 50/50 のトレジャリー/バイバックスプリットへ永続的に
変更します。これはリリースプリフライトが通過した後にのみ有効化されます。

Platho のリリース権限は意図的に狭く、ほとんどが一度限りです。それらは依然として存在し、正直に名前を挙げなければなりません。
トレジャリーオーナーは初期 ATH 供給を一度デプロイします。ジェネシスコントローラーはプレシールバインディングとシーリングを実行します。
BuybackBurn ローンチコントローラーはプール後のルートを一度フリーズします。MarketStabilitySeller の価格フリーズは、その
ローンチコントローラーによって一度実行されます。そして FeeAccumulator のトレジャリーレシーバーはプリフライト後に一方向のバイバックスプリットを有効化します。これらの
役割のいずれも、レスキュー、一時停止、アップグレード、管理者ドレイン、または任意の残高制御メカニズムではありません。

## バイバックとバーン

バイバックは `FeeAccumulator` と `BuybackBurn` を通じて実行されます。

BuybackBurn は完全な実行エンベロープのみを受け付けます。

```text
51.05 GRAM
```

エンベロープの構造:

```text
50.00 GRAM  - STON.fi offer amount
1.00 GRAM   - route forward gas
0.05 GRAM   - pTON transfer gas
```

生の `50 GRAM` は有効なバイバックチャンクではありません。バイバックは完全なルートエンベロープとしてのみ受け付けられます。

ルートフリーズの後、BuybackBurn は以下のようにバイバックを実行します。

1. 紐づけられた FeeAccumulator からのみ `51.05 GRAM` を受け付けます。
2. その数量を `reserve_due_ton` に記録します。
3. `ExecuteBuybackChunk` で 1 つのエンベロープを消費します。
4. フリーズされたクォートとフリーズされた minOut を使用します。
5. STON.fi のデッドラインを内部で設定します。
6. フリーズされた pTON ウォレットを通じてルートを送信します。
7. 公式 BuybackBurn ATH ウォレットを通じてのみ ATH を受け付けます。
8. ソースウォレットがフリーズされた STON.fi プールと一致することを検証します。
9. 受け取った ATH を公式 ATH ウォレットを通じてバーンに送ります。
10. `ATHMaster` からの `ATHBurnFinalized` の後にのみサイクルを完了します。

バイバックの成功は、ルーターメッセージ、送出バーンリクエスト、または ATHWallet バーン通知によっては定義されません。それは、
BuybackBurn が ATHMaster から認証済みの `ATHBurnFinalized` を受け取ったときにのみ定義されます。その確定が到着するまで、
BuybackBurn は依然として保留中のバーンまたはリトライ状態として扱われなければなりません。ダッシュボードとインデクサーは、単にバーン試行が
送信されたという理由だけで ATH がバーンされたとカウントしてはなりません。

バーンが確定しない場合、受け取った ATH はリトライ due へ移動します。`RetryAthBurnDue` はリトライ due の全額をバーンします。

## ユーザーネーム手数料

`.ath` ユーザーネームの登録は、公式 UsernameRegistry ATH ウォレットを通じて ATH で支払われます。

価格:

| 名前の長さ | 価格 |
| ---: | ---: |
| 4 文字 | 10,000 ATH |
| 5 文字 | 1,000 ATH |
| 6 文字以上 | 100 ATH |

UsernameRegistry は正確な価格のみを受け付けます。過少支払いおよび過剰支払いは名前を生成しません。

受理されたミントは pending 状態を経て `UsernameNFTItem` をデプロイします。アイテムの確認応答前は、支払いは収益として認識されません。アイテムの確認応答後、その数量は分割されます。

```text
50% -> treasury_due_ath
50% -> burn_due_ath
```

現在の V1 ユーザーネームミントは Vault 資金供給です。無効なユーザーネーム、誤った価格、または重複名の拒否は、
公式 ATH ウォレット通知経路を通じてバウンスされ、Vault がユーザーの内部 ATH を復元できるようにします。UsernameRegistry は、現在の Vault 資金供給フローにおいて
直接的な外部ユーザーネーム払い戻しバケットを維持しません。

ユーザーネームミントからの ATH は、対応するアイテムのデプロイが確認された後にのみプロトコル収益となります。

ユーザーネームの権限は意図的に分割されています。`UsernameRegistry` は名前を 1 つの正確な `UsernameNFTItem` に固定し、
アイテムの状態が現在の所有者を保持します。アイテムの送金はユーザーネームを移転します。アイテムは標準的な NFT データ
と TEP-64 のオンチェーンメタデータ（`name = <username>.ath` を含む）を公開します。メタデータについて Platho サーバーに依存しません。
V1 のユーザーネームバイトはリテラルであり、表示用の正規化は行われません。先頭、末尾、連続、およびすべてがセパレータの名前は、
各バイトが許可された `a-z`、`0-9`、`_`、`-` のセットに含まれ、長さが 4..16 のときに有効です。
アイテムのデプロイが試行されたがアイテムの ACK がレジストリに到達しなかった場合、`PrunePendingUsernameMint` は V1 で意図的に
非破壊的です。失敗を推測したり、pending 状態を削除したり、払い戻し due を生成したりしません。復旧経路は遅延した
`UsernameItemDeployedAck` または `UsernameNFTItem.ResendDeployedAck` であり、初期化されたアイテムは依然として権威を持つようになります。
アイテムのデプロイが実際にバウンスした場合、レジストリは公式 ATH ウォレットに pending 通知の払い戻しを要求します。
`UsernameRegistry.name_records[name_hash]` がその正確なアイテムを指していない状態でデプロイされた `UsernameNFTItem` は
非権威的です。クライアント、インデクサー、および UI は、アイテム単独を `.ath` 名の所有権として扱ってはならず、
送金後にレジストリレコードの所有者を現在の所有者として使用してはなりません。

## プロフィールアバター手数料

プロフィールアバター更新のコスト:

```text
100 ATH
```

現在の V1 プロフィールアバター更新は Vault 資金供給です。PWA は Vault に `SetProfileAvatarFromVaultBalance` を送信します。Vault はその公式 ATH ウォレット通知経路を通じて、公式 ProfileRegistry ATH ウォレットへ支払います。直接のユーザーウォレットによるアバター支払いは、サポートされている V1 プロダクトフローではありません。

ProfileRegistry は、すべての条件が満たされた場合にのみ更新を受け付けます。

- 数量が正確に `100 ATH` であること;
- 送信者が公式 ProfileRegistry ATH ウォレットであること;
- 支払いウォレットが紐づけられた Vault であること;
- 所有者ウォレットが basechain にあること;
- アバターハッシュがゼロでないこと;
- ストリーム id がゼロでないこと;
- パート数が 1 から 16 であること;
- メディア形式が WebP であること。

受理された更新は新しいアバターバージョンを生成し、手数料を分割します。

```text
50 ATH -> treasury_due_ath
50 ATH -> burn_due_ath
```

拒否されたアバター通知は、ATHWallet 通知バウンス経路を通じて払い戻されます。ProfileRegistry は、不正なアバター更新のための別個の払い戻しバケットを生成しません。

ProfileRegistry は、永続的な画像バイトではなく、認証済みのアバターポインタを保存します。PWA は、パブリック CapsuleHub エントリまたはローカルキャッシュからアバター WebP データを再構築し、保存された `avatar_hash` に対してバイトを検証しなければなりません。欠落した、またはプルーンされた履歴は利用不可として表示されます。

## Market Stability Seller

MarketStabilitySeller は、公式プールローンチ後に ATH を配布するパブリックなコントラクトリザーブです。

```text
60,000,000 ATH
```

その目的は、薄い流動性によって引き起こされる初期マーケットの歪みを軽減することです。ローンチ時、小さなプールは少数の初期購入者グループによって急激に動かされる可能性があります。それが起こると、実際の Platho アクションのために ATH を必要とするユーザーが、人為的な価格スパイクを強いられて買わざるを得なくなる可能性があります。

MarketStabilitySeller は、ローンチ価格を上回る透明な供給の階段を作り出します。固定サイズのトランシェで ATH を販売します。次の各トランシェは前のものより高価であり、各トランシェにはハードなサイズ上限があります。一度限りのエビデンスに紐づく価格フリーズの後、トランシェスケジュールは決定論的であり、チームによって手動で変更することはできません。

初期の投機家が大量の ATH を吸収しようとした場合、薄いプールからすべての安価な流動性を抜き取ってユーザーに転売する代わりに、増加するトランシェ価格でパブリックリザーブから購入することになります。一般ユーザーが Platho のために ATH を必要とする場合、単一の需要波で小さなプールを垂直に押し上げることなく、既知のパブリックトランシェ価格で購入できます。

リザーブはマーケットにトークンをダンプしません。自らは販売せず、需要なしに売り圧力を生み出しません。販売は、購入者が現在のトランシェから自発的に購入したときにのみ発生します。需要がなければ、リザーブはアイドルのままです。

ATH のオンチェーンユーティリティは具体的です。

- `.ath` ユーザーネーム登録は UsernameRegistry を通じて ATH で支払われます;
- プロフィールアバターポインタの更新は ProfileRegistry を通じて ATH で支払われます;
- ユーザーの Vault 内部残高に保有された ATH は、アクティビティ配布ゲート後の Vault パブリッシュのプロトコル手数料を削減します;
- 受理されたユーザーネームおよびアバター手数料は、トレジャリー due とバーン due を生成します;
- BuybackBurn はプロトコル GRAM 手数料で ATH を購入し、受け取った ATH を ATHMaster を通じてバーンします。

Vault パブリッシュは GRAM で支払われます。ATH はパブリッシュトランザクション全体を支払うわけではありません。割引ゲートが開いた後、プロトコル手数料コンポーネントを削減します。

これにより、ATH の需要は具体的なプロトコルアクションと結びつきます。`.ath` 名、アバター更新、エアドロップ後の Vault プロトコル手数料割引、およびバイバック/バーン圧力です。MarketStabilitySeller は、購入者が次のトランシェを取るにつれてのみ利用可能な供給を拡大するため、初期アクセスは薄いプールに支配されるのではなく、パブリックかつ決定論的です。

リザーブは、プール後の価格フリーズの後にのみ販売されます。

価格フリーズは実際の一度限りのローンチ権限です。プールローンチのエビデンスからベーストランシェ価格を一度設定し、その後ローンチコントローラーのハッシュがクリアされます。それ以降、MarketStabilitySeller は資金を窃取したり、販売を一時停止したり、残高をレスキューしたり、購入者をオーバーライドしたり、価格スケジュールを変更したりすることはできません。

MarketStabilitySeller の準備状態はプール後のゲートであり、最終ジェネシス検証の代替ではありません。本番の
シーケンスは次の通りです。クリーンな最終スナップショットで `mainnet:genesis:verify` が通過し、プールローンチ後に価格がフリーズされ、紐づけられた
リザーブファンダーが notify フローを通じてセラーに資金を供給し、その後 `market-stability:readiness` がセラーの状態、資金供給、価格
エビデンス、およびウォレットの裏付けをチェックします。セラーの準備状態は、その準備チェックの通過後にのみ本番で有効です。

資金供給は以下の場合にのみ受け付けられます。

- シール後;
- 価格フリーズ後;
- 公式セラー ATH ウォレットを通じて;
- 紐づけられたリザーブファンダーから;
- 合計上限 `60,000,000 ATH` まで。

認証済みのリザーブ資金供給のみが、販売可能なリザーブ会計を増加させます。ランタイムは部分的なリザーブ資金供給と部分的な販売を許可しますが、ローンチ準備には完全なリザーブが必要です。`reserve_due_ath == 60,000,000 ATH`、`reserve_funded_total_ath == 60,000,000 ATH`、および少なくとも `60,000,000 ATH` の公式ウォレットの裏付けです。公式セラー ATH ウォレットへの求められていない通常の ATH 送金は、`reserve_due_ath` や `reserve_funded_total_ath` を増加させず、販売可能な供給を拡大せず、スタックしたままになる可能性があります。準備チェックは `60,000,000 ATH` を上回る公式ウォレット残高を、追加のリザーブとしてではなく警告として扱います。

リザーブは 20 のトランシェに分割されます。

```text
20 * 3,000,000 ATH = 60,000,000 ATH
```

各トランシェには乗数があります。

```text
x2, x3, x4, ..., x21
```

これは滑らかな価格の階段を作り出します。プロジェクトの人気が高まるにつれて、マーケットは追加の ATH 供給を受け取りますが、次の各トランシェは前のものより高価です。初期需要はすぐに薄いプールを直撃せず、価格の成長はユーティリティトークンを使いにくくする垂直の壁にはなりません。

購入の計算式:

```text
price = ceil(base_tranche_price * current_multiplier * amount / 3,000,000 ATH)
```

`base_tranche_price` はプールローンチ後にフリーズされ、x1 の価格エビデンスと正確に一致します。

ローンチ価格 `1 ATH = 0.001 GRAM` において、1 トランシェの x1 価格は以下の通りです。

```text
3,000,000 ATH * 0.001 GRAM = 3,000 GRAM
```

したがって:

| トランシェ | 乗数 | 3M ATH の価格 | 1 ATH あたりの価格 |
| ---: | ---: | ---: | ---: |
| 1 | x2 | 6,000 GRAM | 0.002 GRAM |
| 2 | x3 | 9,000 GRAM | 0.003 GRAM |
| 3 | x4 | 12,000 GRAM | 0.004 GRAM |
| ... | ... | ... | ... |
| 15 | x16 | 48,000 GRAM | 0.016 GRAM |
| ... | ... | ... | ... |
| 20 | x21 | 63,000 GRAM | 0.021 GRAM |

単一の購入はトランシェの境界を越えることはできません。これにより、次のトランシェの ATH を前のトランシェの価格で購入することを防ぎます。

GRAM 収益は、ATH が購入者に配送された後にのみ認識されます。ATH の送金が失敗またはバウンスした場合、リザーブは復元され、購入者は支払った GRAM 元本を返してもらい、トレジャリー due は増加しません。

最後の x21 トランシェが販売された後、MarketStabilitySeller はもはや ATH 価格を規制しません。その時点から、価格は完全にマーケットによって決定されます。流動性、利用可能な供給、`.ath` 名の需要、アバター更新、エアドロップ後の Vault プロトコル手数料割引、およびバイバック/バーン圧力です。

x21 のステップにおいてさえ、基準評価額はユーティリティモデルに対して穏当なままです。

```text
1 ATH = 0.021 GRAM
100,000,000 ATH = 2,100,000 GRAM
```

x21 のステップで、MarketStabilitySeller はプログラムされたリザーブのリリースを終えます。その後、ATH 価格は完全に、流動性、利用需要、利用可能な供給、およびバイバック/バーン圧力によってマーケット決定されます。残る唯一のプロトコル割り当ては、年間 `100,000 ATH` を上限とする遅い長期ベスティングスケジュールです。

## トレジャリーとバーンのバケット

UsernameRegistry と ProfileRegistry は同じ ATH 手数料分割モデルを使用します。

```text
accepted ATH fee -> 50% treasury_due_ath + 50% burn_due_ath
```

トレジャリー due のフラッシュは、公式 ATH ウォレットを通じてトレジャリーレシーバーへ ATH を送ります。

バーン due のフラッシュは、公式 ATH ウォレットを通じて ATH バーンリクエストを送ります。供給は、ATHMaster でのバーン確定後にのみ減少します。

失敗およびバウンスの経路は due バケットを復元します。会計は、下流の送金またはバーンが完了するまで保持されます。

## ATHWallet 会計

ATH 残高は決定論的な ATHWallet コントラクトに存在します。

ATHWallet は以下を処理します。

- ジェネシス供給クレジット;
- 通常送金;
- transfer with notify;
- ユーザーネームミント通知;
- プロフィールアバター通知;
- バーンリクエスト;
- 通知確認応答;
- 古い通知のプルーン;
- バウンス/失敗の復旧。

ATH を支払いとして受け付けるコントラクトは、任意のアドレスからの直接メッセージを受け付けません。それらは公式 ATHWallet からの通知のみを受け付けます。ソースウォレットの認証は、決定論的なウォレット導出を通じて ATHWallet 内部で実行されます。

ATH は汎用ジェットンツール向けに TEP-74 ライクな送金エントリポイントを公開しますが、Platho プロトコルアクションは認証済みの ATH 通知メッセージを使用します。外部統合は、Platho の notify フローが汎用的な `JettonTransferNotification` を発行すると想定してはなりません。

ATHWallet における送出内部送金は、ソース側の pending 会計とソース確認応答によって保護されます。残高は、pending 証明なしにバウンスボディから復元されることはありません。

## ATH ライフサイクル

1. `ATHMaster` が `100,000,000 ATH` の固定供給を生成します。
2. トレジャリーデプロイの一度限りの処理が、トレジャリー ATH ウォレットで供給を受け取ります。
3. 供給はアクティビティ、流動性、長期ベスティング、およびマーケット安定化に割り当てられます。
4. ユーザーは Vault を通じてメッセージをパブリッシュします。
5. パブリッシュ成功は `10 ATH` のアクティビティ報酬をクレジットします。
6. `15,000,000 ATH` のアクティビティエアドロップが完全に配布され、`airdrop_remaining_ath == 0` となった後、ATH プロトコル手数料割引が解除されます。
7. ATH/GRAM プールが基準価格 `1 ATH = 0.001 GRAM` でローンチします。
8. プール後のルートエビデンスと価格エビデンスがフリーズされます。
9. MarketStabilitySeller が x2..x21 のトランシェを通じてリザーブを販売します。
10. スプリットが有効化された後、FeeAccumulator はプロトコル GRAM 手数料をトレジャリーとバイバックの間で分割します。
11. BuybackBurn は GRAM プロトコル手数料で ATH を購入し、ATHMaster を通じて ATH をバーンします。
12. ユーザーネームおよびプロフィール手数料は、ATH トレジャリー due と ATH バーン due を生成します。
13. 総供給量は認証済みのバーンを通じて徐々に減少します。

## 最終モデル

ATH は Platho の 4 つのレイヤーを結びつけます。

1. **アプリケーション利用** - メッセージがアクティビティ報酬を生成します。
2. **有料機能** - ユーザーネームとアバターは ATH を必要とします。
3. **割引** - ATH 残高は配布ゲート後のプロトコル手数料を削減します。
4. **供給削減** - ATH 手数料とバイバック出力の一部は ATHMaster を通じてバーンされます。

モデルは固定供給量と `100,000 GRAM` の基準評価額から始まります。主要なユーザー配布は実際の有料利用と結びついています。プロダクト文言ではメッセージが `0.0337 GRAM` から始まると表記してもよく、現在の正確な例は 1 KiB のパブリック投稿が `0.0337 GRAM`、ハイブリッドプライベート 1 KiB カプセルが `0.0347 GRAM` であり、加えて確定したカプセルごとに `10 ATH` のアクティビティボーナスがあります。より大きなパブリックまたはプライベートのサイズクラスはより高コストです。そのボーナスは払い戻し、返金、または利益の約束ではありません。供給量の最初の 15% が配布された後、プールがローンチし、プロトコル手数料割引が解除され、バイバック経路が開きます。

ATH は Platho 内部で稼働するトークンとして存在します。アクティビティを通じて配布され、有料アクションで使用され、プロトコル手数料を削減し、定義された階段を通じてリザーブから販売され、オンチェーンバーンを通じてバーンされます。マーケット安定化の階段の後、将来の ATH 価格はマーケットとプロトコル利用によって決定されます。

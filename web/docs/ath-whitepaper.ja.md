# ATH ホワイトペーパー

## Platho プロトコルトークン

ATH は Platho のユーティリティトークンです。アクティビティ報酬、エアドロップ後のプロトコル手数料割引、`.ath` ユーザー名、プロフィールアバターの更新、市場安定化のための販売、buyback、そして burn に利用されます。

ATH は管理用トークンではありません。残高を書き換えたり、操作を一時停止したり、新規供給を発行したり、ユーザーの所有権ルールを変更したりする能力を付与するものではありません。その役割は、アプリケーション経済を動かし、Platho の利用状況をオンチェーン会計と結び付けることにあります。

本書は、Platho における ATH モデルについて説明します。

## 中核パラメータ

ATH は固定の総供給量を持ちます。

```text
100,000,000 ATH
```

ローンチ時の基準価格は次のとおりです。

```text
1 ATH = 0.001 GRAM
```

ローンチ時の完全希薄化評価額は次のとおりです。

```text
100,000,000 ATH * 0.001 GRAM = 100,000 GRAM
```

ATH は `100,000 GRAM` という基準時価総額から出発します。

## 固定供給

ATH は `ATHMaster` によって発行されます。初期化時に、`ATHMaster` は固定の総供給量を `100,000,000 ATH` に設定します。

genesis 以降に mint 機能は存在しません。`ATHMaster` は、管理者による mint、一時停止、ブラックリスト、送金税、強制送金、レスキュードレインのいずれも実装していません。

初期供給のデプロイは、`DeployTreasurySupply` を通じて一度だけ実行されます。これは全供給量をトレジャリーの ATH ウォレットへ送付します。genesis 供給デプロイを繰り返すことはできません。

総供給量は burn を通じてのみ減少します。`ATHMaster` は、オーナーアドレスの決定論的 ATH ウォレットから認証された burn 通知を受け取った後にのみ、burn を受け付けます。検証の後、`ATHMaster` は `total_supply` を減少させ、`ATHBurnFinalized` を送信します。

ATH の burn は総供給量の実際の削減であり、未使用アドレスへの送金ではありません。

## 供給の割り当て

ATH の供給は 4 つのカテゴリに割り当てられます。

| カテゴリ | 割合 | 数量 |
| --- | ---: | ---: |
| アクティビティエアドロップ | 15% | 15,000,000 ATH |
| 初期流動性 | 15% | 15,000,000 ATH |
| 長期プロトコルベスティング | 10% | 10,000,000 ATH |
| 市場安定化リザーブ | 60% | 60,000,000 ATH |

この割り当ては Platho の経済構造を定義します。

- 供給の 15% は、プール立ち上げ前にアプリケーションのアクティビティを通じてユーザーへ配布されます。
- 供給の 15% は初期流動性に利用されます。
- 供給の 10% は不変の長期ベスティングにロックされます。
- 供給の 60% は MarketStabilitySeller に資金供給され genesis でロックされ、プール後の価格凍結の後にローンチ価格を上回る価格でトランシェ単位で販売されます。

アクティビティエアドロップと長期ベスティングリザーブは、最終 genesis において Vault と ATHVesting の公式 ATH ウォレットによって裏付けられ、リリース検証器は本番リリース前にそれらの残高を確認します。`60,000,000 ATH` の市場安定化リザーブは MarketStabilitySeller に資金供給され最終 genesis でロックされ、その公式セラー ATH ウォレットによって裏付けられ、リリース検証器は本番リリース前にその裏付けを確認します。リザーブは当初から資本化されていますが、プール立ち上げ後、evidence に紐づく一度限りの価格凍結が基準トランシェ価格を設定するまで販売されることはありません。

## 長期プロトコルベスティング

長期ベスティングリザーブは次のとおりです。

```text
10,000,000 ATH
```

これは可変のトレジャリーバケットではなく `ATHVesting` によって保持されます。ベスティングスケジュールはコントラクト内で固定されています。

```text
100,000 ATH per 365-day period
100 periods
10,000,000 ATH total
```

ATH がベスト済みになれば誰でもクレームをトリガーできますが、受益者は不変です。このコントラクトには、加速、受益者変更、一時停止、管理者スイープ、レスキュードレイン、裁量的リリースのいずれの機能もありません。

最終 genesis において、公式の `ATHWallet(owner = ATHVesting, master = ATHMaster)` はちょうど `10,000,000 ATH` を保有していなければなりません。検証器はさらに、クレーム済み ATH がゼロであること、idle フェーズであること、そしてローンチ前に保留中の送金が存在しないことを要求します。

このリザーブは意図的に緩やかに設計されています。ローンチ時に流動的な 10M ATH のバケットを市場の上に置くことなく、プロトコル開発のための長い時間軸を作り出します。

## アクティビティエアドロップ

アクティビティエアドロップは次のとおりです。

```text
15,000,000 ATH
```

publish 成功ごとの報酬は次のとおりです。

```text
10 ATH
```

報酬は、publish 成功後にユーザーの Vault 内 ATH 残高へ計上されます。publish 成功とは、Vault がペイロードを CapsuleHub へ送信し、CapsuleHub がそのエントリを受け入れ、Vault が確認応答を受信したことを意味します。

publish の失敗はアクティビティ報酬を生成しません。

報酬会計は次のとおりです。

```text
user.ath_balance += 10 ATH
airdrop_remaining -= 10 ATH
```

残りのエアドロップバケットが 10 ATH を下回っている場合は、残額が計上されます。バケットが枯渇すると、新規のアクティビティ報酬は停止します。

アクティビティエアドロップは Vault で会計処理され、事前に資金供給された公式 Vault ATH ウォレットによって裏付けられます。

Vault への ATH 入金は、ユーザーの ATHWallet の transfer-with-notify フロー
(`ATHTransferRequestWithNotify`) を通じて Vault へ入る場合のみサポートされます。公式 Vault ATHWallet への手動の通常 ATH 送金は
サポートされていません。生の公式ウォレット残高を増やすことはできても、`Vault.user.ath_balance` を生成せず、
PWA は入金経路として表示してはなりません。

Vault からの ATH 出金は、署名された Vault 外部コマンドです。下流の ATHWallet のデプロイ、送金、ストレージ、
ACK 実行のためのリザーブは、ユーザーの Vault 内部 GRAM 残高から支払われます。Vault は、受信した認証済みの
ACK/失敗/バウンス価値から、ローカルの返金リザーブを差し引き、予約された内部価値を上限として、その分のみを払い戻します。

## アクティビティ価格

メッセージは現在の公開基本価格から始まります。

```text
from 0.0337 GRAM
```

ATH 割引前の現在の正確な標準例は次のとおりです。

```text
public post: 0.0337 GRAM
hybrid private 1 KiB capsule: 0.0347 GRAM
```

publish 成功に対して、ユーザーは次を受け取ります。

```text
10 ATH
```

ローンチ基準価格では次のとおりです。

```text
10 ATH * 0.001 GRAM = 0.01 GRAM
```

これは初期の ATH 配布を実際のアプリケーション利用に結び付けます。この報酬はアクティビティボーナスであり、
返金、キャッシュバック、リベート、または ATH が publish の GRAM コストを補償するという約束ではありません。`10 ATH` のローンチ基準価値はカプセルの GRAM コストを
下回る場合があり、それは意図的です。ユーザーは保証された補填ではなく、実際の利用に対する初期のネットワーク所有権を
受け取ります。

カプセル価格: 1 KiB の public post は `0.0337 GRAM` から、hybrid private 1 KiB カプセルは `0.0347 GRAM` から始まります。より大きな public または private のカプセルブロックは、選択された 1、2、4、8、16、または 32 KiB の
本体が Vault/CapsuleHub の実行およびストレージリザーブを変化させるため、より高コストになります。報酬はカプセルサイズにかかわらず、正常に確定したカプセル
ごとに `10 ATH` のままです。

private の publish はデフォルトで hybrid セキュリティプロファイルを使用します: X25519 + ML-KEM-768 + AES-GCM。より安価な古典的 private メッセージモードは存在しません。

公式プールが存在した後、ATH はローンチ基準価格を上回ることも下回ることもあり得ます。アクティビティ報酬は投資リターン、利益の期待、または価格の保証ではありません。

## プロトコル手数料とユーザー価格

Vault 内部では、プロトコル手数料はユーザーが実際に負担する総コストとは別のものです。

プロトコル手数料は次のとおりです。

| publish 種別 | プロトコル手数料 |
| --- | ---: |
| Public post | 0.010 GRAM |
| Hybrid private message | 0.010 GRAM |

ユーザーが実際に負担する価格には、プロトコル手数料、コンパクトなインデックス/ヘッダーのストレージ拠出、Vault ローカル実行リザーブ、そして予想される ACK 返金が含まれます。

| publish 種別 | ユーザーが負担する価格 |
| --- | ---: |
| Public (from) | from 0.0337 GRAM |
| 現在の public post の正確な例 | 0.0337 GRAM |
| 現在の hybrid private 1 KiB の正確な例 | 0.0347 GRAM |

PWA がより高い保守的なネットワーク見積もりを受け取った場合、見積もりの超過分を標準の最大チャージへ加算し、`0.001 GRAM` のきれいな刻みへ切り上げます。ATH 割引はプロトコル手数料に適用され、ネットワークコストやストレージリザーブには適用されません。このサーチャージは署名された安全マージンです。CapsuleHub が publish を受け入れた場合、成功 ACK は固定の publish ACK リザーブである `30,000,000` nanotons (`0.030 GRAM`) のみを返します。Vault がその ACK を処理した後、ユーザーには Vault 内部 GRAM 残高としておよそ `25,800,000` nanotons が計上されます。標準の必要価値を超える部分は、ネットワーク/ストレージリザーブの超過分として CapsuleHub に残ります。それは Vault へ返却されず、publish 時点で `accrued_plato_fee_ton` として計上されません。CapsuleHub の保護されたリザーブを超える生の余剰分のみが、後に許可不要で FeeAccumulator へスイープされ得て、そこでは通常のトレジャリー/buyback 会計に従います。CapsuleHub はコンパクトな認証済みエントリメタデータと body ハッシュを保存します。重い本体は、受け入れられた publish トランザクション履歴から復元され、ローカルで検証されます。

## ATH 割引

ATH は、アクティビティエアドロップが完全に配布された後に、メッセージのプロトコル手数料を軽減します。

割引は、残りのアクティビティエアドロップが次の場合にのみアンロックされます。

```text
airdrop_remaining_ath == 0 ATH
```

この時点より前は、プロトコル手数料は全額支払われます。

全額割引のしきい値は次のとおりです。

```text
10,000 ATH
```

ユーザーの Vault 内 ATH 残高が少なくとも `10,000 ATH` であれば、ユーザーは Platho 手数料コンポーネントについて全額プロトコル手数料割引ティアに到達します。ネットワークコストとストレージリザーブは引き続き支払われます。

残高が `10,000 ATH` を下回る場合、手数料は線形に減少します。

```text
raw_discounted_fee = ceil(full_fee * (10,000 ATH - min(user_ath_balance, 10,000 ATH)) / 10,000 ATH)
discounted_fee = raw_discounted_fee
```

計算は切り上げられます。現在の定数では、全額プロトコル手数料は public と private の両カプセルについて `0.010 GRAM` (`10,000,000 nanotons`) であり、最大軽減額はカプセルあたり `0.010 GRAM` です。

## プール立ち上げ

ATH/GRAM プールは、`15,000,000 ATH` のアクティビティエアドロップが完全に配布された後に立ち上がります。

立ち上げのシーケンスは次のとおりです。

1. ユーザーは実際の Platho 利用を通じて ATH を受け取ります。
2. アクティビティエアドロップが完全に配布されます。
3. ATH 割引がアンロックされます。
4. ATH/GRAM プールが立ち上がります。
5. プール後のルート evidence と価格 evidence が凍結されます。
6. buyback 分割が有効化されます。

プールは基準価格から始まります。

```text
1 ATH = 0.001 GRAM
```

初期流動性の割り当ては次のとおりです。

```text
15,000,000 ATH
```

ローンチ価格での GRAM 側は次のとおりです。

```text
15,000,000 ATH * 0.001 GRAM = 15,000 GRAM
```

プール立ち上げ前に徴収されたプロトコル手数料が、初期流動性の GRAM 側全体を賄います。これはローンチの
ブートストラップの一部であり、アクティビティ報酬を GRAM 建てのクレームに変えるものではありません。

プールは、すでにアプリケーション利用を通じて配布されたトークンの周りで立ち上がります。これは ATH を、ユーザーベースのない空のリスティングから区別します。

## FeeAccumulator

GRAM のプロトコル手数料は `FeeAccumulator` に徴収されます。

buyback 分割が有効化される前は、蓄積されたすべての GRAM はトレジャリーバケットへ移されます。

```text
accumulated_ton -> treasury_due_ton
```

`buyback_due_ton` は分割が有効化される前には増加しません。

`EnableBuybackSplit` の後、蓄積された GRAM は分割されます。

```text
50% -> treasury_due_ton
50% -> buyback_due_ton
```

nanotons 単位で金額が奇数の場合、余りは buyback 側に残ります。

```text
treasury_amount = floor(amount * 50%)
buyback_amount = amount - treasury_amount
```

`EnableBuybackSplit` は、プール立ち上げおよび buyback ルート凍結の後に不変のトレジャリーレシーバによって実行される一方向のアクションです。これは実際の一度限りの権限です。資金を盗む、
一時停止する、レスキューする、アドレスを変更するといったことはできませんが、FeeAccumulator の経済を、ブートストラップのトレジャリー専用蓄積から
50/50 のトレジャリー/buyback 分割へと恒久的に変更します。これはリリースプリフライトが通過した後にのみ
有効化されます。

Platho のリリース権限は意図的に狭く、ほとんどが一度限りです。それらは依然として存在し、正直に名指しされなければなりません。
トレジャリーオーナーは初期 ATH 供給を一度デプロイし、genesis コントローラは事前シールのバインディングとシールを行い、
BuybackBurn ローンチコントローラはプール後のルートを一度凍結し、MarketStabilitySeller の価格凍結はそのローンチコントローラによって
一度実行され、そして FeeAccumulator のトレジャリーレシーバはプリフライトの後に一方向の buyback 分割を有効化します。これらの
役割のいずれも、レスキュー、一時停止、アップグレード、管理者ドレイン、または任意の残高制御メカニズムではありません。

## Buyback と Burn

buyback は `FeeAccumulator` と `BuybackBurn` を通じて実行されます。

BuybackBurn は完全な実行エンベロープのみを受け入れます。

```text
51.05 GRAM
```

エンベロープの構造は次のとおりです。

```text
50.00 GRAM  - STON.fi offer amount
1.00 GRAM   - route forward gas
0.05 GRAM   - pTON transfer gas
```

生の `50 GRAM` は有効な buyback チャンクではありません。buyback は完全なルートエンベロープとしてのみ受け入れられます。

ルート凍結の後、BuybackBurn は次のように buyback を実行します。

1. バインドされた FeeAccumulator からのみ `51.05 GRAM` を受け入れます。
2. その金額を `reserve_due_ton` に記録します。
3. `ExecuteBuybackChunk` で、1 つのエンベロープを消費します。
4. 凍結された quote と凍結された minOut を使用します。
5. STON.fi の deadline を内部で設定します。
6. 凍結された pTON ウォレットを通じてルートを送信します。
7. ATH は公式 BuybackBurn ATH ウォレットを通じてのみ受け入れます。
8. ソースウォレットが凍結された STON.fi プールと一致することを検証します。
9. 受信した ATH を、公式 ATH ウォレットを通じて burn へ送信します。
10. `ATHMaster` からの `ATHBurnFinalized` の後にのみサイクルを完了します。

buyback の成功は、router メッセージ、送信された burn リクエスト、または ATHWallet の burn 通知によって定義されるものではありません。それは
BuybackBurn が ATHMaster から認証済みの `ATHBurnFinalized` を受信したときにのみ定義されます。その確定が到着するまで、
BuybackBurn は依然として burn 保留またはリトライ状態として扱われなければなりません。ダッシュボードやインデクサは、burn の試行が
送信されたというだけで ATH を burn 済みと数えてはなりません。

burn が確定しない場合、受信した ATH はリトライ due へ移されます。`RetryAthBurnDue` はリトライ due の全額を burn します。

## ユーザー名手数料

`.ath` ユーザー名の登録は、公式 UsernameRegistry ATH ウォレットを通じて ATH で支払われます。

価格は次のとおりです。

| 名前の長さ | 価格 |
| ---: | ---: |
| 4 文字 | 10,000 ATH |
| 5 文字 | 1,000 ATH |
| 6 文字以上 | 100 ATH |

UsernameRegistry は正確な価格のみを受け入れます。不足払いや過剰払いは名前を生成しません。

受け入れられた mint は pending 状態を経て `UsernameNFTItem` をデプロイします。item の確認応答の前は、支払いは収益として認識されません。item の確認応答の後、金額は分割されます。

```text
50% -> treasury_due_ath
50% -> burn_due_ath
```

ユーザー名の mint は Vault 資金で賄われます。無効なユーザー名、誤った価格、または重複名による拒否は、
公式 ATH ウォレットの通知経路を通じてバウンスするため、Vault はユーザーの内部 ATH を復元できます。UsernameRegistry は、現在の Vault 資金フローにおいて
直接の外部ユーザー名返金バケットを保持しません。

ユーザー名 mint からの ATH は、対応する item のデプロイが確認された後にのみプロトコル収益になります。

ユーザー名の権限は意図的に分割されています。`UsernameRegistry` は名前をちょうど 1 つの `UsernameNFTItem` にアンカーし、
item の状態が現在の所有者を保持します。item の送金がユーザー名を移転します。item は標準の NFT データ
と TEP-64 オンチェーンメタデータ (`name = <username>.ath` を含む) を公開します。メタデータのために Platho サーバーに依存しません。
ユーザー名のバイトはリテラルであり、表示のための正規化はされません。先頭、末尾、連続、およびすべてが区切り文字の名前は、
すべてのバイトが許可された `a-z`、`0-9`、`_`、`-` の集合に含まれ、長さが 4..16 であれば有効です。
item のデプロイが試みられたものの item の ACK がレジストリに到達しなかった場合、`PrunePendingUsernameMint` は意図的に
非破壊的です。失敗を推測したり、pending 状態を削除したり、返金 due を生成したりしません。回復の経路は遅延した
`UsernameItemDeployedAck` または `UsernameNFTItem.ResendDeployedAck` であり、初期化された item は依然として正式なものになり得ます。
item のデプロイが実際にバウンスした場合、レジストリは公式 ATH ウォレットに pending 通知の返金を要求します。
`UsernameRegistry.name_records[name_hash]` がそのちょうどの item を指していないデプロイ済みの `UsernameNFTItem` は
非正式です。クライアント、インデクサ、UI は、item 単独を `.ath` 名の所有権として扱ってはならず、
送金後にレジストリレコードの所有者を現在の所有者として使用してはなりません。

## プロフィールアバター手数料

プロフィールアバター更新のコストは次のとおりです。

```text
100 ATH
```

プロフィールアバターの更新は Vault 資金で賄われます。PWA は Vault へ `SetProfileAvatarFromVaultBalance` を送信します。Vault はその公式 ATH ウォレットの通知経路を通じて、公式 ProfileRegistry ATH ウォレットへ支払います。ユーザーウォレットからの直接のアバター支払いはサポートされていません。

ProfileRegistry は、すべての条件が満たされた場合にのみ更新を受け入れます。

- 金額がちょうど `100 ATH` であること。
- 送信者が公式 ProfileRegistry ATH ウォレットであること。
- 支払いウォレットがバインドされた Vault であること。
- 所有者ウォレットが basechain にあること。
- アバターハッシュがゼロでないこと。
- stream id がゼロでないこと。
- パート数が 1 から 16 であること。
- メディアフォーマットが WebP であること。

受け入れられた更新は新しいアバターバージョンを生成し、手数料を分割します。

```text
50 ATH -> treasury_due_ath
50 ATH -> burn_due_ath
```

拒否されたアバター通知は、ATHWallet の通知バウンス経路を通じて返金されます。ProfileRegistry は、不正なアバター更新のために別個の返金バケットを生成しません。

ProfileRegistry は、永続的な画像バイトではなく、認証済みのアバターポインタを保存します。PWA は、公開 CapsuleHub エントリまたはローカルキャッシュからアバターの WebP データを再構成し、保存された `avatar_hash` に対してバイトを検証しなければなりません。欠落または prune された履歴は利用不可として表示されます。

## Market Stability Seller

MarketStabilitySeller は、公式プール立ち上げの後に ATH を配布する公開コントラクトリザーブです。

```text
60,000,000 ATH
```

その目的は、薄い流動性によって引き起こされる初期市場の歪みを軽減することです。ローンチ時には、小さなプールは少数の初期購入者グループによって急激に動かされ得ます。もしそうなった場合、実際の Platho アクションのために ATH を必要とするユーザーは、人為的な価格スパイクへの購入を強いられかねません。

MarketStabilitySeller は、ローンチ価格を上回る透明な供給階段を作り出します。固定サイズのトランシェで ATH を販売します。次のトランシェはそれぞれ前のものより高価であり、各トランシェには厳格なサイズ上限があります。evidence に紐づく一度限りの価格凍結の後、トランシェスケジュールは決定論的であり、チームによって手動で変更することはできません。

初期の投機家が大量の ATH を吸収しようとした場合、彼らは薄いプールからすべての安価な流動性を抜き取ってユーザーへ転売するのではなく、増加するトランシェ価格で公開リザーブから購入することになります。通常のユーザーが Platho のために ATH を必要とする場合、単一の需要波で小さなプールを垂直に押し上げることなく、既知の公開トランシェ価格でそれを購入できます。

リザーブはトークンを市場に投げ込むことはありません。自ら販売することはなく、需要なしに売り圧力を生み出すこともありません。販売は、買い手が現在のトランシェから自発的に購入したときにのみ発生します。需要がなければ、リザーブは idle のままです。

ATH のオンチェーンユーティリティは具体的です。

- `.ath` ユーザー名の登録は UsernameRegistry を通じて ATH で支払われます。
- プロフィールアバターポインタの更新は ProfileRegistry を通じて ATH で支払われます。
- ユーザーの Vault 内部残高に保有された ATH は、アクティビティ配布ゲートの後に Vault publish のプロトコル手数料を軽減します。
- 受け入れられたユーザー名およびアバター手数料は、トレジャリー due と burn due を生成します。
- BuybackBurn はプロトコル GRAM 手数料で ATH を購入し、受信した ATH を ATHMaster を通じて burn します。

Vault publish は GRAM で支払われます。ATH は publish トランザクション全体を支払うわけではありません。割引ゲートが開いた後、プロトコル手数料コンポーネントを軽減します。

これにより ATH 需要は具体的なプロトコルアクションに結び付きます。`.ath` 名、アバター更新、エアドロップ後の Vault プロトコル手数料割引、そして buyback/burn の圧力です。MarketStabilitySeller は買い手が次のトランシェを取ったときにのみ利用可能な供給を拡大するため、初期アクセスは薄いプールに支配されるのではなく、公開かつ決定論的です。

リザーブは、プール後の価格凍結の後にのみ販売されます。

価格凍結は実際の一度限りのローンチ権限です。プール立ち上げの evidence から基準トランシェ価格を一度設定し、その後ローンチコントローラのハッシュがクリアされます。それ以降、MarketStabilitySeller は資金を盗む、販売を一時停止する、残高をレスキューする、買い手をオーバーライドする、価格スケジュールを変更する、といったことはできません。

MarketStabilitySeller は最終 genesis で `60,000,000 ATH` のリザーブ全体をもって資本化され、認証済みの
reserve-funder フローを通じて、`60,000,000 ATH` の厳格な上限まで公式セラー ATH ウォレットへ資金供給されます。
`mainnet:genesis:verify` は、セラーがリザーブ全体を保有していること、そしてその公式セラー ATH ウォレットの裏付けが
本番リリース前に少なくとも `60,000,000 ATH` であることを確認します。公式セラー ATH ウォレットへの要求されない通常の ATH 送金は
計上されるリザーブを増加させず、販売可能な供給を拡大せず、詰まったままになり得ます。`60,000,000 ATH` を超えるウォレット残高
は追加のリザーブではなく警告として扱われます。

販売はプール後の別個のステップです。リザーブは、プール立ち上げの後、evidence に紐づく一度限りの
価格凍結が基準トランシェ価格を設定するまで販売されません。それ以降、トランシェスケジュールは決定論的であり、チームによって手動で
変更することはできません。

リザーブは 20 のトランシェに分割されます。

```text
20 * 3,000,000 ATH = 60,000,000 ATH
```

各トランシェには乗数があります。

```text
x2, x3, x4, ..., x21
```

これは滑らかな価格階段を作り出します。プロジェクトの人気が高まるにつれて、市場は追加の ATH 供給を受け取りますが、次のトランシェはそれぞれ前のものより高価です。初期需要が薄いプールに即座にぶつかることはなく、価格上昇がユーティリティトークンを使いにくくする垂直の壁になることもありません。

購入の計算式は次のとおりです。

```text
price = ceil(base_tranche_price * current_multiplier * amount / 3,000,000 ATH)
```

`base_tranche_price` はプール立ち上げの後に凍結され、x1 価格 evidence とちょうど一致します。

ローンチ価格 `1 ATH = 0.001 GRAM` において、1 トランシェの x1 価格は次のとおりです。

```text
3,000,000 ATH * 0.001 GRAM = 3,000 GRAM
```

したがって次のようになります。

| トランシェ | 乗数 | 3M ATH の価格 | 1 ATH あたりの価格 |
| ---: | ---: | ---: | ---: |
| 1 | x2 | 6,000 GRAM | 0.002 GRAM |
| 2 | x3 | 9,000 GRAM | 0.003 GRAM |
| 3 | x4 | 12,000 GRAM | 0.004 GRAM |
| ... | ... | ... | ... |
| 15 | x16 | 48,000 GRAM | 0.016 GRAM |
| ... | ... | ... | ... |
| 20 | x21 | 63,000 GRAM | 0.021 GRAM |

単一の購入がトランシェ境界をまたぐことはできません。これは、次のトランシェの ATH を前のトランシェ価格で購入することを防ぎます。

GRAM 収益は、ATH が買い手へ引き渡された後にのみ認識されます。ATH 送金が失敗またはバウンスした場合、リザーブは復元され、買い手は支払った GRAM 元本を取り戻し、トレジャリー due は増加しません。

最終の x21 トランシェが販売された後、MarketStabilitySeller はもはや ATH 価格を調整しません。その時点から、価格は市場によって完全に決定されます。流動性、利用可能な供給、`.ath` 名の需要、アバター更新、エアドロップ後の Vault プロトコル手数料割引、そして buyback/burn の圧力です。

x21 のステップにおいてさえ、基準評価額はユーティリティモデルに対して穏当なままです。

```text
1 ATH = 0.021 GRAM
100,000,000 ATH = 2,100,000 GRAM
```

x21 のステップで、MarketStabilitySeller はそのプログラムされたリザーブ放出を完了します。その後、ATH 価格は流動性、利用需要、利用可能な供給、そして buyback/burn の圧力によって完全に市場決定されます。残る唯一のプロトコル割り当ては、年間 `100,000 ATH` を上限とする緩やかな長期ベスティングスケジュールです。

## トレジャリーと burn バケット

UsernameRegistry と ProfileRegistry は同じ ATH 手数料分割モデルを使用します。

```text
accepted ATH fee -> 50% treasury_due_ath + 50% burn_due_ath
```

トレジャリー due のフラッシュは、公式 ATH ウォレットを通じてトレジャリーレシーバへ ATH を送信します。

burn due のフラッシュは、公式 ATH ウォレットを通じて ATH burn リクエストを送信します。供給は ATHMaster での burn 確定の後にのみ減少します。

失敗およびバウンスの経路は due バケットを復元します。会計は、下流の送金または burn が完了するまで保持されます。

## ATHWallet 会計

ATH 残高は決定論的な ATHWallet コントラクトに存在します。

ATHWallet は次を処理します。

- genesis 供給のクレジット。
- 通常の送金。
- 通知付きの送金。
- ユーザー名 mint 通知。
- プロフィールアバター通知。
- burn リクエスト。
- 通知の確認応答。
- stale な通知の prune。
- バウンス/失敗からの回復。

ATH を支払いとして受け入れるコントラクトは、任意のアドレスからの直接メッセージを受け入れません。それらは自身の公式 ATHWallet からの通知のみを受け入れます。ソースウォレットの認証は、決定論的ウォレット導出を通じて ATHWallet の内部で実行されます。

ATH は汎用の jetton ツールのために TEP-74 ライクな送金エントリポイントを公開しますが、Platho プロトコルアクションは認証済みの ATH 通知メッセージを使用します。外部連携は、Platho の notify フローが汎用の `JettonTransferNotification` を発行すると想定してはなりません。

ATHWallet における送出内部送金は、送信元側の pending 会計と送信元の確認応答によって保護されています。残高は、pending の証明なしにバウンス body から復元されることはありません。

## ATH のライフサイクル

1. `ATHMaster` が `100,000,000 ATH` の固定供給を生成します。
2. トレジャリーデプロイの一度限りの処理が、トレジャリー ATH ウォレットに供給を受け取ります。
3. 供給がアクティビティ、流動性、長期ベスティング、市場安定化に割り当てられます。
4. ユーザーが Vault を通じてメッセージを publish します。
5. publish の成功が `10 ATH` のアクティビティ報酬を計上します。
6. `15,000,000 ATH` のアクティビティエアドロップが完全に配布され `airdrop_remaining_ath == 0` になった後、ATH プロトコル手数料割引がアンロックされます。
7. ATH/GRAM プールが基準価格 `1 ATH = 0.001 GRAM` で立ち上がります。
8. プール後のルート evidence と価格 evidence が凍結されます。
9. MarketStabilitySeller が x2..x21 のトランシェを通じてリザーブを販売します。
10. 分割が有効化された後、FeeAccumulator はプロトコル GRAM 手数料をトレジャリーと buyback の間で分割します。
11. BuybackBurn が GRAM プロトコル手数料で ATH を購入し、ATHMaster を通じて ATH を burn します。
12. ユーザー名およびプロフィール手数料が ATH トレジャリー due と ATH burn due を生成します。
13. 総供給量が認証済みの burn を通じて徐々に減少します。

## 最終モデル

ATH は Platho の 4 つのレイヤーを接続します。

1. **アプリケーション利用** - メッセージがアクティビティ報酬を生成します。
2. **有料機能** - ユーザー名とアバターには ATH が必要です。
3. **割引** - ATH 残高が配布ゲートの後にプロトコル手数料を軽減します。
4. **供給の削減** - ATH 手数料と buyback 出力の一部が ATHMaster を通じて burn されます。

このモデルは固定供給と `100,000 GRAM` の基準評価額から始まります。主要なユーザー配布は実際の有料利用に結び付けられています。メッセージは `0.0337 GRAM` から始まり、現在は 1 KiB の public post で `0.0337 GRAM`、hybrid private 1 KiB カプセルで `0.0347 GRAM`、加えて確定カプセルごとに `10 ATH` のアクティビティボーナスです。より大きな public または private のサイズクラスはより高コストです。そのボーナスは返金、補填、または利益の約束ではありません。供給の最初の 15% が配布された後、プールが立ち上がり、プロトコル手数料割引がアンロックされ、buyback 経路が開かれます。

ATH は Platho の内部で機能するトークンとして存在します。アクティビティを通じて配布され、有料アクションで使用され、プロトコル手数料を軽減し、定義された階段を通じてリザーブから販売され、オンチェーンの burn を通じて burn されます。市場安定化の階段の後、将来の ATH 価格は市場とプロトコルの利用によって決定されます。

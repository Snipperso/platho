# Криптографический протокол сообщений Platho

Этот документ описывает шифрование сообщений на стороне клиента, реализованное статическим PWA-прототипом.

## Наборы шифров

| Набор | Значение в контракте | Назначение |
| --- | ---: | --- |
| `hybrid-v1` | `2` | Приватные сообщения на основе X25519 плюс ML-KEM-768 плюс AES-GCM. |

Публикация приватных сообщений в V1 принимает только `CRYPTO_SUITE_HYBRID = 2`.

## Наборы ключей

Каждая 24-словная фраза восстановления GRAM, созданная или импортированная в PWA, детерминированно порождает мессенджер-идентичность с парой ключей шифрования и подписывающим ключом Ed25519. Публичный ключевой материал шифрования экспортируется как публичный набор ключей:

- `keyId`: идентификатор на основе SHA-256 по публичному ключевому материалу.
- `x25519PublicKey`: 32-байтовый классический публичный ключ ECDH.
- `mlKem768PublicKey`: 1184-байтовый публичный ключ ML-KEM-768 для `hybrid-v1`.
- `mlKem768PublicKeyHash`: SHA-256 от публичного ключа ML-KEM-768.
- `mlKem768PublicKeyLen`: всегда `1184` для `hybrid-v1`.

PWA пересчитывает `keyId`, `mlKem768PublicKeyHash` и `mlKem768PublicKeyLen` перед шифрованием. Набор, который заявляет несовпадающий идентификатор, набор шифров, набор шифров контракта, хеш или длину, отклоняется.

Поиск получателя определяется по on-chain полям `enc_pubkey`, `sign_pubkey` и полной on-chain ячейке `pq_kem_pubkey`, хранящейся в активной ключевой записи Vault. Хеш и длина остаются в записи в качестве компактных связывающих полей, но именно полный публичный ключ ML-KEM-768 позволяет другому клиенту реально зашифровать капсулу `hybrid-v1`.

## Подписанные наборы

PWA может экспортировать подписанный публичный набор ключей. Подписанная полезная нагрузка включает:

- домен протокола `PLATHO.MESSAGING.KEY_BUNDLE.SIGNATURE.V1`;
- метки времени выпуска и необязательного истечения срока;
- необязательные заполнители кошелька-владельца и адреса Vault;
- публичный набор ключей шифрования;
- 32-байтовый публичный подписывающий ключ Ed25519.

Подпись покрывает стабильную JSON-полезную нагрузку и проверяется до того, как набору начинают доверять. Это предотвращает молчаливую локальную подмену набора и даёт клиенту точный `sign_pubkey`, который Vault хранит в `KeyRecord`.

`keyId` в PWA — это клиентский идентификатор набора. Он не заменяет `current_key_id` контракта Vault, который вычисляется on-chain из адреса владельца, поколения ключа, подписывающего ключа, ключа шифрования, PQ-хеша, PQ-длины и набора шифров. Продакшн-клиент обязан проверить набор относительно ключевой записи Vault, прежде чем доверять ему для идентичности кошелька.

Подписанный набор — это самоподпись мессенджер-ключа. Владение кошельком закрепляется активацией в Vault: встроенный кошелёк Platho отправляет `RegisterMessagingKeys`, последующие ротации `ReplaceMessagingKeys` — это внешние сообщения, подписанные авторизацией Vault, а получатели проверяют подписанный набор относительно активной on-chain ключевой записи для этого кошелька.

## Владение кошельком

Продакшн-PWA не использует внешний коннектор кошелька. Пользователь создаёт или импортирует обычную 24-словную фразу восстановления GRAM, и PWA
детерминированно порождает ключ кошелька GRAM, отдельный ключ авторизации Vault и ключи шифрования/подписи сообщений из этой фразы. Активация в Vault
является якорем владения: встроенный кошелёк подписывает и отправляет `RegisterMessagingKeys` с того же кошелька, которому принадлежит on-chain ключевая запись.
`ReplaceMessagingKeys` ротирует только публичную запись ключа приёма/сообщений; он не ротирует ключ авторизации Vault.

Получатели доверяют мессенджер-набору только после его сверки с активной ключевой записью Vault для этого кошелька:

- владелец записи — ожидаемый кошелёк;
- `enc_pubkey` и `sign_pubkey` совпадают с подписанным набором;
- гибридные записи предоставляют полную ячейку `pq_kem_pubkey`, а не только её хеш;
- декодированные байты ключа ML-KEM-768 хешируются в `pq_kem_pubkey_hash`;
- активный `current_key_id` указывает на проверенную ключевую запись.

Поток экспорта/импорта профиля работает с 24-словной фразой восстановления GRAM. В финальной v1 нет отдельного резервного копирования мессенджер-ключа и нет
режима подключения внешнего кошелька.

## Компактная разметка байтов

On-chain ячейки приватных капсул используют финальную бинарную разметку `platho.byte-layout.v1`. PWA может оборачивать капсулы в JSON для UI экспорта/шаринга, но полезная нагрузка протокола — это бинарные байты, а не JSON и не off-chain указатель. `CapsuleHub` хранит компактные аутентифицированные заголовки/индексы плюс хеш тела; зашифрованная ячейка тела остаётся в теле принятой транзакции публикации и реконструируется из истории сообщений TON, после чего проверяется относительно сохранённых хешей.

Каждая публикация проходит через Vault как подписанное внешнее сообщение, финансируемое балансом Vault. Пользователь сначала пополняет свой внутренний
баланс GRAM в Vault, затем PWA подписывает запрос на публикацию активным `auth_pubkey`; ретранслятор может отправить
внешнее сообщение, не владея ключом кошелька или подписывающим мессенджер-ключом. Подписанная полезная нагрузка разделена по доменам с помощью `VPB1`,
`deployment_manifest_hash`, целевого адреса Vault и вида публикации перед владельцем, nonce, максимальным списанием и полезной нагрузкой.
Значение GRAM, которое CapsuleHub фактически возвращает в ACK или bounce, зачисляется на внутренний баланс GRAM пользователя в Vault,
ограниченное отслеживаемой суммой ожидаемого возврата за публикацию. Если баланс Vault или доступ к цепочке недоступны,
PWA завершает работу закрыто и не должен показывать действия публикации.

Поскольку `auth_pubkey` авторизует расходование баланса Vault, компрометация одного лишь локального подписывающего мессенджер-ключа не авторизует
публикацию через Vault, проверку платежей, действия с именем пользователя или аватаром. Компрометация подписывающего мессенджер-ключа всё же может повлиять на подписи идентичности на уровне сообщений,
поэтому замена ключа отзывает старую публичную запись ключа приёма для будущих проверок входящего шифрования.

Тарификация сообщений в PWA — за капсулу. При текущих резервах и без скидки ATH точные канонические примеры: публичные записи размером 1 KiB от `0.0337 GRAM` и приватные
капсулы `hybrid-v1` размером 1 KiB от `0.0347 GRAM`; более крупные классы размера публичных или приватных сообщений стоят больше по каноническому классу. Это включает полную
протокольную комиссию Platho `0.01 GRAM`, отчисление на хранение компактного индекса CapsuleHub, резерв на локальное исполнение Vault и
ожидаемый возврат по ACK. Отдельно, если консервативная оценка комиссии PWA выше включённого допуска на сетевую комиссию
`0.005 GRAM`, она добавляет
округлённое превышение как надбавку. Вызовы контракта всё равно начинаются со своих канонических
требуемых значений: публикации через Vault отправляют `maxCharge = canonical_max_charge + surcharge`. В финальной v1 у CapsuleHub нет прямого пользовательского
ABI публикации; каждая публикация — это Vault -> CapsuleHub. Скидки ATH применяются только после того, как аирдроп за активность в Vault
распределит 15 000 000 ATH; до этого рубежа протокольные комиссии за сообщения используют полную комиссию `0.01 GRAM`. PWA обязан показать финальную
удержанную сумму и чистую стоимость для выбранного размера контента перед подписанием.

Надбавка — это подписанный запас безопасности на сеть/хранение, а не возвращаемая корзина комиссий. CapsuleHub принимает публикации из Vault,
когда приложенное значение не меньше канонического требуемого значения, но успешный ACK публикации возвращает только фиксированный
резерв ACK публикации `30 000 000` нанотонов (`0.030 GRAM`). После того как Vault обработает этот ACK, пользователю зачисляется примерно
`25 800 000` нанотонов на внутренний баланс GRAM в Vault. Любая подписанная надбавка сверх канонического требуемого значения остаётся в
CapsuleHub как избыток резерва сети/хранения; она не возвращается в Vault и не учитывается как
`accrued_plato_fee_ton`.

CapsuleHub защищает сырой резерв GRAM, равный `accrued_plato_fee_ton + max(100 GRAM, 1.25 * live_index_1y_storage_reserve)`.
Живой резерв использует необрезанные счётчики приватных/публичных записей, а не исторические счётчики `latest_id`. Отдельный
беспермиссионный вызов `SweepExcessReserve` может переместить только излишек сверх этой защищённой суммы в FeeAccumulator как
`DepositProtocolFee`, где он следует обычному разделению казна/выкуп. Обычная отправка сообщений не выполняет этот
сбор. Если депозит этого сбора отскакивает (bounce), возвращённая сумма намеренно переклассифицируется как обеспеченный
`accrued_plato_fee_ton`, чтобы её можно было повторить через обычный поток вывода комиссий.
Обычные частичные вызовы `FlushFees` должны быть не меньше текущей публичной протокольной комиссии (`0.010 GRAM`); меньшая сумма
допустима только тогда, когда это вся оставшаяся накопленная корзина, чтобы даже пыль со скидкой можно было финализировать.

CapsuleHub записывает `created_at = now()` для каждой приватной и публичной записи. PWA использует эту метку времени контракта для упорядочивания и для ограниченного поиска по истории транзакций; клиентские метки времени в заголовках остаются аутентифицированными метаданными полезной нагрузки, а не авторитетом обнаружения. Компактные метаданные записи могут быть беспермиссионно обрезаны после настроенного годичного окна хранения, тогда как доступность тела зависит от покрытия истории сообщений выбранным провайдером TON и локального зашифрованного кэша пользователя.

Баланс ATH в Vault зачисляется через явный учёт по потоку уведомлений, а не путём сканирования сырого баланса официального кошелька.
Поддерживаемый путь депозита — это `ATHTransferRequestWithNotify` из ATHWallet пользователя в Vault. Ручной обычный перевод ATH
на официальный ATHWallet Vault не поддерживается и не должен отображаться как адрес депозита или трактоваться как
зачисление в реестр Vault. Вывод ATH из Vault — это подписанная внешняя команда Vault. Её нижестоящий резерв на
развёртывание/перевод/ACK в ATHWallet оплачивается с внутреннего баланса GRAM пользователя в Vault, и Vault зачисляет обратно только
аутентифицированное значение ACK/fail/bounce, которое получает, минус локальный резерв на возврат и ограниченное зарезервированным внутренним значением.

Публичные посты и комментарии — это отдельный открытый профиль, а не приватные капсулы без шифрования. Они хранят компактную
ячейку публичного заголовка `PPH1` плюс сырую ячейку публичного тела. Публичный текст тела и публичные байты изображения/аватара используют те же
классы размера публичной капсулы 1, 2, 4, 8, 16 или 32 KiB, что и видимый пользователю бюджет тела. Метаданные заголовка никогда не уменьшают
этот бюджет тела. У публичных постов нет постквантового варианта; в публичном тексте используется товарная метка `from 0.0337 GRAM`,
тогда как текущий точный публичный базовый пример — `0.0337 GRAM` плюс то же
правило надбавки на сетевую комиссию. `kind = 1` — это публичный пост; бит 0 в `flags` поста закрывает комментарии для этого поста. `kind = 2` — это
одноуровневый публичный комментарий с `parent_entry_id:uint64` и `parent_body_hash:uint256` в заголовке. `kind = 3` — это
публичный пост-изображение, `kind = 4` — это публичный комментарий-изображение, а `kind = 5` — это публичная медиа-аватар кошелька. Публичные заголовки также несут `stream_id:uint128`,
`part_index:uint16`, `part_count:uint16` и `media_format:u8`; публичная v1 использует `media_format = 0` для текста и
`media_format = 1` для частей WebP-изображения/аватара. Заголовки публичного поста, поста-изображения и аватара также несут
`profile_version:uint32` и `avatar_hash:uint256`; ноль означает отсутствие указателя аватара. Длинный публичный текст или данные изображения реконструируются из нескольких записей
только после того, как каждая запись использовала наименьший подходящий публичный класс размера вплоть до 32 KiB. Официальный PWA сжимает выбранные изображения в WebP до целей 8 KiB
(`low`), 16 KiB (`medium`), 32 KiB (`good`, по умолчанию) или 64 KiB (`maximum`) перед разбиением. В v1 нет слоя редактирования/удаления/реакций/модерации или счётчиков.

Аватары кошелька — это платные обновления профиля, а не off-chain активы. Байты аватара публикуются как публичные записи `kind = 5`
в CapsuleHub, затем `ProfileRegistry` записывает аутентифицированный указатель кошелька:
`version`, `avatar_hash`, первый `avatar_entry_id`, `avatar_stream_id`, `avatar_part_count` и `media_format`. Читатели
разрешают указатель профиля из подписанного приватного заголовка или заголовка публичного поста, проверяют соответствующую запись ProfileRegistry,
извлекают публичные записи аватара из CapsuleHub, конкатенируют части в порядке индекса и требуют, чтобы реконструированные
байты WebP хешировались в `avatar_hash`. Локальный кэш аватара — это лишь ускорение; источник истины — это CapsuleHub плюс
ProfileRegistry.

`header0_cell` хранит ровно 140 байт:

```text
PH0B
|| version:u8
|| publish_kind:u8
|| size_class:u8
|| crypto_suite:u8
|| sender_key_id:32 bytes
|| recipient_key_id:32 bytes
|| sender_sign_pubkey:32 bytes
|| profile_version:uint32
|| avatar_hash:uint256
```

`header1_cell` хранит ровно 30 байт:

```text
PH1B
|| version:u8
|| flags:u8 = 0
|| created_at_s:u32
|| expires_at_s:u32
|| client_nonce:16 bytes
```

`size_class + crypto_suite` подразумевают набор шифров. `profile_version` и `avatar_hash` указывают на аватар кошелька-отправителя на
момент отправки и покрываются хешем заголовка плюс подписью отправителя. `recipient_sign_pubkey` и хеши тредов
намеренно не хранятся в ячейках публичных заголовков. Данные тредов/группировки принадлежат внутри зашифрованных метаданных капсулы.

Каждое зашифрованное тело собирается как:

```text
PLB1 || version:u8 || suite:u8 || flags:u8 || reserved:u8
     || message_id:u128
     || aes_gcm_nonce:12 bytes
     || x25519_ephemeral_public:32 bytes
     || ml_kem_768_ciphertext:1088 bytes, only for hybrid-v1
     || aes_gcm_ciphertext_and_tag
```

Открытый текст AES-GCM — это один фиксированный слот капсулы, выбранный по `size_class`:

```text
PCP1
|| version:u8
|| kind:u8
|| flags:u8
|| media_format:u8
|| stream_id:u128
|| part_index:u16
|| part_count:u16
|| content_len:u16
|| reserved:u16
|| payload[useful_size]
```

Полезная область контента дополняется до выбранного класса приватной капсулы 1, 2, 4, 8, 16 или 32 KiB. Сообщение с 1 байтом, 500 байтами или 1024 байтами полезного текста имеет одинаковый размер зашифрованного открытого текста в классе 1 KiB. Сообщения сверх выбранного класса разбиваются на независимые капсулы с зашифрованными метаданными `stream_id`, `part_index` и `part_count`. Одна капсула никогда не смешивает несвязанные текст/изображение; получатель собирает независимые капсулы обратно в исходное сообщение.

Виды контента:

- `1` текст: байты UTF-8, вплоть до выбранного полезного размера приватной капсулы.
- `2` изображение: сжатые байты изображения, вплоть до выбранного полезного размера приватной капсулы; `media_format` — это `1` WebP, `2` AVIF, `3` JPEG или `4` PNG.
- `3` платёжный чек: `asset:u8 || reserved:u8 || amount:u128 || intent_id:uint256 || secret32:uint256`.

Тела платёжных чеков намеренно не включают `tx`, время активации или срок истечения. Получатель забирает чек по `intent_id + secret32`; если отправитель уже отменил чек или он уже был получен, интерфейс сообщает, что чек уже получен или отменён отправителем.

Зашифрованное тело может быть обёрнуто для экспорта/шаринга как:

```text
PLC1 || version:u8 || suite:u8 || chunk_index:u8 || chunk_total:u8 || message_id:u128 || body_slice
```

Для финального тела капсулы `chunk_total` всегда равен `1`. `PLC1` — это только упаковочный/экспортный каркас. Принятая транзакция публикации Vault -> CapsuleHub несёт собранные байты тела `PLB1` в snake-ячейке; CapsuleHub сохраняет только компактные аутентифицированные метаданные и хеши.

Канонический источник для этой разметки — `artifacts/PLATHO_CAPSULE_V1_FINAL_SPEC.md`.

AES-GCM использует 12-байтовый nonce и 16-байтовый тег. Длина шифртекста равна длине открытого текста плюс тег.

Компактный префикс тела, `header0Hash` и `header1Hash` передаются как дополнительные аутентифицируемые данные (AAD) AES-GCM. Изменение бинарных маршрутизирующих заголовков, набора шифров, nonce, шифртекста KEM, байтов чанка или подписи отправителя приводит к сбою проверки или расшифровки.

Перед расшифровкой клиент также проверяет:

- набор шифров компактного тела совпадает с `header0`;
- идентификатор ключа получателя совпадает с `header0.recipientKeyId`;
- тела `hybrid-v1` действительно несут 1088-байтовый шифртекст ML-KEM;
- каждый чанк имеет одинаковый набор шифров, идентификатор сообщения и общее число чанков.

## Порождение ключей

Для `hybrid-v1`:

```text
x25519_secret = X25519(sender_ephemeral_secret, recipient_x25519_public)
mlkem_secret  = ML-KEM-768.Encapsulate(recipient_mlkem_public)
message_key   = HKDF-SHA-256(x25519_secret || mlkem_secret, compact_aad_hash)
```

Открытый текст шифруется с помощью AES-256-GCM.

Реализация отклоняет полностью нулевые общие секреты X25519, чтобы не принимать публичные ключи низкого порядка.

## Приватные зашифрованные капсулы

Клиент оборачивает компактные зашифрованные тела в приватную капсулу перед публикацией. Приватная капсула имеет:

- `header0`: 140-байтовый бинарный маршрутизирующий заголовок `PH0B`, описанный выше.
- `header1`: 30-байтовый бинарный заголовок защиты от повторов `PH1B`, описанный выше.
- `body`: метаданные чанков `platho.byte-layout.v1` плюс бинарные чанки в кодировке base64url.
- `hashes`: значения TON `Cell.hash()` для точных on-chain ячеек, содержащих `header0`, `header1` и зашифрованные байты тела.
- `chainCells`: полезные нагрузки BOC в base64 с использованием `ton-snake-byte-cell.v1`; это ячейки, принимаемые в транзакции публикации Vault -> CapsuleHub и аутентифицируемые `CapsuleHub`, а не off-chain указатель.
- `senderSignature`: подпись Ed25519 по идентификатору капсулы и всем трём хешам.

Для `hybrid-v1` капсула использует гибридный профиль CapsuleHub:

```text
size_class   in {1,2,4,8,16,32}
crypto_suite = 2
```

Черновик приватной капсулы отображается на тело `PublishPrivateFromVault` (Vault -> CapsuleHub) после того, как подписанный
внешний запрос `PublishPrivateFromVaultBalance` принят Vault:

```text
header_0_hash = Cell.hash(header_0_cell)
header_1_hash = Cell.hash(header_1_cell)
body_hash     = Cell.hash(body_cell)
header_0_cell = snake-cell(header0 bytes)
header_1_cell = snake-cell(header1 bytes)
body_cell     = snake-cell(compact encrypted body bytes)
```

Сообщения публикации Vault несут `protocol_fee_paid`, потому что Vault — это авторитет скидок для тарификации, обеспеченной ATH.

Ёмкость полезной нагрузки — это ёмкость зашифрованных байтов тела, которые фактически сериализуются в `body_cell` и принимаются `CapsuleHub`. Хеш без соответствующего тела принятой транзакции публикации не является читаемым сообщением v1. Локальная история — это только кэш; она не определяет доставку в v1.

Для подписи внешней публикации Vault порядок ссылок на хеши остаётся совместимым с контрактом:

```text
body_hash || header_0_hash || header_1_hash
```

Компактное тело привязывается к `header0Hash` и `header1Hash` через AAD AES-GCM. Замена заголовков, чанков тела, метаданных набора шифров, подписи отправителя, контекста капсулы или ячеек полезной нагрузки BOC приводит к сбою проверки до того, как сообщение будет принято.

## Источник истины доставки

Принятые приватные сообщения v1 — это компактные записи CapsuleHub плюс зашифрованные ячейки полезной нагрузки, переносимые телом принятой транзакции публикации. PWA извлекает эти ячейки из истории сообщений TON и проверяет их относительно хешей CapsuleHub перед расшифровкой. Продакшн-PWA не предоставляет ручной обмен JSON-пакетами публичных наборов или зашифрованных капсул.

Публичные мессенджер-ключи регистрируются в ключевых записях `Vault`. Отправитель обязан разрешить и проверить ключевую запись получателя перед шифрованием приватной капсулы. Локальная зашифрованная история — это только кэш устройства; она не определяет доставку.

Авторитет имени пользователя `.ath` состоит из двух частей. `UsernameRegistry.get_name_record` доказывает, что имя существует и указывает на
точный `UsernameNFTItem` для этого имени. Текущий владелец затем считывается из состояния этого item. Переводы меняют владельца
item; запись реестра остаётся якорем «имя-к-item». Item предоставляет стандартные данные NFT и on-chain метаданные TEP-64,
включая `name = <username>.ath`, без серверного URI метаданных. Байты имени пользователя в V1 намеренно
буквальны: имена с ведущими, замыкающими, последовательными и полностью состоящими из разделителей символами валидны, когда каждый байт входит в разрешённый набор `a-z`,
`0-9`, `_`, `-`, а длина составляет 4..16. Если ожидающий минт становится устаревшим после
пропущенного ACK item, `PrunePendingUsernameMint` в v1 неразрушающий: он доказывает устаревшее условие, но не удаляет
ожидающее состояние и не создаёт задолженность на возврат. Развёрнутый item становится авторитетным именем пользователя только после того, как реестр финализирует
соответствующую запись имени через валидный поздний ACK или `ResendDeployedAck`. Клиенты и индексаторы обязаны игнорировать притязания на владение только на уровне item
и не должны использовать владельца записи реестра как текущего владельца после переводов.

24-словная фраза восстановления GRAM — это единственный секрет пользователя. PWA детерминированно порождает ключ кошелька GRAM и ключи шифрования/подписи сообщений из этой фразы. Поэтому поток экспорта/импорта профиля работает только с фразой восстановления; отдельного резервного копирования мессенджер-ключа нет.

## Политика защиты от повторов и истечения срока

Приватные капсулы по умолчанию имеют TTL 24 часа и ограничены сверху 30 днями. Живая/off-chain проверка пакета капсулы отклоняет:

- капсулы, созданные слишком далеко в будущем;
- истёкшие капсулы;
- TTL выше предела политики;
- дублированные идентификаторы капсул в предоставленном вызывающей стороной кэше защиты от повторов.

Импорт истории цепочки устроен иначе: когда приватная запись уже принята CapsuleHub и тело восстановлено из
принятой истории транзакций TON или локального зашифрованного кэша, PWA проверяет хеши записи, ячейки тела/заголовков и
расшифровку, но не отклоняет её лишь потому, что срок истечения в заголовке в прошлом. Иначе сохранённая история цепочки
по замыслу стала бы нечитаемой.

Кэш защиты от повторов — это локальное состояние; продакшн-клиенты могут подкреплять его IndexedDB или другим локальным хранилищем устройства. Бэкенд не требуется.

## Правило отсутствия бэкенда

Слой шифрования не требует бэкенда Platho. Сервер может хостить статические файлы, но приватная доставка закрепляется состоянием цепочки `CapsuleHub` плюс телами принятых транзакций публикации: компактная запись доказывает хеши, а тело всё равно должно быть доступно из истории сообщений TON или локального зашифрованного кэша пользователя. Сервер никогда не получает открытый текст, приватные ключи или серверный секрет сессии.

## Черновик регистрации в Vault

Клиент может вывести черновик `RegisterMessagingKeys` из проверенного подписанного набора:

- `enc_pubkey`: 32-байтовый публичный ключ X25519 как uint256.
- `sign_pubkey`: 32-байтовый публичный подписывающий ключ Ed25519 как uint256.
- `auth_pubkey`: отдельный 32-байтовый публичный ключ авторизации Vault Ed25519 как uint256.
- `pq_kem_pubkey_hash`: SHA-256 от публичного ключа ML-KEM-768.
- `pq_kem_pubkey_len`: `1184`.
- `pq_kem_pubkey`: каноническая snake-ячейка, содержащая ровно 1184 байта публичного ключа ML-KEM-768.
- `crypto_suite_mask`: `2` для `hybrid-v1`.

Этот черновик подаётся через поток активации встроенного кошелька Platho. После того как кошелёк активирован в Vault, другие активированные пользователи могут разрешить его запись публичного мессенджер-ключа и шифровать приватные капсулы для него.

## Привязка к ключевой записи Vault

После того как кошелёк зарегистрировал ключи on-chain, клиент обязан извлечь:

- `UserState.current_key_id` кошелька;
- для собственного разблокированного кошелька пользователя — `UserState.auth_pubkey`, совпадающий с локально выведенным публичным ключом авторизации Vault;
- `VaultKeyRecordView` для этого идентификатора ключа.

PWA предоставляет это как fail-closed мост провайдера в `web/vault-chain-provider.mjs`. Мост ожидает провайдера с:

```js
{
  async getUser(ownerWallet) {},
  async getKeyRecord(currentKeyId) {},
}
```

Если провайдер не настроен, привязка к Vault остаётся недоступной, а не принимает локальный черновик или UI-заполнитель. Продакшн/статическое развёртывание может установить провайдера в `globalThis.plathoVaultChainProvider`, который читает развёрнутый Vault через зеркало TON API или транспорт, совместимый с лёгким клиентом.

Статическая среда выполнения включает `web/vault-ton-rpc-provider.mjs` как скелет продакшн-провайдера. Он может оборачивать эндпоинты, совместимые с TON Center v3, или пользовательский `globalThis.plathoTonRpcTransport`, установленный хост-бандлом. Текущий PWA не предоставляет встроенного экрана пользовательских настроек RPC; если документация утверждает, что RPC выбирается пользователем, этот UI обязан существовать. Провайдер:

- кодирует адреса владельца `get_user(owner)` как элементы стека `slice` BoC;
- вызывает `get_key_record(current_key_id)` с числовым элементом стека;
- декодирует стеки геттеров в `VaultUserView` и `VaultKeyRecordView`;
- завершает работу закрыто, если RPC-транспорт, адрес Vault, ответ геттера или привязка ключевой записи недоступны.

Клиентский верификатор проверяет, что активная запись Vault совпадает с проверенным подписанным набором:

- `owner_wallet` совпадает с адресом встроенного кошелька Platho;
- `enc_pubkey` совпадает с публичным ключом X25519;
- `sign_pubkey` совпадает с подписывающим публичным ключом набора;
- `pq_kem_pubkey`, `pq_kem_pubkey_hash` и `pq_kem_pubkey_len` совпадают с материалом ML-KEM-768;
- `crypto_suite_mask` совпадает с набором шифров;
- `revoked_lt` равен нулю;
- необязательный `current_key_id` указывает на извлечённый идентификатор записи.

Клиент не выдумывает on-chain идентификатор ключа. Vault вычисляет его из адреса владельца, поколения ключа, полей ключа, PQ-длины и набора шифров. Вместо этого клиент проверяет извлечённую запись.

## Долговечное хранилище защиты от повторов

PWA использует IndexedDB для защиты приватных капсул от повторов, когда он доступен, с запасным вариантом в памяти. Хранилище держит идентификаторы капсул до истечения их срока и локально обрезает истёкшие записи. Это локальное состояние устройства, и оно не требует сервера.

## Зашифрованная локальная история сообщений

У PWA также есть локальное зашифрованное хранилище истории сообщений на устройстве. Оно использует неизвлекаемый ключ WebCrypto AES-GCM-256, сохранённый в IndexedDB, и хранит каждое тело сообщения как аутентифицированный шифртекст. Заголовок записи хранит только локальные метаданные запросов: id, id треда, метку времени, направление и необязательный id капсулы.

Заголовок привязывается как дополнительные аутентифицируемые данные AES-GCM. Изменение id треда, метки времени, направления, id капсулы, nonce или шифртекста не даёт записи открыться. Если IndexedDB недоступен, приложение переходит на зашифрованную историю в памяти для этой сессии и избегает записи открытого текста в постоянное хранилище браузера.

## Статус продакшна

Путь релиза в mainnet использует порождение встроенного кошелька GRAM, мессенджер-ключи, закреплённые в Vault, валидацию подписанного набора, fail-closed привязку к цепочке Vault, хеширование ячеек приватных капсул, подписи отправителя, долговечное хранилище защиты от повторов, зашифрованную локальную историю сообщений и экспорт/импорт фразы восстановления. Продакшн-развёртывание обязано держать конфигурацию PWA привязанной к проверенному манифесту mainnet и одобренным провайдерам TON RPC; независимый криптографический аудит по-прежнему рекомендуется для долгосрочной уверенности.

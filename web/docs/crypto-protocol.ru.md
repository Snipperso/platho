# Криптографический протокол сообщений Platho

Этот документ описывает клиентское шифрование сообщений, реализованное в Platho PWA.

## Шифрование

Приватные сообщения используют X25519 + ML-KEM-768 + AES-GCM — единственный набор шифрования приватных сообщений (`hybrid-v1`, значение в контракте `2`).

## Пакеты ключей

Каждая 24-словная фраза восстановления GRAM, созданная или импортированная в PWA, детерминированно порождает идентичность для обмена сообщениями с парой ключей шифрования и подписывающим ключом Ed25519. Публичный ключевой материал шифрования экспортируется как публичный пакет ключей:

- `keyId`: идентификатор на основе SHA-256, вычисленный по публичному ключевому материалу.
- `x25519PublicKey`: 32-байтовый классический публичный ключ ECDH.
- `mlKem768PublicKey`: 1184-байтовый публичный ключ ML-KEM-768 для `hybrid-v1`.
- `mlKem768PublicKeyHash`: SHA-256 публичного ключа ML-KEM-768.
- `mlKem768PublicKeyLen`: всегда `1184` для `hybrid-v1`.

PWA пересчитывает `keyId`, `mlKem768PublicKeyHash` и `mlKem768PublicKeyLen` перед шифрованием. Пакет, заявляющий несоответствующий идентификатор, набор, набор из контракта, хеш или длину, отвергается.

Поиск получателя определяется по хранящимся в активной записи ключа Vault значениям `enc_pubkey`, `sign_pubkey` и полной он-чейн ячейке `pq_kem_pubkey`. Хеш и длина остаются в записи в качестве компактных связующих полей, но именно полный публичный ключ ML-KEM-768 позволяет другому клиенту действительно зашифровать капсулу `hybrid-v1`.

## Подписанные пакеты

PWA может экспортировать подписанный публичный пакет ключей. Подписываемая полезная нагрузка включает:

- домен протокола `PLATHO.MESSAGING.KEY_BUNDLE.SIGNATURE.V1`;
- метки времени выпуска и необязательного истечения;
- необязательные заполнители адреса кошелька владельца и адреса Vault;
- публичный пакет шифрования;
- 32-байтовый публичный подписывающий ключ Ed25519.

Подпись покрывает стабильную полезную нагрузку JSON и проверяется до того, как пакету начинают доверять. Это предотвращает тихую локальную подделку пакета и даёт клиенту точный `sign_pubkey`, который Vault хранит в `KeyRecord`.

`keyId` в PWA — это клиентский идентификатор пакета. Он не заменяет `current_key_id` контракта Vault, который вычисляется он-чейн из адреса владельца, поколения ключа, подписывающего ключа, ключа шифрования, PQ-хеша, PQ-длины и набора шифрования. Продакшн-клиент обязан проверить пакет по записи ключа Vault, прежде чем доверять ему для идентичности кошелька.

Подписанный пакет — это самоподпись ключа для обмена сообщениями. Владение кошельком закрепляется активацией Vault: встроенный кошелёк Platho отправляет `RegisterMessagingKeys`, последующие ротации `ReplaceMessagingKeys` являются внешними сообщениями, подписанными Vault-авторизацией, а получатели проверяют подписанный пакет по активной он-чейн записи ключа для этого кошелька.

## Владение кошельком

Продакшн-PWA не использует внешний коннектор кошелька. Пользователь создаёт или импортирует обычную 24-словную фразу восстановления GRAM, и PWA
детерминированно порождает из этой фразы ключ кошелька GRAM, отдельный ключ авторизации Vault и ключи шифрования/подписи для обмена сообщениями. Активация
Vault является якорем владения: встроенный кошелёк подписывает и отправляет `RegisterMessagingKeys` с того же кошелька, который владеет он-чейн записью ключа.
`ReplaceMessagingKeys` ротирует только публичную запись ключа приёма/обмена сообщениями; он не ротирует ключ авторизации Vault.

Получатели доверяют пакету для обмена сообщениями только после проверки его по активной записи ключа Vault для этого кошелька:

- владелец записи является ожидаемым кошельком;
- `enc_pubkey` и `sign_pubkey` соответствуют подписанному пакету;
- гибридные записи раскрывают полную ячейку `pq_kem_pubkey`, а не только её хеш;
- декодированные байты ключа ML-KEM-768 хешируются в `pq_kem_pubkey_hash`;
- активный `current_key_id` указывает на проверенную запись ключа.

Поток экспорта/импорта профиля обрабатывает 24-словную фразу восстановления GRAM. Отдельной резервной копии ключа для обмена сообщениями нет, как нет и
режима подключения внешнего кошелька.

## Компактная байтовая раскладка

Он-чейн ячейки приватной капсулы используют финальную бинарную раскладку `platho.byte-layout.v1`. PWA может оборачивать капсулы в JSON для UI экспорта/шеринга, но полезная нагрузка протокола — это бинарные байты, а не JSON и не офф-чейн указатель. `CapsuleHub` хранит компактные аутентифицированные заголовки/индексы плюс хеш тела; ячейка зашифрованного тела остаётся в теле принятой транзакции публикации и восстанавливается из истории сообщений TON, после чего проверяется по сохранённым хешам.

Каждая публикация проходит через Vault как подписанное внешнее сообщение, финансируемое из баланса Vault. Пользователь сначала пополняет свой внутренний
GRAM-баланс Vault, затем PWA подписывает запрос публикации активным `auth_pubkey`; релеер может отправить
внешнее сообщение, не владея ключом кошелька или подписывающим ключом для обмена сообщениями. Подписываемая полезная нагрузка домен-разделена префиксом `VPB1`,
`deployment_manifest_hash`, целевым адресом Vault и видом публикации перед владельцем, nonce, максимальным списанием и полезной нагрузкой.
GRAM-значение, которое CapsuleHub фактически возвращает в ACK или отскоке, зачисляется на внутренний GRAM-баланс Vault
пользователя, ограниченный отслеживаемой суммой ожидающего возврата за публикацию. Если баланс Vault или доступ к цепочке недоступны,
PWA отказывает по принципу fail-closed и не должен открывать действия публикации.

Поскольку `auth_pubkey` авторизует расходование баланса Vault, компрометация одного лишь локального подписывающего ключа для обмена сообщениями не авторизует
публикацию в Vault, проверку платежа, действия с именем пользователя или аватаром. Компрометация подписывающего ключа для обмена сообщениями всё же может повлиять на
подписи идентичности на уровне сообщений, поэтому замена ключа отзывает старую публичную запись ключа приёма для будущих проверок входящего шифрования.

Ценообразование сообщений PWA — за капсулу. При текущих резервах и без скидки ATH точные канонические примеры таковы: публичные записи 1 KiB от `0.0337 GRAM` и приватные
капсулы `hybrid-v1` 1 KiB от `0.0347 GRAM`; более крупные публичные или приватные классы размера стоят дороже по каноническому классу. Это включает полную
протокольную комиссию Platho `0.01 GRAM`, эндаумент хранения компактного индекса CapsuleHub, резерв локального исполнения Vault и
ожидаемый возврат по ACK. Отдельно, если консервативная оценка комиссии PWA выше включённого допуска сетевой комиссии
`0.005 GRAM`, он добавляет
округлённое превышение в виде надбавки. Вызовы контрактов всё равно начинаются со своих канонических
требуемых значений: публикации Vault отправляют `maxCharge = canonical_max_charge + surcharge`. У CapsuleHub нет прямого пользовательского
ABI публикации; каждая публикация — это Vault -> CapsuleHub. Скидки ATH применяются только после того, как аирдроп за активность Vault
раздал 15,000,000 ATH; до этого рубежа протокольные комиссии за сообщения используют полную комиссию `0.01 GRAM`. PWA обязан показать финальное
удержание и чистую стоимость для выбранного размера контента перед подписанием.

Надбавка — это подписанный запас безопасности на сеть/хранение, а не возвращаемая корзина комиссии. CapsuleHub принимает публикации Vault,
когда прикреплённое значение не меньше канонического требуемого значения, но успешный ACK публикации возвращает лишь фиксированный
резерв ACK публикации `30,000,000` нанотонов (`0.030 GRAM`). После того как Vault обрабатывает этот ACK, пользователю зачисляется примерно
`25,800,000` нанотонов на внутренний GRAM-баланс Vault. Любая подписанная надбавка сверх канонического требуемого значения остаётся в
CapsuleHub как избыток сетевого/хранилищного резерва; она не возвращается в Vault и не учитывается как
`accrued_plato_fee_ton`.

CapsuleHub защищает сырой резерв GRAM, равный `accrued_plato_fee_ton + max(100 GRAM, 1.25 * live_index_1y_storage_reserve)`.
Живой резерв использует необрезанные счётчики приватных/публичных записей, а не исторические счётчики `latest_id`. Отдельный
беспермиссионный вызов `SweepExcessReserve` может переместить в FeeAccumulator только излишек сверх этой защищённой суммы как
`DepositProtocolFee`, где он следует обычному разделению treasury/buyback. Обычная отправка сообщений эту
подметку не выполняет. Если этот депозит подметки отскакивает, возвращённая сумма намеренно переклассифицируется как обеспеченный
`accrued_plato_fee_ton`, чтобы её можно было повторить через обычный поток сброса комиссий.
Обычные частичные вызовы `FlushFees` должны быть не меньше текущей публичной протокольной комиссии (`0.010 GRAM`); меньшая сумма
допустима только когда это вся оставшаяся начисленная корзина, так что дисконтированную пыль всё равно можно финализировать.

CapsuleHub записывает `created_at = now()` для каждой приватной и публичной записи. PWA использует эту метку времени контракта для упорядочивания и для ограниченного поиска по истории транзакций; клиентские метки времени заголовков остаются аутентифицированными метаданными полезной нагрузки, а не авторитетом обнаружения. Компактные метаданные записи можно беспермиссионно обрезать после настроенного годичного окна хранения, тогда как доступность тела зависит от покрытия истории сообщений выбранным провайдером TON и локального зашифрованного кэша пользователя.

ATH-баланс Vault зачисляется через явный учёт по потоку уведомлений, а не сканированием сырого баланса официального кошелька.
Поддерживаемый путь депозита — `ATHTransferRequestWithNotify` из ATHWallet пользователя в Vault. Ручной обычный ATH-перевод
на официальный ATHWallet Vault не поддерживается и не должен отображаться как адрес депозита или трактоваться как
зачисление в реестр Vault. Вывод ATH из Vault — это подписанная внешняя команда Vault. Её нижестоящий резерв на
деплой/перевод/ACK ATHWallet оплачивается из внутреннего GRAM-баланса Vault пользователя, а Vault зачисляет обратно только
аутентифицированное значение ACK/fail/bounce, которое он получает, за вычетом локального резерва на возврат и с ограничением зарезервированным внутренним значением.

Публичные посты и комментарии — это отдельный открытый профиль, а не приватные капсулы без шифрования. Они хранят компактную
ячейку публичного заголовка `PPH1` плюс сырую ячейку публичного тела. Текст публичного тела и байты публичного изображения/аватара используют те же
классы размера публичной капсулы 1, 2, 4, 8, 16 или 32 KiB, что и видимый пользователю бюджет тела. Метаданные заголовка никогда не уменьшают
этот бюджет тела. У публичных постов нет постквантовой опции; публичные сообщения начинаются от `0.0337 GRAM`,
тогда как текущий точный пример публичной базы — `0.0337 GRAM` плюс то же правило надбавки за
сетевую комиссию. `kind = 1` — публичный пост; бит 0 в `flags` поста закрывает комментарии для этого поста. `kind = 2` —
одноуровневый публичный комментарий с `parent_entry_id:uint64` и `parent_body_hash:uint256` в заголовке. `kind = 3` —
публичный пост с изображением, `kind = 4` — публичный комментарий с изображением, а `kind = 5` — публичная медиа аватара кошелька. Публичные заголовки также несут `stream_id:uint128`,
`part_index:uint16`, `part_count:uint16` и `media_format:u8`; публичные заголовки используют `media_format = 0` для текста и
`media_format = 1` для WebP-частей изображения/аватара. Заголовки публичного поста, поста с изображением и аватара также несут
`profile_version:uint32` и `avatar_hash:uint256`; ноль означает отсутствие указателя аватара. Длинный публичный текст или данные изображения восстанавливаются из нескольких записей
только после того, как каждая запись использовала наименьший подходящий публичный класс размера вплоть до 32 KiB. Официальный PWA сжимает выбранные изображения в WebP с целями 8 KiB
(`low`), 16 KiB (`medium`), 32 KiB (`good`, по умолчанию) или 64 KiB (`maximum`) перед разбиением. Нет слоя редактирования/удаления/реакций/модерации или счётчиков.

Аватары кошелька — это платные обновления профиля, а не офф-чейн ассеты. Байты аватара публикуются как публичные записи CapsuleHub `kind = 5`,
после чего `ProfileRegistry` записывает аутентифицированный указатель кошелька:
`version`, `avatar_hash`, первый `avatar_entry_id`, `avatar_stream_id`, `avatar_part_count` и `media_format`. Читатели
разрешают указатель профиля из подписанного приватного заголовка или заголовка публичного поста, проверяют соответствующую запись ProfileRegistry,
забирают публичные записи аватара из CapsuleHub, конкатенируют части в порядке индексов и требуют, чтобы восстановленные
байты WebP хешировались в `avatar_hash`. Локальный кэш аватара — лишь ускорение; источником истины является CapsuleHub плюс
ProfileRegistry.

`header0_cell` хранит ровно 140 байт:

```text
PH0B
|| version:u8
|| publish_kind:u8
|| size_class:u8
|| crypto_suite:u8
|| sender_key_id:32 bytes
|| recipient_key_id:32 bytes
|| sender_sign_pubkey:32 bytes
|| profile_version:uint32
|| avatar_hash:uint256
```

`header1_cell` хранит ровно 30 байт:

```text
PH1B
|| version:u8
|| flags:u8 = 0
|| created_at_s:u32
|| expires_at_s:u32
|| client_nonce:16 bytes
```

`size_class + crypto_suite` подразумевают набор. `profile_version` и `avatar_hash` указывают на аватар кошелька отправителя на
момент отправки и покрыты хешем заголовка плюс подписью отправителя. `recipient_sign_pubkey` и хеши треда
намеренно не хранятся в публичных ячейках заголовка. Данные треда/группировки принадлежат внутри зашифрованных метаданных капсулы.

Каждое зашифрованное тело собирается как:

```text
PLB1 || version:u8 || suite:u8 || flags:u8 || reserved:u8
     || message_id:u128
     || aes_gcm_nonce:12 bytes
     || x25519_ephemeral_public:32 bytes
     || ml_kem_768_ciphertext:1088 bytes, only for hybrid-v1
     || aes_gcm_ciphertext_and_tag
```

Открытый текст AES-GCM — это один фиксированный слот капсулы, выбранный по `size_class`:

```text
PCP1
|| version:u8
|| kind:u8
|| flags:u8
|| media_format:u8
|| stream_id:u128
|| part_index:u16
|| part_count:u16
|| content_len:u16
|| reserved:u16
|| payload[useful_size]
```

Полезная область контента дополняется до выбранного класса приватной капсулы 1, 2, 4, 8, 16 или 32 KiB. Сообщение из 1 байта, 500 байт или 1024 байт полезного текста имеет одинаковый размер зашифрованного открытого текста в классе 1 KiB. Сообщения сверх выбранного класса разбиваются на независимые капсулы с зашифрованными метаданными `stream_id`, `part_index` и `part_count`. Одна капсула никогда не смешивает несвязанные текстовые/графические единицы; получатель собирает независимые капсулы обратно в исходное сообщение.

Виды контента:

- `1` текст: байты UTF-8, вплоть до выбранного полезного размера приватной капсулы.
- `2` изображение: сжатые байты изображения WebP, вплоть до выбранного полезного размера приватной капсулы (`media_format = 1`).
- `3` платёжный чек: `asset:u8 || reserved:u8 || amount:u128 || intent_id:uint256 || secret32:uint256`.

Тела платёжных чеков намеренно не включают `tx`, время активации или истечение. Получатель забирает по `intent_id + secret32`; если отправитель уже отменил чек или он уже был забран, UI сообщает, что чек уже забран или отменён отправителем.

Зашифрованное тело может быть обёрнуто для экспорта/шеринга как:

```text
PLC1 || version:u8 || suite:u8 || chunk_index:u8 || chunk_total:u8 || message_id:u128 || body_slice
```

Для финального тела капсулы `chunk_total` всегда равен `1`. `PLC1` — это только упаковочное/экспортное обрамление. Принятая транзакция публикации Vault -> CapsuleHub несёт собранные байты тела `PLB1` в snake-ячейке; CapsuleHub сохраняет только компактные аутентифицированные метаданные и хеши.

Финальные приватные лимиты:

| Набор | Полезный предел на капсулу | Байты тела | Байты экспортного чанка |
| --- | ---: | ---: | ---: |
| `hybrid-v1` | 1 KiB | 2,228 bytes | 2,252 bytes |
| `hybrid-v1` | 2 KiB | 3,252 bytes | 3,276 bytes |
| `hybrid-v1` | 4 KiB | 5,300 bytes | 5,324 bytes |

Канонический источник этой раскладки — `artifacts/PLATHO_CAPSULE_V1_FINAL_SPEC.md`.

AES-GCM использует 12-байтовый nonce и 16-байтовый tag. Длина шифротекста равна длине открытого текста плюс tag.

Компактный префикс тела, `header0Hash` и `header1Hash` передаются как дополнительные аутентифицированные данные AES-GCM. Изменение бинарных маршрутизирующих заголовков, набора, nonce, шифротекста KEM, байтов чанка или подписи отправителя приводит к сбою проверки или расшифровки.

Перед расшифровкой клиент также проверяет:

- набор компактного тела соответствует `header0`;
- идентификатор ключа получателя соответствует `header0.recipientKeyId`;
- тела `hybrid-v1` действительно несут 1088-байтовый шифротекст ML-KEM;
- каждый чанк имеет одинаковые набор, идентификатор сообщения и общее число чанков.

## Порождение ключей

Для `hybrid-v1`:

```text
x25519_secret = X25519(sender_ephemeral_secret, recipient_x25519_public)
mlkem_secret  = ML-KEM-768.Encapsulate(recipient_mlkem_public)
message_key   = HKDF-SHA-256(x25519_secret || mlkem_secret, compact_aad_hash)
```

Открытый текст шифруется с помощью AES-256-GCM.

Реализация отвергает нулевые общие секреты X25519, чтобы не принимать публичные ключи низкого порядка.

## Приватные зашифрованные капсулы

Клиент оборачивает компактные зашифрованные тела в приватную капсулу перед публикацией. Приватная капсула имеет:

- `header0`: 140-байтовый бинарный маршрутизирующий заголовок `PH0B`, описанный выше.
- `header1`: 30-байтовый бинарный заголовок защиты от повтора `PH1B`, описанный выше.
- `body`: метаданные чанков `platho.byte-layout.v1` плюс бинарные чанки, закодированные в base64url.
- `hashes`: значения TON `Cell.hash()` для точных он-чейн ячеек, содержащих `header0`, `header1` и байты зашифрованного тела.
- `chainCells`: полезные нагрузки BOC в base64, использующие `ton-snake-byte-cell.v1`; это ячейки, принятые в транзакции публикации Vault -> CapsuleHub и аутентифицированные `CapsuleHub`, а не офф-чейн указатель.
- `senderSignature`: подпись Ed25519 по идентификатору капсулы и всем трём хешам.

Для `hybrid-v1` капсула использует гибридный профиль CapsuleHub:

```text
size_class   in {1,2,4,8,16,32}
crypto_suite = 2
```

Черновик приватной капсулы отображается в тело Vault -> CapsuleHub `PublishPrivateFromVault` после того, как подписанный
внешний запрос `PublishPrivateFromVaultBalance` принят Vault:

```text
header_0_hash = Cell.hash(header_0_cell)
header_1_hash = Cell.hash(header_1_cell)
body_hash     = Cell.hash(body_cell)
header_0_cell = snake-cell(header0 bytes)
header_1_cell = snake-cell(header1 bytes)
body_cell     = snake-cell(compact encrypted body bytes)
```

Сообщения публикации Vault несут `protocol_fee_paid`, потому что Vault является авторитетом скидок для ценообразования, обеспеченного ATH.

Полезная ёмкость нагрузки — это ёмкость байтов зашифрованного тела, которые фактически сериализуются в `body_cell` и принимаются `CapsuleHub`. Хеш без соответствующего тела принятой транзакции публикации не является читаемым сообщением. Локальная история — только кэш; она не определяет доставку.

Для подписания внешней публикации Vault порядок ссылок на хеши остаётся совместимым с контрактом:

```text
body_hash || header_0_hash || header_1_hash
```

Компактное тело привязано к `header0Hash` и `header1Hash` через AAD AES-GCM. Замена заголовков, чанков тела, метаданных набора, подписи отправителя, контекста капсулы или ячеек полезной нагрузки BOC приводит к сбою проверки до того, как сообщение принимается.

## Источник истины доставки

Принятые приватные сообщения — это компактные записи CapsuleHub плюс ячейки зашифрованной полезной нагрузки, несомые телом принятой транзакции публикации. PWA извлекает эти ячейки из истории сообщений TON и проверяет их по хешам CapsuleHub перед расшифровкой. Продакшн-PWA не открывает ручной обмен JSON-пакетами публичного пакета или зашифрованной капсулы.

Публичные ключи для обмена сообщениями регистрируются в записях ключей `Vault`. Отправитель обязан разрешить и проверить запись ключа получателя перед шифрованием приватной капсулы. Локальная зашифрованная история — только кэш на устройстве; она не определяет доставку.

Авторитет имени пользователя `.ath` состоит из двух частей. `UsernameRegistry.get_name_record` доказывает, что имя существует и указывает на
точный `UsernameNFTItem` для этого имени. Текущий владелец затем читается из состояния этого item. Переводы меняют владельца item;
запись реестра остаётся якорем «имя-к-item». Item раскрывает стандартные данные NFT и он-чейн метаданные TEP-64,
включая `name = <username>.ath`, без размещённого на сервере URI метаданных. Байты имени пользователя намеренно
буквальны: имена с ведущими, конечными, последовательными разделителями и целиком из разделителей допустимы, когда каждый байт входит в разрешённый набор `a-z`,
`0-9`, `_`, `-` и длина составляет 4..16. Если ожидающий минт устаревает после
отсутствующего ACK item, `PrunePendingUsernameMint` не разрушителен: он доказывает устаревшее состояние, но не удаляет
ожидающее состояние и не создаёт причитающийся возврат. Задеплоенный item становится авторитетным именем пользователя только после того, как реестр финализирует
соответствующую запись имени через валидный поздний ACK или `ResendDeployedAck`. Клиенты и индексаторы обязаны игнорировать претензии на владение только на уровне item
и не должны использовать владельца записи реестра в качестве текущего владельца после переводов.

24-словная фраза восстановления GRAM — единственный секрет пользователя. PWA детерминированно порождает ключ кошелька GRAM и ключи шифрования/подписи для обмена сообщениями из этой фразы. Поэтому поток экспорта/импорта профиля обрабатывает только фразу восстановления; отдельной резервной копии ключа для обмена сообщениями нет.

## Политика защиты от повтора и истечения

Приватные капсулы по умолчанию имеют TTL 24 часа и ограничены 30 днями. Живая/офф-чейн проверка пакета капсулы отвергает:

- капсулы, созданные слишком далеко в будущем;
- истёкшие капсулы;
- TTL выше предела политики;
- дублированные идентификаторы капсул в предоставленном вызывающей стороной кэше повторов.

Импорт из истории цепочки устроен иначе: когда приватная запись уже принята CapsuleHub и тело восстановлено из
принятой истории транзакций TON или локального зашифрованного кэша, PWA проверяет хеши записи, ячейки тела/заголовка и
расшифровку, но не отвергает лишь потому, что истечение заголовка в прошлом. Иначе сохранённая история цепочки
стала бы нечитаемой по замыслу.

Кэш повторов — это локальное состояние; продакшн-клиенты могут поддерживать его с помощью IndexedDB или другого локального хранилища на устройстве. Бэкенд не требуется.

## Правило отсутствия бэкенда

Слой шифрования не требует бэкенда Platho. Сервер может размещать статические файлы, но приватная доставка закреплена состоянием цепочки `CapsuleHub` плюс телами принятых транзакций публикации: компактная запись доказывает хеши, а тело всё равно должно быть доступно из истории сообщений TON или локального зашифрованного кэша пользователя. Сервер никогда не получает открытый текст, приватные ключи или серверный секрет сессии.

## Черновик регистрации в Vault

Клиент может вывести черновик `RegisterMessagingKeys` из проверенного подписанного пакета:

- `enc_pubkey`: 32-байтовый публичный ключ X25519 как uint256.
- `sign_pubkey`: 32-байтовый публичный подписывающий ключ Ed25519 как uint256.
- `auth_pubkey`: отдельный 32-байтовый публичный ключ авторизации Vault Ed25519 как uint256.
- `pq_kem_pubkey_hash`: SHA-256 публичного ключа ML-KEM-768.
- `pq_kem_pubkey_len`: `1184`.
- `pq_kem_pubkey`: каноническая snake-ячейка, содержащая ровно 1184 байта публичного ключа ML-KEM-768.
- `crypto_suite_mask`: `2` для `hybrid-v1`.

Этот черновик отправляется потоком активации встроенного кошелька Platho. Как только кошелёк активирован в Vault, другие активированные пользователи могут разрешить его публичную запись ключа для обмена сообщениями и шифровать приватные капсулы для него.

## Привязка к записи ключа Vault

После того как кошелёк зарегистрировал ключи он-чейн, клиент обязан забрать:

- `UserState.current_key_id` кошелька;
- для собственного разблокированного кошелька пользователя — `UserState.auth_pubkey`, соответствующий локально порождённому публичному ключу авторизации Vault;
- `VaultKeyRecordView` для этого идентификатора ключа.

> **clean-17.** Контракт Vault, описанный в этой главе, относится к clean-15. В clean-17 та же привязка читается из СОБСТВЕННОГО контракта KeyShard кошелька (`web/key-shard-ton-rpc-provider.mjs`), адрес которого выводится из кошелька — поэтому запись может содержать только ключи, зарегистрированные этим кошельком. Мост провайдера `web/vault-chain-provider.mjs` удалён вместе с Vault.

```js
{
  async getUser(ownerWallet) {},
  async getKeyRecord(currentKeyId) {},
}
```

Если провайдер не настроен, привязка Vault остаётся недоступной, а не принимает локальный черновик или UI-заполнитель. Продакшн/статический деплой может установить провайдера на `globalThis.plathoVaultChainProvider`, который читает задеплоенный Vault через зеркало TON API или совместимый с лёгким клиентом транспорт.

Статический рантайм включает `web/vault-ton-rpc-provider.mjs` как скелет продакшн-провайдера. Он может оборачивать конечные точки, совместимые с TON Center v3, или пользовательский `globalThis.plathoTonRpcTransport`, установленный бандлом хоста. Текущий PWA не раскрывает встроенный экран пользовательских настроек RPC. Провайдер:

- кодирует адреса владельца `get_user(owner)` как стек-элементы BoC `slice`;
- вызывает `get_key_record(current_key_id)` с числовым стек-элементом;
- декодирует стеки геттеров в `VaultUserView` и `VaultKeyRecordView`;
- отказывает по fail-closed, если транспорт RPC, адрес Vault, ответ геттера или привязка записи ключа недоступны.

Клиентский верификатор проверяет, что активная запись Vault соответствует проверенному подписанному пакету:

- `owner_wallet` соответствует адресу встроенного кошелька Platho;
- `enc_pubkey` соответствует публичному ключу X25519;
- `sign_pubkey` соответствует подписывающему публичному ключу пакета;
- `pq_kem_pubkey`, `pq_kem_pubkey_hash` и `pq_kem_pubkey_len` соответствуют материалу ML-KEM-768;
- `crypto_suite_mask` соответствует набору;
- `revoked_lt` равен нулю;
- необязательный `current_key_id` указывает на забранный идентификатор записи.

Клиент не изобретает он-чейн идентификатор ключа. Vault вычисляет его из адреса владельца, поколения ключа, полей ключа, PQ-длины и набора. Вместо этого клиент проверяет забранную запись.

## Долговременное хранилище повторов

PWA использует IndexedDB для защиты приватных капсул от повтора, когда он доступен, с резервным вариантом в памяти. Хранилище держит идентификаторы капсул до их истечения и обрезает истёкшие записи локально. Это состояние на устройстве, и оно не требует сервера.

## Зашифрованная локальная история сообщений

У PWA также есть локальное на устройстве зашифрованное хранилище истории сообщений. Оно использует неизвлекаемый ключ WebCrypto AES-GCM-256, сохранённый в IndexedDB, и хранит каждое тело сообщения как аутентифицированный шифротекст. Заголовок записи держит только локальные метаданные запроса: id, id треда, метку времени, направление и необязательный id капсулы.

Заголовок привязан как дополнительные аутентифицированные данные AES-GCM. Изменение id треда, метки времени, направления, id капсулы, nonce или шифротекста не даёт открыть запись. Если IndexedDB недоступен, приложение откатывается к зашифрованной истории в памяти на эту сессию и избегает записи открытого текста в постоянное хранилище браузера.

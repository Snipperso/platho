# Platho संदेश क्रिप्टो प्रोटोकॉल

यह दस्तावेज़ Platho PWA द्वारा कार्यान्वित क्लाइंट-साइड संदेश एन्क्रिप्शन का वर्णन करता है।

## एन्क्रिप्शन

निजी संदेश X25519 + ML-KEM-768 + AES-GCM का उपयोग करते हैं — एकमात्र निजी-संदेश सुइट (`hybrid-v1`, कॉन्ट्रैक्ट मान `2`)।

## Key bundles

PWA द्वारा बनाया या इम्पोर्ट किया गया प्रत्येक 24-शब्द वाला GRAM रिकवरी वाक्यांश निर्धारकपूर्वक (deterministically) एक messaging पहचान व्युत्पन्न करता है, जिसमें एक एन्क्रिप्शन key जोड़ी और एक Ed25519 signing key होती है। सार्वजनिक एन्क्रिप्शन key सामग्री को एक public key bundle के रूप में एक्सपोर्ट किया जाता है:

- `keyId`: सार्वजनिक key सामग्री पर आधारित SHA-256 पहचानकर्ता।
- `x25519PublicKey`: 32-byte क्लासिकल ECDH सार्वजनिक key।
- `mlKem768PublicKey`: `hybrid-v1` के लिए 1184-byte ML-KEM-768 सार्वजनिक key।
- `mlKem768PublicKeyHash`: ML-KEM-768 सार्वजनिक key का SHA-256।
- `mlKem768PublicKeyLen`: `hybrid-v1` के लिए हमेशा `1184`।

PWA एन्क्रिप्शन से पहले `keyId`, `mlKem768PublicKeyHash`, और `mlKem768PublicKeyLen` को पुनः गणना करता है। ऐसा कोई bundle जो बेमेल id, suite, कॉन्ट्रैक्ट suite, hash, या length का दावा करता है, अस्वीकृत कर दिया जाता है।

प्राप्तकर्ता (recipient) लुकअप को ऑन-चेन `enc_pubkey`, `sign_pubkey`, और सक्रिय Vault key रिकॉर्ड में संग्रहीत पूर्ण ऑन-चेन `pq_kem_pubkey` सेल द्वारा परिभाषित किया जाता है। hash और length रिकॉर्ड में संहत (compact) बाइंडिंग फ़ील्ड के रूप में बने रहते हैं, लेकिन पूर्ण ML-KEM-768 सार्वजनिक key ही वह चीज़ है जो किसी अन्य क्लाइंट को वास्तव में `hybrid-v1` कैप्सूल एन्क्रिप्ट करने देती है।

## Signed bundles

PWA एक signed public key bundle एक्सपोर्ट कर सकता है। signed पेलोड में शामिल हैं:

- प्रोटोकॉल डोमेन `PLATHO.MESSAGING.KEY_BUNDLE.SIGNATURE.V1`;
- जारी करने का और वैकल्पिक समाप्ति टाइमस्टैम्प;
- वैकल्पिक स्वामी wallet और Vault पता प्लेसहोल्डर;
- सार्वजनिक एन्क्रिप्शन bundle;
- 32-byte Ed25519 signing सार्वजनिक key।

signature स्थिर JSON पेलोड को कवर करता है और bundle पर भरोसा करने से पहले इसे सत्यापित किया जाता है। यह मौन स्थानीय bundle छेड़छाड़ को रोकता है और क्लाइंट को ठीक वही `sign_pubkey` देता है जो Vault `KeyRecord` में संग्रहीत करता है।

PWA का `keyId` एक क्लाइंट bundle पहचानकर्ता है। यह Vault कॉन्ट्रैक्ट के `current_key_id` को प्रतिस्थापित नहीं करता, जिसकी गणना ऑन-चेन स्वामी पते, key जनरेशन, signing key, एन्क्रिप्शन key, PQ hash, PQ length, और क्रिप्टो suite से की जाती है। एक प्रोडक्शन क्लाइंट को किसी wallet पहचान के लिए bundle पर भरोसा करने से पहले उसे Vault key रिकॉर्ड के विरुद्ध सत्यापित करना चाहिए।

signed bundle एक messaging-key स्व-signature है। wallet स्वामित्व Vault सक्रियण द्वारा एंकर किया जाता है: एम्बेडेड Platho wallet `RegisterMessagingKeys` भेजता है, बाद के `ReplaceMessagingKeys` रोटेशन Vault-auth-signed बाहरी संदेश होते हैं, और प्राप्तकर्ता उस wallet के लिए सक्रिय ऑन-चेन key रिकॉर्ड के विरुद्ध signed bundle को सत्यापित करते हैं।

## Wallet स्वामित्व

प्रोडक्शन PWA किसी बाहरी wallet कनेक्टर का उपयोग नहीं करता। एक उपयोगकर्ता एक सामान्य 24-शब्द वाला GRAM रिकवरी वाक्यांश बनाता या इम्पोर्ट करता है, और PWA
निर्धारकपूर्वक उस वाक्यांश से GRAM wallet key, एक अलग Vault auth key, और messaging एन्क्रिप्शन/signing keys व्युत्पन्न करता है। Vault
सक्रियण स्वामित्व एंकर है: एम्बेडेड wallet उसी wallet से `RegisterMessagingKeys` पर हस्ताक्षर करता और भेजता है जो ऑन-चेन key रिकॉर्ड का स्वामी है।
`ReplaceMessagingKeys` केवल सार्वजनिक receive/messaging key रिकॉर्ड को घुमाता है; यह Vault auth key को नहीं घुमाता।

प्राप्तकर्ता किसी messaging bundle पर तभी भरोसा करते हैं जब उसे उस wallet के लिए सक्रिय Vault key रिकॉर्ड के विरुद्ध जाँच लिया जाए:

- रिकॉर्ड स्वामी अपेक्षित wallet है;
- `enc_pubkey` और `sign_pubkey` signed bundle से मेल खाते हैं;
- hybrid रिकॉर्ड पूर्ण `pq_kem_pubkey` सेल को उजागर करते हैं, केवल इसके hash को नहीं;
- डिकोड किए गए ML-KEM-768 key बाइट्स का hash `pq_kem_pubkey_hash` बनता है;
- सक्रिय `current_key_id` सत्यापित key रिकॉर्ड की ओर इंगित करता है।

प्रोफ़ाइल एक्सपोर्ट/इम्पोर्ट फ़्लो 24-शब्द वाले GRAM रिकवरी वाक्यांश को संभालता है। कोई अलग messaging key बैकअप नहीं है और न ही कोई
बाहरी wallet कनेक्शन मोड है।

## संहत byte layout

निजी कैप्सूल ऑन-चेन सेल अंतिम `platho.byte-layout.v1` बाइनरी layout का उपयोग करते हैं। PWA एक्सपोर्ट/शेयर UI के लिए कैप्सूल को JSON में लपेट सकता है, लेकिन प्रोटोकॉल पेलोड बाइनरी बाइट्स है, न कि JSON और न ही कोई ऑफ-चेन पॉइंटर। `CapsuleHub` संहत प्रमाणित हेडर/इंडेक्स के साथ body hash संग्रहीत करता है; एन्क्रिप्टेड body सेल स्वीकृत publish लेनदेन body में रहता है और TON संदेश इतिहास से पुनर्निर्मित किया जाता है, फिर संग्रहीत hashes के विरुद्ध सत्यापित किया जाता है।

प्रत्येक publish एक Vault-balance से वित्तपोषित signed बाहरी संदेश के रूप में Vault से होकर गुजरता है। उपयोगकर्ता पहले अपने आंतरिक
Vault GRAM बैलेंस को फंड करता है, फिर PWA सक्रिय `auth_pubkey` के साथ एक publish अनुरोध पर हस्ताक्षर करता है; एक रिलेयर wallet key या messaging signing key रखे बिना
बाहरी संदेश सबमिट कर सकता है। signed पेलोड स्वामी, nonce, अधिकतम शुल्क, और पेलोड से पहले `VPB1`,
`deployment_manifest_hash`, लक्ष्य Vault पते, और publish प्रकार के साथ डोमेन-पृथक्कृत होता है।
वह GRAM मान जो CapsuleHub वास्तव में किसी ACK या bounce में वापस भेजता है, उपयोगकर्ता के आंतरिक Vault GRAM
बैलेंस में जमा किया जाता है, जो ट्रैक की गई लंबित publish रिफंड राशि तक सीमित है। यदि Vault बैलेंस या चेन एक्सेस उपलब्ध नहीं है, तो
PWA fail closed हो जाता है और उसे publish क्रियाएँ उजागर नहीं करनी चाहिए।

क्योंकि `auth_pubkey` Vault-balance खर्च को अधिकृत करता है, केवल स्थानीय messaging signing key से समझौता होने पर
Vault publish, payment-check, username, या avatar क्रियाएँ अधिकृत नहीं होतीं। messaging signing-key से समझौता अभी भी संदेश-स्तरीय
पहचान signatures को प्रभावित कर सकता है, इसलिए key प्रतिस्थापन भविष्य की इनबाउंड एन्क्रिप्शन जाँचों के लिए पुरानी सार्वजनिक receive key रिकॉर्ड को निरस्त कर देता है।

PWA संदेश मूल्य निर्धारण प्रति कैप्सूल होता है। वर्तमान रिज़र्व के साथ और बिना किसी ATH छूट के, सटीक कैनोनिकल उदाहरण हैं: 1 KiB सार्वजनिक प्रविष्टियाँ `0.0337 GRAM` से और `hybrid-v1` 1 KiB निजी
कैप्सूल `0.0347 GRAM` से; बड़े सार्वजनिक या निजी आकार वर्गों की कीमत कैनोनिकल वर्ग के अनुसार अधिक होती है। इसमें पूर्ण
Platho प्रोटोकॉल शुल्क `0.01 GRAM`, CapsuleHub संहत-इंडेक्स स्टोरेज एंडाउमेंट, Vault स्थानीय निष्पादन रिज़र्व, और
अपेक्षित ACK रिफंड शामिल है। अलग से, यदि PWA का रूढ़िवादी शुल्क अनुमान शामिल नेटवर्क-शुल्क
भत्ते `0.005 GRAM` से अधिक है, तो यह
गोल की गई अधिकता को अधिभार (surcharge) के रूप में जोड़ता है। कॉन्ट्रैक्ट कॉल अभी भी अपने कैनोनिकल
आवश्यक मानों से शुरू होते हैं: Vault publishes `maxCharge = canonical_max_charge + surcharge` भेजते हैं। CapsuleHub का कोई प्रत्यक्ष उपयोगकर्ता
publish ABI नहीं है; प्रत्येक publish Vault -> CapsuleHub है। ATH छूट केवल तभी लागू होती है जब Vault गतिविधि एयरड्रॉप
15,000,000 ATH वितरित कर चुका हो; उस गेट से पहले, संदेश प्रोटोकॉल शुल्क पूर्ण `0.01 GRAM` शुल्क का उपयोग करते हैं। PWA को हस्ताक्षर से पहले चयनित सामग्री आकार के लिए अंतिम
होल्ड और शुद्ध लागत दिखानी चाहिए।

अधिभार एक signed नेटवर्क/स्टोरेज सुरक्षा मार्जिन है, न कि कोई रिफंड-योग्य शुल्क बकेट। CapsuleHub Vault publishes को
तब स्वीकार करता है जब संलग्न मान कम से कम कैनोनिकल आवश्यक मान हो, लेकिन एक सफल publish ACK केवल निश्चित
publish ACK रिज़र्व `30,000,000` nanotons (`0.030 GRAM`) लौटाता है। Vault द्वारा उस ACK को संसाधित करने के बाद, उपयोगकर्ता को आंतरिक Vault GRAM बैलेंस में लगभग
`25,800,000` nanotons जमा किए जाते हैं। कैनोनिकल आवश्यक मान से ऊपर कोई भी signed अधिभार
CapsuleHub में नेटवर्क/स्टोरेज रिज़र्व अधिकता के रूप में बना रहता है; इसे Vault को वापस नहीं किया जाता और न ही इसे
`accrued_plato_fee_ton` के रूप में गिना जाता है।

CapsuleHub `accrued_plato_fee_ton + max(100 GRAM, 1.25 * live_index_1y_storage_reserve)` के बराबर कच्चे GRAM रिज़र्व की सुरक्षा करता है।
लाइव रिज़र्व ऐतिहासिक `latest_id` काउंटरों के बजाय अछँटे (unpruned) निजी/सार्वजनिक प्रविष्टि काउंटरों का उपयोग करता है। एक अलग
अनुमति-रहित (permissionless) `SweepExcessReserve` कॉल केवल उस सुरक्षित राशि से ऊपर की अधिशेष राशि को FeeAccumulator में
`DepositProtocolFee` के रूप में स्थानांतरित कर सकती है, जहाँ यह सामान्य treasury/buyback विभाजन का अनुसरण करती है। सामान्य संदेश भेजना यह
sweep नहीं करता। यदि वह sweep जमा bounce हो जाती है, तो लौटाई गई राशि को जानबूझकर backed
`accrued_plato_fee_ton` के रूप में पुनर्वर्गीकृत किया जाता है ताकि इसे सामान्य शुल्क फ्लश पथ के माध्यम से पुनः प्रयास किया जा सके।
सामान्य आंशिक `FlushFees` कॉल कम से कम वर्तमान सार्वजनिक प्रोटोकॉल शुल्क (`0.010 GRAM`) होनी चाहिए; एक छोटी राशि
केवल तभी वैध है जब यह संपूर्ण शेष संचित बकेट हो, ताकि छूट वाली धूल (dust) को भी अंतिम रूप दिया जा सके।

CapsuleHub प्रत्येक निजी और सार्वजनिक प्रविष्टि के लिए `created_at = now()` रिकॉर्ड करता है। PWA उस कॉन्ट्रैक्ट टाइमस्टैम्प का उपयोग क्रम निर्धारण और परिबद्ध (bounded) लेनदेन-इतिहास लुकअप के लिए करता है; क्लाइंट हेडर टाइमस्टैम्प प्रमाणित पेलोड मेटाडेटा बने रहते हैं, न कि डिस्कवरी प्राधिकरण। संहत प्रविष्टि मेटाडेटा को कॉन्फ़िगर किए गए एक-वर्षीय रिटेंशन विंडो के बाद अनुमति-रहित रूप से छाँटा जा सकता है, जबकि body उपलब्धता चुने गए TON प्रदाता के संदेश-इतिहास कवरेज और उपयोगकर्ता के स्थानीय एन्क्रिप्टेड कैश पर निर्भर करती है।

Vault ATH बैलेंस को स्पष्ट notify-flow अकाउंटिंग के माध्यम से जमा किया जाता है, न कि कच्चे आधिकारिक wallet बैलेंस को स्कैन करके।
समर्थित जमा पथ उपयोगकर्ता के ATHWallet का `ATHTransferRequestWithNotify` Vault में है। आधिकारिक Vault ATHWallet में मैनुअल सामान्य ATH
हस्तांतरण असमर्थित है और इसे जमा पते के रूप में प्रदर्शित नहीं किया जाना चाहिए और न ही इसे
Vault खाता-बही जमा के रूप में माना जाना चाहिए। Vault से ATH निकासी एक signed बाहरी Vault कमांड है। इसका डाउनस्ट्रीम ATHWallet
deploy/transfer/ACK रिज़र्व उपयोगकर्ता के आंतरिक Vault GRAM बैलेंस से भुगतान किया जाता है, और Vault केवल उसे प्राप्त होने वाला
प्रमाणित ACK/fail/bounce मान वापस जमा करता है, स्थानीय रिफंड रिज़र्व घटाकर और आरक्षित आंतरिक मान तक सीमित।

सार्वजनिक पोस्ट और टिप्पणियाँ एक अलग खुली प्रोफ़ाइल हैं, न कि बिना एन्क्रिप्शन वाले निजी कैप्सूल। वे एक संहत
`PPH1` सार्वजनिक हेडर सेल के साथ एक कच्चा सार्वजनिक body सेल संग्रहीत करते हैं। सार्वजनिक body टेक्स्ट और सार्वजनिक image/avatar बाइट्स उपयोगकर्ता-दृश्य body बजट के रूप में उन्हीं
1, 2, 4, 8, 16, या 32 KiB सार्वजनिक कैप्सूल आकार वर्गों का उपयोग करते हैं। हेडर मेटाडेटा उस body बजट को कभी कम नहीं करता।
सार्वजनिक पोस्ट के पास कोई पोस्टक्वांटम विकल्प नहीं है; सार्वजनिक संदेश `0.0337 GRAM` से शुरू होते हैं,
जबकि वर्तमान सटीक सार्वजनिक आधार उदाहरण `0.0337 GRAM` जमा उसी
नेटवर्क-शुल्क अधिभार नियम के साथ है। `kind = 1` एक सार्वजनिक पोस्ट है; पोस्ट `flags` बिट 0 उस पोस्ट के लिए टिप्पणियाँ बंद कर देता है। `kind = 2` हेडर में
`parent_entry_id:uint64` और `parent_body_hash:uint256` के साथ एक एक-स्तरीय सार्वजनिक टिप्पणी है। `kind = 3` एक
सार्वजनिक image पोस्ट है, `kind = 4` एक सार्वजनिक image टिप्पणी है, और `kind = 5` सार्वजनिक wallet avatar मीडिया है। सार्वजनिक हेडर
`stream_id:uint128`, `part_index:uint16`, `part_count:uint16`, और `media_format:u8` भी वहन करते हैं; सार्वजनिक हेडर टेक्स्ट के लिए `media_format = 0` और
WebP image/avatar भागों के लिए `media_format = 1` का उपयोग करते हैं। सार्वजनिक पोस्ट, image पोस्ट, और avatar हेडर
`profile_version:uint32` और `avatar_hash:uint256` भी वहन करते हैं; शून्य का अर्थ कोई avatar पॉइंटर नहीं है। लंबा सार्वजनिक टेक्स्ट या image डेटा कई प्रविष्टियों से केवल तभी पुनर्निर्मित किया जाता है
जब प्रत्येक प्रविष्टि ने 32 KiB तक सबसे छोटे उपयुक्त सार्वजनिक आकार वर्ग का उपयोग किया हो। आधिकारिक PWA विभाजित करने से पहले चयनित images को 8 KiB
(`low`), 16 KiB (`medium`), 32 KiB (`good`, डिफ़ॉल्ट), या 64 KiB (`maximum`) के WebP लक्ष्यों में संपीड़ित करता है। कोई edit/delete/reaction/moderation या काउंटर परत नहीं है।

Wallet avatars भुगतान की गई प्रोफ़ाइल अपडेट हैं, न कि ऑफ-चेन एसेट। avatar बाइट्स को `kind = 5` सार्वजनिक
CapsuleHub प्रविष्टियों के रूप में publish किया जाता है, फिर `ProfileRegistry` प्रमाणित wallet पॉइंटर रिकॉर्ड करता है:
`version`, `avatar_hash`, पहला `avatar_entry_id`, `avatar_stream_id`, `avatar_part_count`, और `media_format`। पाठक
signed निजी हेडर या सार्वजनिक पोस्ट हेडर से प्रोफ़ाइल पॉइंटर को हल करते हैं, मेल खाते ProfileRegistry
रिकॉर्ड को सत्यापित करते हैं, CapsuleHub से avatar सार्वजनिक प्रविष्टियाँ प्राप्त करते हैं, भागों को इंडेक्स क्रम में जोड़ते हैं, और पुनर्निर्मित
WebP बाइट्स का hash `avatar_hash` बनने की माँग करते हैं। स्थानीय avatar कैश केवल एक गति-वृद्धि है; सत्य का स्रोत CapsuleHub प्लस
ProfileRegistry है।

`header0_cell` ठीक 140 बाइट्स संग्रहीत करता है:

```text
PH0B
|| version:u8
|| publish_kind:u8
|| size_class:u8
|| crypto_suite:u8
|| sender_key_id:32 bytes
|| recipient_key_id:32 bytes
|| sender_sign_pubkey:32 bytes
|| profile_version:uint32
|| avatar_hash:uint256
```

`header1_cell` ठीक 30 बाइट्स संग्रहीत करता है:

```text
PH1B
|| version:u8
|| flags:u8 = 0
|| created_at_s:u32
|| expires_at_s:u32
|| client_nonce:16 bytes
```

`size_class + crypto_suite` suite का संकेत देते हैं। `profile_version` और `avatar_hash` भेजने के समय प्रेषक wallet avatar की ओर इंगित करते हैं और
हेडर hash प्लस प्रेषक signature द्वारा कवर किए जाते हैं। `recipient_sign_pubkey` और thread hashes को
जानबूझकर सार्वजनिक हेडर सेल में संग्रहीत नहीं किया जाता। Thread/समूहन डेटा एन्क्रिप्टेड कैप्सूल मेटाडेटा के अंदर आता है।

प्रत्येक एन्क्रिप्टेड body इस प्रकार संयोजित होता है:

```text
PLB1 || version:u8 || suite:u8 || flags:u8 || reserved:u8
     || message_id:u128
     || aes_gcm_nonce:12 bytes
     || x25519_ephemeral_public:32 bytes
     || ml_kem_768_ciphertext:1088 bytes, only for hybrid-v1
     || aes_gcm_ciphertext_and_tag
```

AES-GCM प्लेनटेक्स्ट `size_class` द्वारा चयनित एक निश्चित कैप्सूल स्लॉट है:

```text
PCP1
|| version:u8
|| kind:u8
|| flags:u8
|| media_format:u8
|| stream_id:u128
|| part_index:u16
|| part_count:u16
|| content_len:u16
|| reserved:u16
|| payload[useful_size]
```

उपयोगी सामग्री क्षेत्र को चयनित 1, 2, 4, 8, 16, या 32 KiB निजी कैप्सूल वर्ग तक पैड किया जाता है। 1 byte, 500 बाइट्स, या 1024 बाइट्स उपयोगी टेक्स्ट वाले संदेश का 1 KiB वर्ग में समान एन्क्रिप्टेड प्लेनटेक्स्ट आकार होता है। चयनित वर्ग से ऊपर के संदेशों को एन्क्रिप्टेड `stream_id`, `part_index`, और `part_count` मेटाडेटा के साथ स्वतंत्र कैप्सूल में विभाजित किया जाता है। एक कैप्सूल कभी असंबंधित टेक्स्ट/image इकाइयों को नहीं मिलाता; प्राप्तकर्ता स्वतंत्र कैप्सूल को मूल संदेश में पुनः संयोजित करता है।

सामग्री प्रकार:

- `1` text: UTF-8 बाइट्स, चयनित उपयोगी निजी कैप्सूल आकार तक।
- `2` image: संपीड़ित WebP image बाइट्स, चयनित उपयोगी निजी कैप्सूल आकार तक (`media_format = 1`)।
- `3` payment check: `asset:u8 || reserved:u8 || amount:u128 || intent_id:uint256 || secret32:uint256`।

Payment check bodies जानबूझकर `tx`, सक्रियण समय, या समाप्ति को शामिल नहीं करतीं। प्राप्तकर्ता `intent_id + secret32` द्वारा दावा करता है; यदि प्रेषक ने पहले ही चेक रद्द कर दिया है या इसका पहले ही दावा किया जा चुका है, तो UI कहता है कि चेक का पहले ही दावा किया जा चुका है या प्रेषक द्वारा रद्द कर दिया गया है।

एन्क्रिप्टेड body को एक्सपोर्ट/शेयर के लिए इस प्रकार लपेटा जा सकता है:

```text
PLC1 || version:u8 || suite:u8 || chunk_index:u8 || chunk_total:u8 || message_id:u128 || body_slice
```

अंतिम कैप्सूल body के लिए, `chunk_total` हमेशा `1` होता है। `PLC1` केवल पैकेज/एक्सपोर्ट फ़्रेमिंग है। स्वीकृत Vault -> CapsuleHub publish लेनदेन असेंबल किए गए `PLB1` body बाइट्स को एक snake सेल में वहन करता है; CapsuleHub केवल संहत प्रमाणित मेटाडेटा और hashes को बनाए रखता है।

अंतिम निजी सीमाएँ:

| Suite | प्रति कैप्सूल उपयोगी सीमा | Body बाइट्स | Export chunk बाइट्स |
| --- | ---: | ---: | ---: |
| `hybrid-v1` | 1 KiB | 2,228 bytes | 2,252 bytes |
| `hybrid-v1` | 2 KiB | 3,252 bytes | 3,276 bytes |
| `hybrid-v1` | 4 KiB | 5,300 bytes | 5,324 bytes |
| `hybrid-v1` | 8 KiB | 9,396 bytes | 9,420 bytes |
| `hybrid-v1` | 16 KiB | 17,588 bytes | 17,612 bytes |
| `hybrid-v1` | 32 KiB | 33,972 bytes | 33,996 bytes |

इस layout का कैनोनिकल स्रोत `artifacts/PLATHO_CAPSULE_V1_FINAL_SPEC.md` है।

AES-GCM एक 12-byte nonce और एक 16-byte tag का उपयोग करता है। ciphertext लंबाई प्लेनटेक्स्ट लंबाई प्लस tag के बराबर होती है।

संहत body उपसर्ग, `header0Hash`, और `header1Hash` को AES-GCM अतिरिक्त प्रमाणित डेटा के रूप में पास किया जाता है। बाइनरी रूटिंग हेडर, suite, nonce, KEM ciphertext, chunk बाइट्स, या प्रेषक signature को बदलने से सत्यापन या डिक्रिप्शन विफल हो जाता है।

डिक्रिप्शन से पहले क्लाइंट यह भी जाँचता है:

- संहत body suite `header0` से मेल खाता है;
- प्राप्तकर्ता key id `header0.recipientKeyId` से मेल खाता है;
- `hybrid-v1` bodies एक 1088-byte ML-KEM ciphertext वहन करती हैं;
- प्रत्येक chunk का suite, संदेश id, और chunk total समान है।

## Key व्युत्पत्ति

`hybrid-v1` के लिए:

```text
x25519_secret = X25519(sender_ephemeral_secret, recipient_x25519_public)
mlkem_secret  = ML-KEM-768.Encapsulate(recipient_mlkem_public)
message_key   = HKDF-SHA-256(x25519_secret || mlkem_secret, compact_aad_hash)
```

प्लेनटेक्स्ट को AES-256-GCM के साथ एन्क्रिप्ट किया जाता है।

निम्न-क्रम (low-order) सार्वजनिक keys को स्वीकार करने से बचने के लिए कार्यान्वयन सभी-शून्य X25519 साझा secrets को अस्वीकार करता है।

## निजी एन्क्रिप्टेड कैप्सूल

क्लाइंट प्रकाशन से पहले संहत एन्क्रिप्टेड bodies को एक निजी कैप्सूल में लपेटता है। एक निजी कैप्सूल में होता है:

- `header0`: ऊपर वर्णित 140-byte `PH0B` बाइनरी रूटिंग हेडर।
- `header1`: ऊपर वर्णित 30-byte `PH1B` बाइनरी replay हेडर।
- `body`: `platho.byte-layout.v1` chunk मेटाडेटा प्लस base64url-एन्कोडेड बाइनरी chunks।
- `hashes`: उन ठीक ऑन-चेन सेल के लिए TON `Cell.hash()` मान जिनमें `header0`, `header1`, और एन्क्रिप्टेड body बाइट्स होते हैं।
- `chainCells`: `ton-snake-byte-cell.v1` का उपयोग करने वाले base64 BOC पेलोड; ये वे सेल हैं जो Vault -> CapsuleHub publish लेनदेन में स्वीकृत होते हैं और `CapsuleHub` द्वारा प्रमाणित होते हैं, न कि कोई ऑफ-चेन पॉइंटर।
- `senderSignature`: कैप्सूल id और तीनों hashes पर Ed25519 signature।

`hybrid-v1` के लिए, कैप्सूल CapsuleHub की hybrid प्रोफ़ाइल का उपयोग करता है:

```text
size_class   in {1,2,4,8,16,32}
crypto_suite = 2
```

signed `PublishPrivateFromVaultBalance` बाहरी अनुरोध के Vault द्वारा स्वीकृत होने के बाद निजी कैप्सूल ड्राफ्ट Vault -> CapsuleHub `PublishPrivateFromVault`
body में मैप होता है:

```text
header_0_hash = Cell.hash(header_0_cell)
header_1_hash = Cell.hash(header_1_cell)
body_hash     = Cell.hash(body_cell)
header_0_cell = snake-cell(header0 bytes)
header_1_cell = snake-cell(header1 bytes)
body_cell     = snake-cell(compact encrypted body bytes)
```

Vault publish संदेश `protocol_fee_paid` वहन करते हैं, क्योंकि Vault ATH-backed मूल्य निर्धारण के लिए छूट प्राधिकरण है।

उपयोगी पेलोड क्षमता उन एन्क्रिप्टेड body बाइट्स की क्षमता है जो वास्तव में `body_cell` में क्रमबद्ध की जाती हैं और `CapsuleHub` द्वारा स्वीकृत की जाती हैं। मेल खाते स्वीकृत publish लेनदेन body के बिना कोई hash पठनीय संदेश नहीं है। स्थानीय इतिहास केवल कैश है; यह डिलीवरी को परिभाषित नहीं करता।

Vault बाहरी publish हस्ताक्षर के लिए, hashes-ref क्रम कॉन्ट्रैक्ट-संगत बना रहता है:

```text
body_hash || header_0_hash || header_1_hash
```

संहत body को AES-GCM AAD के माध्यम से `header0Hash` और `header1Hash` से बाँधा जाता है। हेडर, body chunks, suite मेटाडेटा, प्रेषक signature, कैप्सूल संदर्भ, या BOC पेलोड सेल को प्रतिस्थापित करने से संदेश स्वीकृत होने से पहले सत्यापन विफल हो जाता है।

## डिलीवरी सत्य का स्रोत

स्वीकृत निजी संदेश संहत CapsuleHub प्रविष्टियाँ प्लस स्वीकृत publish लेनदेन body द्वारा वहन किए गए एन्क्रिप्टेड पेलोड सेल हैं। PWA उन सेल को TON संदेश इतिहास से पुनः प्राप्त करता है और डिक्रिप्ट करने से पहले उन्हें CapsuleHub hashes के विरुद्ध सत्यापित करता है। प्रोडक्शन PWA मैनुअल public-bundle या एन्क्रिप्टेड-कैप्सूल JSON पैकेज विनिमय को उजागर नहीं करता।

सार्वजनिक messaging keys `Vault` key रिकॉर्ड में पंजीकृत होते हैं। किसी निजी कैप्सूल को एन्क्रिप्ट करने से पहले एक प्रेषक को प्राप्तकर्ता key रिकॉर्ड को हल और सत्यापित करना चाहिए। स्थानीय एन्क्रिप्टेड इतिहास केवल एक डिवाइस कैश है; यह डिलीवरी को परिभाषित नहीं करता।

`.ath` username प्राधिकरण के दो भाग हैं। `UsernameRegistry.get_name_record` सिद्ध करता है कि एक नाम मौजूद है और उस नाम के लिए
ठीक `UsernameNFTItem` की ओर इंगित करता है। वर्तमान स्वामी फिर उस item स्थिति से पढ़ा जाता है। हस्तांतरण item
स्वामी को बदलते हैं; रजिस्ट्री रिकॉर्ड नाम-से-item एंकर बना रहता है। item मानक NFT डेटा और TEP-64 ऑन-चेन
मेटाडेटा को उजागर करता है, जिसमें बिना किसी सर्वर-होस्टेड मेटाडेटा URI के `name = <username>.ath` शामिल है। Username बाइट्स जानबूझकर
शाब्दिक हैं: अग्रणी, अनुगामी, लगातार, और सभी-विभाजक वाले नाम तब वैध होते हैं जब प्रत्येक byte अनुमत `a-z`,
`0-9`, `_`, `-` समुच्चय में हो और लंबाई 4..16 हो। यदि कोई लंबित mint किसी अनुपस्थित item ACK के बाद
बासी (stale) हो जाता है, तो `PrunePendingUsernameMint` गैर-विनाशकारी है: यह बासी स्थिति सिद्ध करता है लेकिन
लंबित स्थिति को हटाता नहीं या रिफंड बकाया नहीं बनाता। एक तैनात item केवल तभी एक आधिकारिक username बनता है जब रजिस्ट्री
मेल खाते नाम रिकॉर्ड को किसी वैध विलंबित ACK या `ResendDeployedAck` के माध्यम से अंतिम रूप देती है। क्लाइंट और इंडेक्सर को item-केवल
स्वामित्व दावों को अनदेखा करना चाहिए और हस्तांतरण के बाद रजिस्ट्री रिकॉर्ड स्वामी को वर्तमान स्वामी के रूप में उपयोग नहीं करना चाहिए।

24-शब्द वाला GRAM रिकवरी वाक्यांश एकमात्र उपयोगकर्ता secret है। PWA निर्धारकपूर्वक उस वाक्यांश से GRAM wallet key और messaging एन्क्रिप्शन/signing keys व्युत्पन्न करता है। इसलिए प्रोफ़ाइल एक्सपोर्ट/इम्पोर्ट फ़्लो केवल रिकवरी वाक्यांश को संभालता है; कोई अलग messaging-key बैकअप नहीं है।

## Replay और समाप्ति नीति

निजी कैप्सूल डिफ़ॉल्ट रूप से 24-घंटे के TTL पर होते हैं और 30 दिनों पर सीमित होते हैं। लाइव/ऑफ-चेन कैप्सूल पैकेज सत्यापन अस्वीकार करता है:

- भविष्य में बहुत दूर बनाए गए कैप्सूल;
- समाप्त कैप्सूल;
- नीति सीमा से ऊपर TTL;
- कॉलर-प्रदत्त replay कैश में डुप्लिकेट कैप्सूल ids।

चेन-इतिहास इम्पोर्ट अलग है: जब कोई निजी प्रविष्टि पहले से ही CapsuleHub द्वारा स्वीकृत हो और body को
स्वीकृत TON लेनदेन इतिहास या स्थानीय एन्क्रिप्टेड कैश से पुनः प्राप्त किया जाए, तो PWA प्रविष्टि hashes, body/header सेल, और
डिक्रिप्शन को सत्यापित करता है, लेकिन यह केवल इसलिए अस्वीकार नहीं करता क्योंकि हेडर समाप्ति अतीत में है। अन्यथा प्रतिधारित (retained) चेन इतिहास
डिज़ाइन द्वारा अपठनीय हो जाता।

Replay कैश स्थानीय स्थिति है; प्रोडक्शन क्लाइंट इसे IndexedDB या किसी अन्य डिवाइस-स्थानीय स्टोर से समर्थित कर सकते हैं। किसी बैकएंड की आवश्यकता नहीं है।

## बैकएंड-रहित नियम

एन्क्रिप्शन परत को किसी Platho बैकएंड की आवश्यकता नहीं होती। एक सर्वर स्थिर फ़ाइलें होस्ट कर सकता है, लेकिन निजी डिलीवरी `CapsuleHub` चेन स्थिति प्लस स्वीकृत publish लेनदेन bodies द्वारा एंकर की जाती है: संहत प्रविष्टि hashes सिद्ध करती है, और body को अभी भी TON संदेश इतिहास या उपयोगकर्ता के स्थानीय एन्क्रिप्टेड कैश से उपलब्ध होना चाहिए। सर्वर को कभी प्लेनटेक्स्ट, निजी keys, या कोई सर्वर-साइड सत्र secret प्राप्त नहीं होता।

## Vault पंजीकरण ड्राफ्ट

क्लाइंट एक सत्यापित signed bundle से एक `RegisterMessagingKeys` ड्राफ्ट व्युत्पन्न कर सकता है:

- `enc_pubkey`: uint256 के रूप में 32-byte X25519 सार्वजनिक key।
- `sign_pubkey`: uint256 के रूप में 32-byte Ed25519 signing सार्वजनिक key।
- `auth_pubkey`: uint256 के रूप में अलग 32-byte Ed25519 Vault auth सार्वजनिक key।
- `pq_kem_pubkey_hash`: ML-KEM-768 सार्वजनिक key का SHA-256।
- `pq_kem_pubkey_len`: `1184`।
- `pq_kem_pubkey`: ठीक 1184 ML-KEM-768 सार्वजनिक-key बाइट्स वाला कैनोनिकल snake-cell।
- `crypto_suite_mask`: `hybrid-v1` के लिए `2`।

यह ड्राफ्ट एम्बेडेड Platho wallet सक्रियण फ़्लो द्वारा सबमिट किया जाता है। एक बार जब wallet Vault में सक्रिय हो जाता है, तो अन्य सक्रिय उपयोगकर्ता इसके सार्वजनिक messaging key रिकॉर्ड को हल कर सकते हैं और इसे निजी कैप्सूल एन्क्रिप्ट कर सकते हैं।

## Vault key रिकॉर्ड बाइंडिंग

wallet द्वारा ऑन-चेन keys पंजीकृत करने के बाद, क्लाइंट को यह प्राप्त करना चाहिए:

- wallet `UserState.current_key_id`;
- उपयोगकर्ता के अपने अनलॉक किए गए wallet के लिए, स्थानीय रूप से व्युत्पन्न Vault auth सार्वजनिक key से मेल खाता `UserState.auth_pubkey`;
- उस key id के लिए `VaultKeyRecordView`।

PWA इसे `web/vault-chain-provider.mjs` में एक fail-closed प्रदाता ब्रिज के रूप में उजागर करता है। ब्रिज एक ऐसे प्रदाता की अपेक्षा करता है जिसमें हो:

```js
{
  async getUser(ownerWallet) {},
  async getKeyRecord(currentKeyId) {},
}
```

यदि कोई प्रदाता कॉन्फ़िगर नहीं किया गया है, तो Vault बाइंडिंग किसी स्थानीय ड्राफ्ट या UI प्लेसहोल्डर को स्वीकार करने के बजाय अनुपलब्ध बनी रहती है। एक प्रोडक्शन/स्थिर तैनाती `globalThis.plathoVaultChainProvider` पर एक प्रदाता स्थापित कर सकती है जो तैनात Vault को किसी TON API मिरर या light-client संगत ट्रांसपोर्ट के माध्यम से पढ़ता है।

स्थिर रनटाइम में प्रोडक्शन-प्रदाता कंकाल के रूप में `web/vault-ton-rpc-provider.mjs` शामिल है। यह TON Center v3 संगत एंडपॉइंट या होस्ट bundle द्वारा स्थापित किसी कस्टम `globalThis.plathoTonRpcTransport` को लपेट सकता है। वर्तमान PWA किसी अंतर्निहित उपयोगकर्ता RPC सेटिंग्स स्क्रीन को उजागर नहीं करता। प्रदाता:

- `get_user(owner)` स्वामी पतों को `slice` BoC स्टैक आइटम के रूप में एन्कोड करता है;
- `get_key_record(current_key_id)` को एक संख्यात्मक स्टैक आइटम के साथ कॉल करता है;
- getter स्टैक को `VaultUserView` और `VaultKeyRecordView` में डिकोड करता है;
- यदि RPC ट्रांसपोर्ट, Vault पता, getter प्रतिक्रिया, या key-रिकॉर्ड बाइंडिंग अनुपलब्ध हो तो fail closed हो जाता है।

क्लाइंट-साइड सत्यापनकर्ता जाँचता है कि सक्रिय Vault रिकॉर्ड सत्यापित signed bundle से मेल खाता है:

- `owner_wallet` एम्बेडेड Platho wallet पते से मेल खाता है;
- `enc_pubkey` X25519 सार्वजनिक key से मेल खाता है;
- `sign_pubkey` bundle signing सार्वजनिक key से मेल खाता है;
- `pq_kem_pubkey`, `pq_kem_pubkey_hash`, और `pq_kem_pubkey_len` ML-KEM-768 सामग्री से मेल खाते हैं;
- `crypto_suite_mask` suite से मेल खाता है;
- `revoked_lt` शून्य है;
- वैकल्पिक `current_key_id` प्राप्त किए गए रिकॉर्ड id की ओर इंगित करता है।

क्लाइंट ऑन-चेन key id का आविष्कार नहीं करता। Vault इसकी गणना स्वामी पते, key जनरेशन, key फ़ील्ड, PQ length, और suite से करता है। क्लाइंट इसके बजाय प्राप्त किए गए रिकॉर्ड को सत्यापित करता है।

## टिकाऊ replay स्टोर

PWA उपलब्ध होने पर निजी कैप्सूल replay सुरक्षा के लिए IndexedDB का उपयोग करता है, एक मेमोरी fallback के साथ। स्टोर कैप्सूल ids को उनकी कैप्सूल समाप्ति तक रखता है और समाप्त प्रविष्टियों को स्थानीय रूप से छाँटता है। यह डिवाइस-स्थानीय स्थिति है और इसे किसी सर्वर की आवश्यकता नहीं है।

## एन्क्रिप्टेड स्थानीय संदेश इतिहास

PWA में एक डिवाइस-स्थानीय एन्क्रिप्टेड संदेश इतिहास स्टोर भी है। यह IndexedDB में सहेजी गई एक गैर-निष्कर्षण-योग्य (non-extractable) WebCrypto AES-GCM-256 key का उपयोग करता है और प्रत्येक संदेश body को प्रमाणित ciphertext के रूप में संग्रहीत करता है। रिकॉर्ड हेडर केवल स्थानीय क्वेरी मेटाडेटा रखता है: id, thread id, टाइमस्टैम्प, दिशा, और वैकल्पिक कैप्सूल id।

हेडर को AES-GCM अतिरिक्त प्रमाणित डेटा के रूप में बाँधा जाता है। thread id, टाइमस्टैम्प, दिशा, कैप्सूल id, nonce, या ciphertext को बदलने से रिकॉर्ड खुलने से रुक जाता है। यदि IndexedDB अनुपलब्ध है, तो ऐप उस सत्र के लिए एन्क्रिप्टेड इन-मेमोरी इतिहास पर वापस आ जाता है और स्थायी ब्राउज़र स्टोरेज में प्लेनटेक्स्ट लिखने से बचता है।
